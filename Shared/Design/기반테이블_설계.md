# 기반 테이블 설계

> 2D 탑다운 방치형 핵앤슬래시 (Unity, 싱글플레이) — Stat / StatDetail / Option / Currency
> 관련 문서: `테이블규약_설계.md`, `스킬시스템_설계.md`, `무기마스터리시스템_설계.md`, `아이템시스템_설계.md`
> **이 문서는 현재 구현 상태를 기술한다.** 행 수·수치는 `ProjectOne/Assets/Project/Data/Tables/` 의 실제 데이터 기준이다.

---

## 1. 개요

### 1.1 이 문서의 범위

여기서 정의하는 네 테이블은 **특정 시스템에 속하지 않고 전 시스템이 공유하는 기반**이다.

| 대상 | 파일 | 시트 | 현재 행 수 |
|---|---|---|---|
| 능력치 | `Stat.xlsx` | `#Enum`, `#Stat`, `#StatDetail` | 23 / 56 |
| 옵션 | `Option.xlsx` | `#Enum`, `#Option` | 36 |
| 재화 | `Currency.xlsx` | `#Currency` | 3 |

### 1.2 왜 기반인가

```
캐릭터 · 몬스터 · 소환물의 능력치        → Stat / StatDetail
장비 옵션 · 스킬 트리 노드 · 버프의 효과   → Option → StatDetail | Skill | SkillModifier
강화 · 승급 · 부활 · 상점의 비용          → Currency
```

**세 시스템(아이템 / 마스터리 / 스킬)이 값의 공급처이고, 이 문서의 테이블이 값의 수신처다.** 공급처마다 다른 스탯 체계를 두면 최종 스탯 계산을 한 곳에서 할 수 없다.

### 1.3 소유 관계

| 정의 | 이 문서 | 사용 규칙 |
|---|---|---|
| `Stat` / `StatDetail` 구조·레이어 | O | **최종 스탯 계산식과 순서는 이 문서 8장이 소유한다.** 데미지 적용은 스킬 10장 |
| `Option` 구조·타입 | O | 장비 옵션 계산은 아이템 5장, 노드 값 계산은 마스터리 6.3 |
| `Currency` | O | 비용 규칙은 아이템 6장, 부활 비용은 맵 8.1 |

### 1.4 런타임 구현 위치

| 대상 | 파일 |
|---|---|
| 스탯 컨테이너 (합성·클램프·모디파이어) | `GamePlay/Unit/Stats/StatContainer.cs` |
| 테이블 → 런타임 인덱스 | `GamePlay/Unit/Stats/StatCatalog.cs` |
| `StatDetail` → (스탯, 레이어) 참조 | `GamePlay/Unit/Stats/StatPart.cs` |
| Base 레이어 조립 (캐릭터/몬스터) | `GamePlay/Unit/Stats/StatContainerFactory.cs` |
| 실시간 상태값 (`CurrentHp`) | `GamePlay/Unit/Stats/Vitals.cs` |
| `Option` → 실제 대상 해석 | `Contents/Items/OptionCatalog.cs` |
| 재화 보유량 | `Core/Currency/Wallet.cs`, `Core/Currency/CurrencyManager.cs` |

## 2. Stat — 능력치 정의

### 2.1 Enum

```
!Enum   StatCategory
        Offensive       공격
        Defensive       방어
        Utility         보조

!Enum   StatDetailTypes
        Base            기본
        Add             추가
        Ratio           증가
        Amp             증폭

!Enum   StatValueTypes
        Flat            고정값
        Percent         비율값
```

`StatCategory` 는 **UI 분류 전용**이다. 계산에 관여하지 않는다.

### 2.2 `Stat` 테이블 (EnumTable)

| 컬럼 | 타입 | 설명 |

### 2.3 Min / Max 클램프

> **클램프는 최종 스탯 계산이 끝난 뒤 딱 한 번 적용한다.**
> **`MinValue` · `MaxValue` 는 0이 아닐 때만 적용한다.** 0이면 그 방향의 제한이 없다 (`StatCatalog.ApplyClamp`).

```
최종값 = (Base + ΣAdd) × (1 + ΣRatio) × (1 + ΣAmp)
         → MinValue != 0 이면 max(값, MinValue)
         → MaxValue != 0 이면 min(값, MaxValue)
```

> **0 을 하한으로 쓸 수 없다** — 구현이 `!= 0f` 로 판정하므로 `MinValue = 0` 은 "제한 없음"과 구분되지 않는다. 음수를 막아야 하는 스탯이 생기면 클램프가 아니라 계산부에서 처리한다.

**클램프에 담긴 의도**

| 스탯 | 값 | 이유 |
|---|---|---|
| `Stat_AtkSpeed` | 0.1 ~ 3 | 과도한 공속으로 애니메이션·판정 주기가 붕괴하는 것을 막는다 |
| `Stat_CritRate` `Stat_DefPen` | ~ 1 | 확률·비율이 100%를 넘을 수 없다 |
| `Stat_CritDamage` | 1.5 ~ | 치명타가 일반 공격보다 약해지는 것을 막는다 |
| `Stat_MaxHp` | 1 ~ | 0이면 소환 즉시 사망한다 |
| `Stat_DamageReduction` `Stat_EvasionRate` `Stat_BlockRate` | ~ 0.8 | **무적 방지.** 셋이 겹쳐도 완전 무효화가 되지 않는다 |

> **`Stat_CritDamage` 의 하한 1.5는 기본값이 아니다** — Base 레이어가 비면 0이 되고 클램프가 1.5로 끌어올린다. 결과적으로 "채우지 않아도 동작"하지만 여기에 의존하지 않는다. 4.1절의 필수 스탯 규칙에 따라 명시적으로 채운다.

## 3. StatDetail — 레이어 분해

### 3.1 왜 Stat과 분리하는가

> **`Stat` 은 값을 담지 않는다.** 최종 수치의 enum이자 메타데이터(표시명·아이콘·분류·클램프)일 뿐이다.
> **값을 바꾸는 모든 것은 `StatDetail` 을 지목한다.** 예외는 없다.

```
Stat_Atk  ←  StatDetail_Atk_Base   (캐릭터·몬스터 기본값)
          ←  StatDetail_Atk_Add    (장비·노드 합연산)
          ←  StatDetail_Atk_Ratio  (증가율)
          ←  StatDetail_Atk_Amp    (증폭)
```

`StatContainer` 의 **입구는 언제나 `StatDetail`, 출구는 언제나 `Stat`** 이다. `SetBase` / `AddBase` / `AddModifier` 는 `StatDetail` 을 받고, `GetStat` 은 `Stat` 을 받는다.

### 3.2 컬럼

| 컬럼 | 타입 | 설명 |
|---|---|---|
| ID | `!StatDetail` | `StatDetail_{스탯}_{레이어}` |
| StatID | `!Stat` | 소속 스탯 |
| StatDetailType | `!StatDetailTypes` | Base / Add / Ratio / Amp |
| StatValueType | `!StatValueTypes` | 이 레이어 값의 성격 |
| DisplayFormat | `!string` | `{0}` 자리에 값이 들어간다 |

> **레이어 판정은 테이블 두 컬럼으로 한다** — 구버전은 enum 이름의 접미사(`_Ratio`)를 문자열로 파싱했으나, 지금은 `StatCatalog.Build()` 가 `StatID` / `StatDetailType` 을 읽어 `StatPart` 구조체를 만든다. ID 명명 규칙은 사람이 읽기 위한 관례일 뿐 판정 근거가 아니다.

### 3.3 레이어 커버리지 — 전부 4개를 만들지 않는다

**현재 56행.** 23개 스탯 × 4레이어 = 92가 아니다.

| 레이어 구성 | 대상 스탯 |
|---|---|
| Base / Add / Ratio / Amp (4종) | `Atk` `MaxHp` `HpRegen` `Def` `LifeOnHit` |
| Base / Add (2종) | 나머지 18종 |

> **비율 옵션은 위 5개 스탯에만 붙일 수 있다.** `Stat_CritRate` 는 그 자체가 이미 비율이다. 여기에 "치명타 확률 +10% 증가"를 붙이면 **비율의 비율**이 되어 최종값을 암산할 수 없다. 확률·보너스 계열은 `Base + ΣAdd` 합연산으로만 쌓는다.
>
> 데이터를 만들 때 `OPT_CRIT_RATE_RATIO` 같은 옵션을 요구하지 않는다. 대응하는 `StatDetail` 행이 아예 없다.

### 3.4 값의 공급처

| 레이어 | 공급처 | 성격 |
|---|---|---|
| `Base` | `CharacterStat` / `MonsterStat` | 레벨 성장. 주체당 1행 |
| `Add` `Ratio` `Amp` | `EquipOption` / `SkillTreeNode` / `WeaponMastery` / `MasteryLevelBonus` / 버프 | 누적. 여러 출처가 합산 |

**`Base` 레이어에 장비·노드·버프가 값을 넣을 수 없다.** `StatContainer.AddModifier` 가 Base 레이어를 받으면 `ArgumentException` 을 던진다. 넣을 수 있게 하면 장비를 벗었을 때 기본 능력치가 사라진다.

### 3.5 DisplayFormat

```
StatDetail_Atk_Add        공격력 {0}
StatDetail_Atk_Ratio      공격력 {0}%
StatDetail_Atk_Amp        공격력 증폭 {0}%
```

- `Percent` 값은 저장은 0.15, 표시는 15로 한다. **× 100은 표시 시점에 코드가 한다.**
- `Ratio` 와 `Amp` 는 둘 다 `%` 지만 문구가 다르다. 곱연산 레이어가 서로 다르다는 것을 플레이어가 구분할 수 있어야 한다.
- 소수 자릿수는 포맷 문자열에 넣지 않고 `StatValueType` 으로 코드가 결정한다.
- 부호(`+`)는 포맷에 넣지 않는다. 값의 부호를 보고 표시 코드가 붙인다.

> **한 스탯 안에서 `StatValueType` 이 레이어마다 다를 수 있다** — `Stat_MoveSpeed` 는 `Flat`(절대 속도)이지만 `StatDetail_MoveSpeed_Add` 는 `Percent`("이동 속도 증가 {0}%")다. 표시는 레이어의 `StatValueType` 을 따르고, 계산은 8장의 합성식을 그대로 따른다.

### 3.6 모디파이어의 출처(source) 태그

`StatContainer.AddModifier(detail, value, source)` 의 세 번째 인자는 **일괄 제거용 태그**다.

```
장비 착용   → AddModifier(..., "Equipment")
장비 해제   → RemoveAllFromSource("Equipment")
```

현재 쓰이는 태그는 `"Equipment"`(`EquipmentAspect`), `"Mastery"`(`MasteryAspect`), 버프 인스턴스별 태그(`BuffRuntime`)다. 태그가 비면 인덱스에 등록되지 않으므로 개별 `RemoveModifier(mod)` 로만 뗄 수 있다.

## 4. 필수 스탯

### 4.1 Base 레이어 필수 항목

`CharacterStat` / `MonsterStat` 은 세로형이라 **"이 주체는 공격속도 행이 없다"가 표현 가능**하다. 그런데 스킬 4장의 `cycleTime = Cooldown / useSpeed` 가 공속으로 나누므로, 비어 있으면 계산이 붕괴한다.

| StatDetail | 필수 여부 |
|---|---|
| `StatDetail_Atk_Base` | 필수 |
| `StatDetail_AtkSpeed_Base` | **필수** — 없으면 공격 주기가 0으로 나뉜다 |
| `StatDetail_MaxHp_Base` | 필수 |
| `StatDetail_Def_Base` | 필수 |
| `StatDetail_CritDamage_Base` | `CritRate_Base` 가 있으면 필수 |

### 4.2 현재 `CharacterStat` (10행)

캐릭터는 1종이므로 `CharacterStat` 에 그룹 키가 없다. 성장식은 `BaseValue + PerLevel × (Level - 1)` 이며 **1레벨 기준**이다.

| StatDetailID | BaseValue | PerLevel |
|---|---|---|
| `StatDetail_Atk_Base` | 3 | 2 |
| `StatDetail_AtkSpeed_Base` | 1.5 | 0 |
| `StatDetail_CritRate_Base` | 0.1 | 0 |
| `StatDetail_CritDamage_Base` | 1.5 | 0 |
| `StatDetail_MaxHp_Base` | 1000 | 20 |
| `StatDetail_HpRegen_Base` | 20 | 1 |
| `StatDetail_Def_Base` | 10 | 1 |
| `StatDetail_MoveSpeed_Base` | 2.5 | 0 |
| `StatDetail_EvasionRate_Base` | 0.1 | 0 |
| `StatDetail_BlockRate_Base` | 0.1 | 0 |

몬스터는 `MonsterStat.GroupID` 로 묶이며 같은 성장식을 쓴다 (`StatContainerFactory.ForMonster`).

### 4.3 `Stat.DefaultValue` 컬럼을 두지 않는다

"Base가 비면 이 값을 쓴다"는 기본값 컬럼은 두지 않는다. 값이 자동으로 채워지면 **데이터가 빠진 것을 아무도 눈치채지 못한다.** 몬스터 100종 중 한 종의 공속을 빠뜨려도 게임은 돌아가고, 나중에 "얘만 왜 느리지"를 역추적하게 된다.

### 4.4 소환물

소환물은 자기 스탯 그룹을 갖지 않고 **주인의 스탯을 비율로 상속**한다 (`Summon.InheritStatType_1/2` + `InheritStatRatio_1/2`). 상속 슬롯이 2개뿐이라 공속을 상속하지 못하는 경우가 많으므로, **소환물 스킬은 `SkillCategory = Active` 로 만든다.** `Normal` 은 공속을 참조한다.

`InheritStatType` 은 결과(`Stat`)로 적혀 있는데 값을 넣는 입구는 `StatDetail` 이므로, `StatCatalog.TryGetBaseDetail(stat, out detail)` 이 Base 레이어를 역참조한다.

## 5. 유닛 런타임 상태

`Stat` 이 정적 정의라면, 실제 전투 주체는 **`StatContainer`** 를 동적 데이터로 들고 있다. 캐릭터·몬스터·소환물이 같은 컨테이너를 쓴다.

### 5.1 컨테이너가 갖는 것

| 항목 | 성격 |
|---|---|
| 스탯별 레이어 누적값 (Base/Add/Ratio/Amp) | 출처가 바뀔 때 갱신 |
| 스탯별 최종값 캐시 + dirty 플래그 | `GetStat` 시점에 lazy 재계산 |
| 출처(source)별 모디파이어 인덱스 | `RemoveAllFromSource` 용 |
| `Version` | 값이 바뀔 때마다 증가 |
| `CurrentHp` (`Vitals`) | **유일한 상태값.** 스탯이 아니다 |

`Stat_MaxHp` 는 계산되는 값이고 `CurrentHp` 는 소모·회복되는 값이다. 둘을 같은 층위로 두면 최대 체력을 올리는 옵션이 현재 체력을 직접 건드리게 된다.

> **`Version` 은 이벤트의 대체물이다** — 장비 교체 한 번에 모디파이어가 수십 개 붙는다. 이벤트면 그때마다 소환물이 전부 재계산하지만, 버전 비교는 틱당 int 비교 한 번이다. 소환물이 주인 스탯 변경을 감지하는 데 쓴다.

### 5.2 최대 체력이 바뀔 때 — 비율 유지

```
비율 = CurrentHp / MaxHp(이전)
CurrentHp = clamp(round(MaxHp(신규) × 비율), 1, MaxHp(신규))
```

`Vitals.RescaleToNewMaxHp(previousMaxHp)` 이며 **호출자가 변경 직전의 최대치를 넘긴다.**

> 차분 가산(`CurrentHp += ΔMaxHp`)은 최대 체력 장비를 반복 착·탈하면 체력이 회복되는 악용이 가능하다. 비율 유지는 최대 체력이 줄 때 현재 체력도 줄지만 **이 때문에 사망하지는 않는다(하한 1).**

### 5.3 체력 회복 시점

| 시점 | 회복 |
|---|---|
| 필드(액트 내 맵) 이동 | **회복하지 않는다** |
| 던전 입장 | **전체 회복** (`DungeonDirector`) |
| 마을 귀환 | 전체 회복 |
| 부활 | 전체 회복 |
| 자연 재생 | `Stat_HpRegen` 만큼 **1초마다** (`UnitBase` 의 1초 주기 틱) |

필드 진행이 연속된 소모전이 되도록 맵 이동에서는 회복하지 않는다. 던전은 입장 횟수를 소모하는 독립 시도이므로 항상 완전한 상태에서 시작한다.

### 5.4 사망과 부활

| 상황 | 처리 | 부활 후 체력 |
|---|---|---|
| 필드에서 사망 | 해당 맵의 `MapAnchor` 에서 부활 | 전체 회복 |
| 던전에서 사망 | 재화를 소모해 사망 지점에서 부활 | 전체 회복 |
| 부활 포기 / 부활 횟수 소진 | 던전 실패. 마을로 귀환 | 전체 회복 |

- **부활 후에는 항상 전체 회복이다.** 부활 자체가 리셋이므로 상황별로 다르게 두지 않는다.
- **부활 지점은 씬의 `MapAnchor` 마커가 소유한다.** `Map` 테이블에 좌표 컬럼이 없다.
- 던전 부활의 **재화·비용·증가폭·최대 횟수는 `Dungeon` EnumTable이 소유한다** (`맵시스템_설계.md` 8.1절). 던전마다 값이 다르다.
- **던전에서 부활해도 입장 횟수를 다시 소모하지 않는다.** 횟수는 입장 시점에 이미 소모됐다.

### 5.5 저장 위치

**서버 저장이 원칙이다.** 진행도·인벤토리·재화는 서버가 소유하고, 로컬에는 개인 옵션 설정(사운드·그래픽·조작)만 저장한다.

| 항목 | 결과 |
|---|---|
| 던전 일일 초기화 기준시 | 서버 시간 기준 |
| `CurrentHp` | **저장하지 않는다** — 5.6절 |
| 몬스터 리젠 시각 | **저장하지 않는다** — 로컬 세션 값 (`몬스터시스템_설계.md`) |

> 각 시스템 문서의 "저장 데이터" 절은 **서버가 보관하는 데이터**를 뜻한다.

### 5.6 `CurrentHp` 는 세션 값이다

체력은 매 초 변하므로 서버에 보내지 않는다. 싱글플레이라 다른 플레이어에게 영향을 주지 않고, 통신량 대비 얻는 것이 없다.

대신 **세션이 끊기면 마을에서 시작한다.**

```
앱 종료 · 재접속 → 마을 · 전체 회복
```

> 마지막 위치를 유지한 채 체력만 초기화하면 **"죽을 것 같을 때 앱을 껐다 켜기"** 가 완전한 회복 수단이 된다. 필드 이동에서 회복하지 않기로 한 규칙(5.3)이 통째로 무력해진다. 마을 귀환은 이미 전체 회복 지점이므로, 세션 종료를 마을 귀환으로 처리하면 규칙이 하나 늘지 않는다.

### 5.7 변경 통지

`Vitals` 는 값이 바뀔 때 이벤트를 쏘지 않고 **dirty 플래그만 세운다.** 다단히트·흡혈·DoT 스택이면 한 프레임에 수십 번 변하기 때문이다. 실제 발행은 `UnitBase.ManualTick` 이 프레임당 1회 모아서 한다.

## 6. Option — 값의 출처와 대상을 잇는다

### 6.1 Enum

```
!Enum   OptionTypes
        Stat            능력치 증감
        SkillGrant      스킬 획득
        SkillLevel      스킬 레벨 +N
        Modifier        스킬 변형
```

### 6.2 `Option` 테이블 (EnumTable)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| ID | `!Option` | `OPT_` 접두 |
| OptionType | `!OptionTypes` | 판별 컬럼 |
| OptionTarget | `!string` | 타입별 참조 대상 |

**`OptionTarget` 이 `!string` 인 이유** — `OptionType` 에 따라 가리키는 테이블이 다르다. 다형 컬럼 규약(`테이블규약_설계.md` 5장)에 따라 `!string` + 판별 컬럼 조합을 쓴다. 부팅 시 `OptionCatalog.Build()` 가 문자열을 실제 enum으로 1회 해석하며, 해석 실패는 에러 로그로 드러난다.

| OptionType | OptionTarget | 값의 해석 |
|---|---|---|
| `Stat` | `StatDetail.ID` | 해당 레이어에 값 누적 |
| `SkillGrant` | `Skill.ID` | 값 미사용. 스킬 습득 |
| `SkillLevel` | `Skill.ID` | 스킬 레벨 +N |
| `Modifier` | `SkillModifier.ID` | `SkillModifier.Operator` 가 값 해석을 결정 |

### 6.3 Option이 하는 일

**공급처와 수신처를 분리하는 중간층**이다.

```
[공급처]                                [Option]              [수신처]
EquipOption.Opt1~4_ID / UnlockOpt_ID  ──┐
SkillTreeNode.Option / Option_02      ──┼──→ OPT_ATK_ADD ──→ StatDetail_Atk_Add
WeaponMastery.LevelBonusOption        ──┤
MasteryLevelBonus.LevelBonusOption    ──┘
```

**값은 언제나 부착처가 소유하고, `Option` 은 "무엇을 건드리는가"만 정의한다.** 공급처가 `StatDetail` 을 직접 가리켜도 동작은 하지만, 그러면 "붙일 수 있는 옵션 목록"이 존재하지 않게 된다.

수신처별 소비자는 다음과 같다.

| OptionType | 소비자 |
|---|---|
| `Stat` | `StatContainer.AddModifier` (`EquipmentAspect` / `MasteryAspect`) |
| `SkillGrant` | 보유 스킬 목록 등록 |
| `SkillLevel` `Modifier` | `GamePlay/Skill/SkillResolver.cs` — 스탯 식에 들어가지 않는다 |

### 6.4 현재 36행

| 구성 | 행 수 | 비고 |
|---|---|---|
| `OptionType = Stat` | 32 | `OPT_{스탯}_{레이어}` |
| `OptionType = SkillGrant` | 1 | `OPT_LEARN_DualBlades_Active_01` |
| `OptionType = Modifier` | 3 | `OPT_DMG_*` / `OPT_APPEND_*` / `OPT_ATKSPEED_*` |
| `OptionType = SkillLevel` | 0 | 데이터 없음 |

**네이밍**

```
OPT_{스탯}_{레이어}          OPT_ATK_ADD / OPT_MAX_HP_RATIO / OPT_DEF_AMP
OPT_LEARN_{스킬}             OPT_LEARN_DualBlades_Active_01      (SkillGrant)
OPT_{항목}_{대상}            OPT_DMG_DualBlades_Active_01        (Modifier)
                             OPT_APPEND_DualBlades_AtkSpeedBuff
                             OPT_ATKSPEED_DualBlades_Buff
```

### 6.5 옵션 폭증 관리

`Modifier` 옵션은 **대상 스킬 × 변경 항목**만큼 늘어난다. 마스터리 4종 × 스킬 3~4개 × 항목 4개면 최대 64행이다.

행이 늘어나는 것 자체는 문제가 아니다. 문제는 **ID 문자열에서 대상 스킬을 알아내려 하면 명명 규칙이 흔들리는 순간 조용히 깨진다**는 점이다.

> **판정은 문자열 파싱이 아니라 참조로 한다**
>
> ```
> Option(Modifier) → SkillModifier.Scope_Skill                  → 대상 스킬
> Option(Modifier) → SkillModifier.Scope_Effect → SkillEffect   → 대상 스킬 (역인덱스)
> ```
>
> `SkillModifier` 가 이미 대상을 타입 안전하게 갖고 있다. ID 문자열은 사람이 읽기 위한 관례일 뿐 판정 근거가 아니다.

## 7. Currency — 재화

### 7.1 테이블 (EnumTable)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| ID | `!Currency` | |
| Name | `!string` | |
| Desc | `!string` | |
| Icon | `!string` | |

**현재 3종**

| ID | 표시명 | 설명 | 주 용도 |
|---|---|---|---|
| `Gold` | 골드 | 일반적인 재화이다 | 강화·승급 비용 |
| `Dia` | 다이아 | 유료 재화이다 | |
| `Ruby` | 루비 | 부분유료 재화이다 | 던전 부활 비용 |

- **시간 재생(Regen) 컬럼은 없다.** 재화가 시간에 따라 차오르는 개념을 쓰지 않는다.
- **입장권·티켓 재화는 없다.** 던전은 입장 비용 대신 일일 카운터만 갖는다 (`맵시스템_설계.md` 8.2절).

### 7.2 왜 Item이 아닌가

재화는 **인벤토리 슬롯을 차지하지 않고, 개수가 하나의 카운터로 관리되며, 등급·스택·인스턴스 개념이 없다.** `Item` 에 넣으면 이 네 가지가 전부 예외 처리가 된다.

대신 **ID 타입이 다르다는 대가**를 치른다. `Item.ID` 는 `int`, `Currency.ID` 는 문자열 EnumTable이다. 두 가지를 한 컬럼에 담아야 하는 곳(`Reward.TargetID`)은 `!string` 으로 두고 타입별로 파싱한다.

### 7.3 참조처

```
EquipEnhance.CostCurrencyID    → Currency    (!Currency 직접 참조)
EquipPromotion.CostCurrencyID  → Currency    (!Currency 직접 참조)
Dungeon.RevivalCostType        → Currency    (!Currency 직접 참조)
Costume.CostCurrencyType       → Currency    (!Currency 직접 참조)
Reward.TargetID                → Currency    (!string, RewardType=Currency일 때)
```

앞의 넷은 재화만 담으므로 `!Currency` 로 타입 안전하게 두고, 마지막은 다형 컬럼이라 `!string` 이다.

### 7.4 런타임

`Core/Currency/Wallet.cs` 가 도메인 모델(`Dictionary<Currency, int>`)이고, `Core/Currency/CurrencyManager.cs` 가 공개 API(`GetAmount` / `Add` / `TrySpend` / `SetAmount`)를 제공한다. 보유 상한은 두지 않는다.

## 8. 계산 순서 — 어디서 무엇이 확정되는가

```
[1] Base 레이어 수집                     StatContainerFactory
      CharacterStat / MonsterStat + 레벨
      → BaseValue + PerLevel × (Level - 1)

[2] Add / Ratio / Amp 레이어 수집         IHeroAspect 계층
      마스터리 레벨 보너스                 MasteryAspect
      현재 무기의 스킬 트리 노드            MasteryAspect
      장비 옵션 (Opt1~4 + UnlockOpt)      EquipmentAspect
      버프                                BuffRuntime

[3] 스탯별 합성                          StatContainer.GetStat
      (Base + ΣAdd) × (1 + ΣRatio) × (1 + ΣAmp)

[4] 클램프                               StatCatalog.ApplyClamp, 이 시점 1회

[5] 데미지 계산에 투입                     스킬 문서 10장
```

> **이 식은 여기에만 둔다.** 마스터리 8.3절과 아이템 5.3절은 자기가 [2]에 무엇을 공급하는지만 서술하고, 식과 클램프는 이 절을 참조한다. 식을 복제하면 레이어가 하나 늘 때 세 곳을 고쳐야 한다.

`Percent` 값은 [3]까지 전부 소수(0.15)로 다루고, 표시할 때만 × 100 한다.

**[2]의 적용 순서는 결과에 영향을 주지 않는다.** 같은 레이어에 들어가는 값은 전부 합산이므로 어느 Aspect가 먼저 붙든 최종값이 같다. 순서가 의미를 갖는 것은 스킬 리졸브 파이프라인(`Replace` / `Append`)뿐이다 (스킬 11장).

### 8.1 유틸리티 스탯의 적용 지점

계산식 밖에서 소비되는 스탯들이다. **어디에 쓰이는지가 스탯 정의만으로는 드러나지 않으므로** 여기에 고정한다.

| 스탯 | 적용 대상 |
|---|---|
| `Stat_ExpBonus` | **적 처치 경험치에만** 곱한다. 퀘스트·던전 클리어 경험치는 고정값 |
| `Stat_GoldDropBonus` | **적 처치로 얻는 골드 수량에만** 곱한다 (`RewardContext.MonsterKill`) |
| `Stat_MoveSpeed` | 유닛의 **절대 이동 속도**(유닛/초). 계수가 아니라 `UnitBase` 가 `GetStat` 값을 그대로 쓴다 |
| `Stat_PickupRange` | 자석 펫의 **절대 흡입 반경**. 0이면 `HeroMagnet` 인스펙터 기본값으로 떨어진다 |
| `Stat_HpRegen` | 1초마다 이 값만큼 회복 |
| `Stat_MaxBreakGauge` | 몬스터 브레이크 게이지 최대치 |

> **보상 시스템에 지급 맥락이 필요하다**
>
> `Reward` 테이블은 "무엇을 얼마나 주는가"만 갖고 **누가 왜 주는지는 모른다.** 같은 보상 그룹이 몬스터 드랍과 퀘스트 보상 양쪽에 쓰일 수 있으므로 테이블만으로는 구분할 수 없다.
>
> 따라서 지급 API가 맥락을 인자로 받는다.
>
> ```
> RewardGranter — RewardContext = MonsterKill | QuestComplete | DungeonClear | ConsumableUse
> ```
>
> `MonsterKill` 일 때만 `GoldDropBonus` 를 적용한다. 이 규칙은 데이터가 아니라 코드가 소유한다.

## 9. 부트 순서

카탈로그는 테이블 로드 이후에만 구축할 수 있고 서로 의존한다. `Core/Flow/States/BootState.cs` 의 실제 순서는 다음과 같다.

```
TableBootLoader.LoadAllAsync()
  → StatCatalog.Build()          StatDetail → StatPart, 클램프, Base 역참조
  → SkillParamCatalog.Build()    EffectParam 슬롯 의미
  → OptionCatalog.Build()        OptionTarget 문자열 해석
  → EquipmentCatalog.Build()
  → MasteryCatalog.Build()       LevelBonusOption 해석에 OptionCatalog 의존
  → SkillModifierCatalog.Build() ParamKey 굽기에 SkillParamCatalog 의존
  → MonsterCatalog.Build()
  → CostumeCatalog.Build()
  → RewardCatalog.Build()
  → ConsumableCatalog.Build()
  → QuestCatalog.Build()         상자 보상 그룹 검증에 RewardCatalog 의존
  → ShopCatalog.Build()
```

각 카탈로그는 `Build()` 이전에 조회하면 에러 로그를 남긴다.

## 11. 검증 규칙

### Stat / StatDetail

- `StatDetail.StatID` 가 `Stat` 에 존재 (오류)
- 같은 `(StatID, StatDetailType)` 조합이 2행 이상 (오류)
- `MinValue > MaxValue` (오류, 둘 다 0이 아닐 때)
- `DisplayFormat` 에 `{0}` 이 없으면 (오류)
- 파트맵 수와 `StatDetail` 행 수 불일치 — `StatCatalog.Build()` 가 런타임 에러 로그
- 어느 공급처에서도 참조되지 않는 `StatDetail` (경고) — 죽은 데이터

### 필수 스탯

- `CharacterStat` / `MonsterStat` 의 각 그룹에 `Atk` / `AtkSpeed` / `MaxHp` / `Def` 의 `_Base` 가 모두 있는가 (오류)
- `CritRate_Base` 가 있으면 `CritDamage_Base` 도 있는가 (오류)
- `CharacterStat` / `MonsterStat` 이 `_Base` 계열이 아닌 `StatDetail` 을 참조 (오류)
- `EquipOption` / `SkillTreeNode` 가 가리키는 옵션의 대상이 `_Base` 계열 (오류) — 런타임에서는 `AddModifier` 가 예외를 던진다

### Option

- `OptionType` 별 `OptionTarget` 파싱·실존 검증 (오류) — `OptionCatalog.Build()` 가 런타임에도 검사한다
- 어느 공급처에서도 참조되지 않는 `Option` (경고)
- `WeaponMastery.LevelBonusOption` / `MasteryLevelBonus.LevelBonusOption` 이 `OptionType=Stat` 이 아님 (오류) — 무기와 무관하게 적용되므로 모디파이어를 붙일 수 없다 (`MasteryAspect.applyStatOption` 의 `statOnly` 가드)

### Currency

- 참조처(`CostCurrencyID`, `RevivalCostType`, `Reward.TargetID`)의 값이 `Currency` 에 존재 (오류)

## 12. 미결 / 다음 작업

- **`SkillLevel` 옵션이 0행** — 타입과 해석 경로는 있으나 데이터가 없다. 스킬 레벨 개념을 쓸 때 채운다.
- **`Stat_MaxBreakGauge` 의 Base 값이 `CharacterStat` 에 없다** — 브레이크는 현재 몬스터 전용이라 정상이나, 히어로가 브레이크 대상이 되면 필요해진다.
- **`Ruby` 획득 경로 없음** — 던전 부활 소모처만 있고 획득처가 정해져 있지 않다.
- **재화 보유 상한 없음** — 필요해지면 `Currency` 에 컬럼을 추가한다.
- **로컬라이징** — `Stat.Name` / `Currency.Name` / `DisplayFormat` 이 직접 텍스트다. 다국어가 필요해지면 키 방식으로 전환한다.
