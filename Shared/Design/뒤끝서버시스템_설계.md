# 뒤끝 서버 시스템 설계

서버 작업을 할 때 알아야 할 것과 지금까지 처리한 방법을 모은 참고 문서다.
남은 작업은 `출시전 작업.md` / `출시후 작업.md` 에 따로 있다.

## 1. 구조 한눈에

```
클라(Unity) ── NetworkManager.Request* ── BackndFunctionCaller
                                              │  InvokeFunction("ProjectOneFunction", { action, req, rid?, retry? })
                                              ▼
서버(뒤끝 펑션) ── BFunc.Function ── action 분기 ── 핸들러 ── USER_* 테이블
```

- **서버 권위**: 재화·아이템·진행도가 바뀌는 판정은 서버가 한다. 클라는 요청하고 응답을 반영한다
- **펑션은 하나다**: 뒤끝 콘솔에 `ProjectOneFunction` 하나만 등록하고, 요청 본문의 `action` 으로 갈라 처리한다
- **코드를 공유한다**: 서버 csproj 가 클라의 `Assets/Project/Scripts/Core/Network/Shared/**`(DTO·패킷·규칙)와 `Core/ExcelData/*.cs`(테이블 파서)를 링크 컴파일한다. 판정 규칙은 한 벌뿐이다
- **테이블도 공유한다**: `Assets/Project/Data/Tables/*.bytes` 가 서버 패키지의 `Tables\` 에 동봉된다. `GameData.EnsureLoaded`(`Function_GameData.cs`)가 콜드스타트에 한 번 읽는다. **테이블을 바꾸면 서버 재배포가 동기화 절차다**

| 위치 | 내용 |
|---|---|
| `Server/Functions/BackendFunction/Function_*.cs` | 서버 핸들러(영역별 파일) |
| `Assets/Project/Scripts/Core/Network/Shared/` | 클라·서버 공유: `Dto/`, `Packet/`, 영역별 `*Rules.cs`, `Reward/`, `FunctionName.cs` |
| `Assets/Project/Scripts/Core/Network/` | 클라 전송: `NetworkManager`, `Backend/BackndFunctionCaller`, `NetworkFailureHandler`, flush·배처·티커 |

## 2. 호출 규약

### 서버 진입점 — `Function_Main.cs`
- 클래스·메서드 이름은 반드시 `BackendFunction.BFunc.Function(Stream, ILambdaContext)` 다. 뒤끝에 등록된 핸들러 이름이 고정이라 다르면 `Unable to load type 'BackendFunction.BFunc'` 로 로드에 실패한다
- 어셈블리에서 `public` + `Stream` 반환 + `(Stream, ILambdaContext)` 인자를 가진 메서드는 이것 하나뿐이어야 한다. 핸들러는 인자 없는 `public Stream XXX()` 로 둔다
- 순서: `Backend.Initialize(ref stream)` 1회 → `Backend.Content["action"]` 으로 `dispatch` → 핸들러. 핸들러에서 `Initialize` 를 다시 부르지 않는다

### 요청·응답
- 요청: `Backend.Content["req"]` 에 요청 DTO 의 JSON 이 들어 있다(`req` 는 뒤끝 규약이 아니라 클라·서버 약속). `JsonConvert.DeserializeObject<T>` 로 읽는다
- 응답: `ServerResponse`(success, error)를 상속한 DTO. `FuncResult.Json(payload)` / `FuncResult.Error(message)`(`Function_Common.cs`)로 만든다
  - 둘 다 `Backend.StringToStream` 을 쓴다. `JsonToStream` 은 문자열을 한 번 더 직렬화해 이중 인코딩된다
- DTO 는 public 필드만 쓴다 — 클라 `JsonUtility` 와 서버 `Newtonsoft.Json` 양쪽에서 직렬화되어야 한다. Dictionary 는 `JsonUtility` 가 못 다뤄 List 로 둔다

### 클라 — `BackndFunctionCaller`
- 항상 `FunctionName.Deployed` 로 `InvokeFunction` 하고, 본문에 `action` + `req` 를 싣는다
- 뒤끝 동기 호출은 내부에서 Unity 메인 스레드 API 를 써서 스레드풀로 보낼 수 없다. `SendQueue.Enqueue` 로 보낸다(부트 씬의 `SendQueueMgr` 가 매 프레임 `Poll`)
- 응답은 `{"result":"<응답 JSON>"}` 으로 감싸여 온다. `bro.GetReturnValuetoJSON()["result"]` 를 꺼내 역직렬화한다
- 같은 `action` 이 진행 중이면 두 번째 호출은 **콜백 없이** 버려진다. 콜백을 기다리는 호출부는 같은 요청을 겹쳐 보내지 않도록 스스로 막아야 한다
- `SendQueue` 는 넣은 순서대로 처리한다. 먼저 반영돼야 하는 요청(필드 처치 배치)은 앞에 넣는다 — `NetworkManager` 의 여러 `Request*` 가 `FlushFieldBatch()` 를 먼저 부르는 이유다

## 3. 데이터 저장

### 테이블
유저당 1행, `Data` 컬럼 하나에 DTO JSON 을 넣는다. 콘솔에서 테이블을 먼저 만들어야 한다(없으면 조회가 실패한다).

| 테이블 | DTO | 내용 |
|---|---|---|
| `USER_INFO` | (컬럼) | 유저 존재 표시. `Exp`, `NicknameChangeCount` 컬럼 |
| `USER_CURRENCY` | `CurrencyDto` | 재화 |
| `USER_INVENTORY` | `InventoryDto` | 스택 아이템·장비 인스턴스·`nextEquipmentUid` |
| `USER_LOADOUT` | `LoadoutDto` | 장착 8슬롯, 경험치·레벨 |
| `USER_COSTUME` | `CostumeDto` | 보유·착용 코스튬 |
| `USER_PET` | `PetDto` | 보유·장착 펫, 강화 |
| `USER_MASTERY` | `MasteryDto` | 마스터리 경험치·스킬트리 |
| `USER_QUEST` | `QuestDto` | 퀘스트 진행 |
| `USER_DUNGEON` | `DungeonProgressDto` | 최고 단계, 입장 횟수, 진행 중인 런 |
| `USER_FIELD` | `FieldSessionDto` | 필드 정산 세션(시드·epoch·다음 처치 번호), 필드보스 처치 기록 |
| `USER_SHOP` | `ShopDto` | 상품 구매 횟수 |
| `USER_DAILYBONUS` | `DailyBonusDto` | 출석 |
| `USER_HEROPASS` | `HeroPassDto` | 히어로패스 시즌·수령 |
| `USER_RANKDATA` | (컬럼) | 랭킹 점수 컬럼(`BattlePower`). **비공개** — 리더보드 대상 |
| `USER_PROFILE` | `PlayerProfileDto` | 남에게 보이는 정보 스냅샷. **공개** |
| `USER_REQUEST` | `RequestRecordDto` | 마지막으로 처리한 요청 1건(재전송 중복 방지) |

### 읽고 쓰는 방법
- 읽기: `MyData.Load("USER_X", out dto, out err)`(`Function_Common.cs`) — 내 행의 `Data` 를 DTO 로
- 쓰기: `Backend.GameData.Update(table, new Where(), param)` — 내 단일 행 수정
  - `UpdateV2(table, inDate, Backend.UserInDate, param)` 는 쓰지 못한다. 펑션 컨텍스트에서 `Backend.UserInDate` 가 비어 `UndefinedParameterException` 이 난다
- 여러 테이블을 함께 바꾸면 `Backend.GameData.TransactionWriteV2(List<TransactionValue>)` 로 묶는다
- 새 테이블은 GetUserData(`Function_Auth.cs` 의 `ensureDomainRow`)에서 "없으면 기본값으로 생성"을 한다. 개발 중 추가한 테이블이 기존 유저에게 자동으로 생긴다
- 핸들러 처리 순서: `GameData.EnsureLoaded` → `req` 파싱 → `MyData.Load` → 판정 → 변경 → 저장

### 재화는 증감으로만 반영한다
응답에 "차감한 양"(`spent`)이나 "얻은 것"(`rewards`)을 싣고, 클라는 그만큼 더하거나 뺀다. 서버의 최종 값으로 덮어쓰지 않는다.
필드에서 주웠지만 아직 정산되지 않은 재화가 클라에 먼저 반영돼 있기 때문이다 — 덮어쓰면 그 몫이 사라진다.

### 지급의 한 입구
보상을 주는 모든 경로(던전·상점·퀘스트·우편·출석·패스·필드보스)는 `RewardRoller.Roll`(공유, `Shared/Reward/`)로 굴리고 `RewardApplier`(`Function_Reward.cs`)로 인벤토리·재화에 반영한다. 장비 UID 는 서버가 `nextEquipmentUid` 로 매긴다.
수집품(펫·코스튬)은 아이템으로 지급되고, 지급 단계에서 보유로 전환된다(펫·코스튬 ID = 아이템 ID, 보유 중이면 제외).

## 4. 새 펑션 추가 절차

1. **공유 규칙** `Core/Network/Shared/<영역>/<영역>Rules.cs` — 클라의 사전 판정과 서버의 최종 판정이 같은 코드를 쓴다
2. **패킷** `Shared/Packet/Packet_<영역>.cs`(요청, `ServerResponse` 상속 응답) + `FunctionName` 에 action 상수
3. **서버** `Function_<영역>.cs` 에 `public Stream NewAction()` + `Function_Main.cs` `dispatch` 에 `case`
4. **중복 방지 대상 등록** — 유저가 직접 누르는 상태 변경 요청이면 `RequestOps.IsGuarded`(`Function_Request.cs`)에 더한다. 빼먹으면 재전송 때 두 번 반영된다
5. **클라** `NetworkManager.Request<X>` — 전송 방식은 5절에서 고른다
6. **새 테이블**이 필요하면 콘솔에서 먼저 만들고(`Data` 컬럼, 비공개) GetUserData 에 ensure 를 넣는다
7. **검증**: 서버 `dotnet build -c Release` / Unity 컴파일 → `Build.bat` 배포 → 실행 확인. 클라만 바꿨으면 재배포는 필요 없다

## 5. 클라 전송 방식 고르기

| 방식 | 언제 | 딤 | 실패하면 | 예 |
|---|---|---|---|---|
| **딤 요청** | 버튼 한 번에 결과가 나와야 하는 행위. 응답을 받은 뒤 반영 | 켬 | 자동 재전송 → 안내(6절) | ShopBuy, EquipmentPromote, DailyBonusClaim, MailReceive, DungeonEnter |
| **dirty flush** | 클릭은 즉시 로컬 반영, 화면 닫기·일시정지·종료 때 최종 상태를 한 번 전송 | 끔 | dirty 를 되살려 다음 기회에 재전송 | SaveLoadout, SaveAppearance, SaveMasteryTree, SaveQuestProgress (`LoadoutSyncFlusher`) |
| **묶음 배처** | 연타하는 행위. 미리 적용하고 묶어서 전송 | 끔 | 묶음을 되돌리고 서버 값에 맞춤 | EquipmentEnhance, PetEnhance (`GrowthBatcher<T>`) |
| **필드 처치 배치** | 처치마다 시드로 굴린 결과를 주기적으로 정산 | 끔 | 원장을 그대로 두고 다음 주기에 재전송 | FieldSettle (`FieldSettleTicker` 20초, `FieldKillLedger`) |
| **뒤따라 보내기** | 로컬에서 이미 끝낸 일을 서버에 알림 | 끔 | 로그만. 다음 로그인에 서버 값으로 정리 | UseSkillPointItem, ItemSpend (`ItemSpendSender`) |

- 딤은 `Invoke` 의 `showOverlay` 로 정한다. 전투 중 자동으로 일어나는 일(퀘스트 자동 완료, 필드보스 정산, 던전 종료 정산)은 딤을 쓰지 않는다
- 딤 요청만 요청 번호(`rid`)가 붙고 자동 재전송된다

## 6. 실패 처리

실패는 두 종류로 가른다(`BackndFunctionCaller.handleResponse`).

| 종류 | 판별 | 서버 상태 | 처리 |
|---|---|---|---|
| **거절** | 응답 본문이 왔고 `success == false` + `error` 있음 | 바뀌지 않음 | 경고 메시지(`UIPrefab_AlertMessage`) |
| **통신 실패** | 응답 없음 · 20초 시간 초과 · 형식 오류(펑션 시간 초과 봉투) | 알 수 없음 | 같은 요청을 다시 보냄 |

대상은 딤 요청뿐이다. 딤 없는 요청은 실패 콜백만 받고 각자 재전송·되돌림을 한다(5절).

### 거절
- `NetworkFailureHandler.OnRejected` 가 `NetworkMessages.ForRejected(error)` 문구를 경고 메시지로 띄운다. 서버 `error` 는 영문 개발자용이라 화면에 그대로 내지 않는다
- 호출부가 직접 안내하는 요청은 `Invoke(..., notifyRejected: false)` — 닉네임 변경이 팝업 안의 ErrorText 에 띄운다

### 통신 실패 — 자동 재전송
1. 게임을 멈추고(`Time.timeScale = 0`) 네트워크 딤(`UINetworkRespone`)에 "재연결 중입니다." 를 띄운다 — `NetworkFailureHandler.BeginRetry`
2. 2초 뒤 **같은 요청을 같은 요청 번호로** 다시 보낸다. 최대 3회. 시도마다 20초 시간 초과
3. 성공하거나 서버가 거절하면 문구를 끄고 속도를 원래 값으로 되돌린 뒤 호출부 콜백을 **한 번** 부른다 — 유저가 다시 누를 필요가 없다
4. 3회 모두 실패하면 콜백을 실패로 부르고 타이틀로 돌려보낸다 — `OnRetryExhausted`

- 네트워크 딤의 Text 는 `UIManager.ShowNetworkMessage` 로만 켠다. 평소 응답 대기에는 문구 없이 회전 아이콘만 뜬다
- 재연결 표시 직전의 `timeScale` 을 기억했다가 되돌린다 — 계속하기 팝업처럼 이미 멈춘 상태에서 불릴 수 있다

### 서버 중복 방지 — `Function_Request.cs` `RequestOps`
재전송한 요청이 두 번 반영되지 않게 한다.
- 클라는 딤 요청에 `rid`(GUID)를 붙이고, 재전송에는 같은 `rid` + `retry` 를 싣는다
- 진입점이 핸들러의 **성공** 응답을 `rid` 와 함께 `USER_REQUEST` 에 남긴다. 거절은 남기지 않는다(상태가 안 바뀌어 다시 돌려도 안전하다)
- `retry` 가 붙은 요청의 `rid` 가 남겨 둔 것과 같으면 핸들러를 돌리지 않고 남겨 둔 응답을 그대로 돌려준다
- 대상은 `RequestOps.IsGuarded` 의 action 뿐이다: ShopBuy · DungeonEnter · DungeonSweep · DungeonRevive · EquipmentPromote · EquipmentTransfer · PetPromote · DailyBonusClaim · HeroPassClaim · MailReceive · ChangeNickname. 조회는 다시 돌려도 안전해 뺐다
- 유저당 마지막 1건만 둔다. 딤이 입력을 막아 대상 요청이 하나씩만 나가기 때문이다
- **알고 둔 한계**: 핸들러가 저장을 끝낸 직후 `rid` 를 기록하기 전에 펑션이 죽으면 재전송이 한 번 더 반영된다. 막으려면 기록을 각 핸들러의 트랜잭션에 넣어야 한다

### 계정 데이터 로드 실패
로그인 직후의 GetUserData 는 `DataLoadState` 가 로딩 화면 아래에서 2초 간격으로 3회까지 다시 요청한다. 다 실패하면 타이틀로 보낸다. 미로그인(개발·오프라인)은 요청을 건너뛰고 빈 계정으로 통과한다.

### 타이틀 복귀 — `DataLoadState.GoToTitleAsync`
타이틀에 처음 들어온 것처럼 만든다.
1. 로딩 화면을 띄운다(이미 떠 있으면 그대로)
2. `UIManager.ResetForTitle()` — 창·팝업·MainHUD·던전 HUD·네비게이션 바·알림 메시지·월드 게이지를 전부 해제하고 네트워크 딤을 초기화한다. 다음 마을 진입의 `Ensure*` 가 다시 세운다
3. `NetworkManager.ResetLogin()` — 지우지 않으면 `TitleState` 가 이미 로그인된 것으로 보고 곧바로 넘어간다
4. `GameStateChangedEvent(TitleState)` 를 발행해 UI 밖의 정리(맵 해제 등)를 기존 처리에 맡긴다
5. **다음 프레임**에 `TitleState` 로 전이한다
6. 타이틀 씬이 뜨면 `TitleState` 가 로딩을 걷고 "서버와의 연결이 실패했습니다." 확인 팝업을 띄운다

> 5번을 같은 프레임에 하면 안 된다. `MapManager` 가 4번의 이벤트로 맵 인스턴스를 해제하는데, 비동기 씬 로드와 같은 프레임에 겹치면 메인 스레드가 영영 멈춘다(에디터 정지로 두 번 재현). 상태의 `EnterAsync` 안에서, 첫 대기가 씬 로드인 상태로 바로 전이할 때 생긴다.

### 게스트 로그인 실패
`GuestLoginHandler` 는 실패 사유가 `bad customId`(서버에서 계정이 지워진 경우)일 때만 기기의 게스트 정보를 지우고 새 계정으로 재시도한다. 통신 오류에서 지우면 기존 계정을 잃는다.

## 7. 영역별 처리 방법

### 로그인·계정 데이터 — `Function_Auth.cs` (GetUserData)
- 로그인 후 한 번 호출해 모든 `USER_*` 를 한 응답(`GetUserDataResponse`)으로 받는다. 도메인이 늘면 같은 응답에 필드만 더한다(테이블 분리 ≠ 패킷 분리)
- 신규 계정: 최초 지급(Reward 그룹 100)과 `USER_INFO` 생성을 한 트랜잭션에 묶는다. 실패하면 다음 로그인에 다시 시도되고, 성공하면 다시 지급되지 않는다
- 호출할 때마다 필드 정산 세션을 새로 발급한다(시드 교체, epoch 증가). **게임 도중에 재연결 확인용으로 부르면 진행 중인 처치 정산이 어긋난다**
- 신규 계정 첫 호출은 일이 많아 펑션 10초 제한에 걸릴 수 있다(`Sandbox.Timedout`). 클라의 자동 재시도가 넘긴다 — 두 번째 호출은 기존 계정 경로라 가볍다
- 클라는 `Account` 싱글톤이 도메인 객체를 소유하고, `Account.Set*(dto)` 가 DTO 를 도메인 객체로 **통째로 새로 만든다**. 게임 도중에 다시 부르면 스폰된 히어로와 열린 화면이 옛 객체를 붙든다 — 제자리 재동기화를 하지 않는 이유다

### 닉네임 — `Function_Nickname.cs`, 공유 `Shared/Nickname/NicknameRules`
- **자동 부여**: 닉네임이 없으면 GetUserData 에서 `Player` + 8자리 숫자를 뒤끝 계정 닉네임으로 등록한다. 값은 계정 gamerId(UUID)를 64비트로 접어 섞은 것이고, 중복(409)이면 시도 번호를 섞어 최대 10회 다시 만든다. 실패해도 로그인은 막지 않는다
- **변경**(ChangeNickname): 규칙 → 현재 닉네임과 같은지 → 비용 → `Backend.BMember.UpdateNickname` → 횟수·재화 저장
  - 규칙: 3~16byte(한글·일본어 2, 영숫자 1), 한글 완성형·영문·숫자·히라가나·가타카나·한자만, 첫 글자 숫자 불가, 금칙어·비속어 포함 불가
  - 비용: 첫 변경 무료, 그 뒤 다이아 5000 고정(테이블 없이 규칙 상수). 횟수는 `USER_INFO.NicknameChangeCount`. 닉네임변경권 아이템은 만들지 않는다
  - **닉네임을 먼저 바꾸고 차감을 나중에 저장한다.** 계정 API 와 게임 데이터는 한 트랜잭션으로 묶을 수 없다. 저장이 실패하면 무료로 바꾼 셈이 되지만 재화만 빠지는 것보다 낫다
- **단어 목록**: `BanWord.xlsx` 의 시트 — `BanWord`(금칙어, 프로젝트 기준으로 직접 정리) / `BadWord_KR` · `BadWord_US` · `BadWord_JP`(비속어, 외부 목록). 접속 언어와 무관하게 전부 본다. 포함 여부로 검사하므로 짧은 단어·일상어는 넣지 않는다(부록)
- 클라는 응답의 닉네임을 `MyPlayerProfile` 에 둔다. SDK 의 `UserNickName` 은 로그인 시점 캐시라 서버가 방금 만든 값을 모른다

### 필드 처치 정산 — `Function_Field.cs`, 공유 `Shared/Reward/`
- 잡몹 보상은 **시드로 재현**한다. 클라가 처치마다 `KillSeed.Derive(세션 시드, 처치 번호, 몬스터)` 로 굴려 바닥에 떨구고, 주운 것만 표시해 배치로 보낸다. 서버는 같은 시드로 다시 굴려 주운 것만 지급한다
- 재현이 깨지지 않게 난수는 정수만 쓴다(`DeterministicRandom`, 확률은 ppm 정수, 골드·경험치 보너스는 퍼밀 정수). 실수가 끼면 IL2CPP 와 .NET 결과가 달라진다
- 세션(`USER_FIELD`)은 로그인과 맵 이동(로딩)마다 교체한다 — `FieldSessionRotate`. 남은 처치 정산과 새 시드 발급을 한 번에 한다
- 필드 드랍 장비 UID 는 `(epoch<<32)|(처치 번호<<8)|보상 번호` 로 클라·서버가 각자 같은 값을 만든다
- 서버 검증: 세션 시드 일치, 처치 번호 연속, 시간당 처치 수 상한, 몬스터·지역·레벨·보너스 범위. 어긋나면 배치를 지급 없이 버리고 번호만 넘긴다
- 응답은 통신 실패(`data == null`)와 거절을 구분한다. 거절도 `nextKillIndex` 를 실어 와 그 기준으로 원장을 정리한다
- 필드보스는 이 경로가 아니라 `FieldBossKill`(`Function_FieldBoss.cs`)로 즉시 정산한다. 하루 1회 기록은 `USER_FIELD.bossKills`. 일반 몬스터 리젠은 서버에 저장하지 않는다(재접속 시 부활 — 의도)
- 알고 둔 한계: 레벨은 몬스터별이 아니라 전체 최대치로 검증, 보너스 상한은 상수, 처치가 진짜인지는 수 상한으로만 막는다. 필드보스가 어느 필드에 배치됐는지는 검증하지 않는다

### 던전 — `Function_DungeonRun.cs`, `Function_Dungeon.cs`, 공유 `Shared/Dungeon/DungeonRules`
- **입장**(DungeonEnter): 해금·일일 횟수를 확인해 차감하고 런(runId·시드)을 발급한다. 일일 리셋은 서버 시간 KST 06시(`ResetDay`)
- **종료**(DungeonClear): 런이 끝나면(클리어·실패·강제 귀환) 한 번 보낸다. 서버가 클리어 보상과 최고 단계를 저장하고 런을 정산 완료로 바꾼다 — 같은 런은 한 번만 정산된다
- **부활**(DungeonRevive): 런 단위 상한과 회차별 비용을 서버가 판정해 즉시 차감한다. **소탕**(DungeonSweep): 균열 입장 1회 + 보상
- 미궁 상자는 런 시드로 굴려 바닥에 떨구고, 주운 것만 서버가 지급한다. 균열은 웨이브 최소 시간으로 속도 조작을 막는다
- 알고 둔 한계: 미궁 상자 등급은 클라 값을 믿는다(맵 프리팹이라 서버가 모른다)
- 미로그인·개발용 이동은 로컬 런이다(정산 요청 없음)

### 상점 — `Function_Shop.cs`, 공유 `Shared/Shop/ShopRules`
- ShopBuy 하나가 전 상품을 처리한다: 가격 차감 → 보상 추첨 → 지급, 구매 횟수는 `USER_SHOP`(일일 리셋은 서버 시간)
- 가격 종류는 재화·아이템(열쇠)·무료·광고·현금. **광고와 현금은 지금 검증 없이 통과한다(임시)** — `trySpendPrice`. 히어로패스 구매(`buyHeroPass`)도 결제 없이 처리한다. 교체는 `출시후 작업.md`
- 뒤끝 확률표는 쓰지 않는다. 보물상자도 다른 보상과 같은 공유 코어로 굴린다

### 장비·펫 성장, 외형 — `Function_Equipment.cs`, `Function_Pet.cs`, `Function_Loadout.cs`
- 강화는 묶음(EquipmentEnhance / PetEnhance), 승급·전이는 한 번씩(EquipmentPromote / EquipmentTransfer / PetPromote). 판정은 공유 `EquipmentGrowthRules` / `PetRules`
- 장착(SaveLoadout)과 외형(SaveAppearance — 펫 장착 + 코스튬 착용)은 dirty flush 로 최종 상태를 보낸다. 서버는 보유 여부를 확인한다

### 마스터리·소모품 — `Function_Mastery.cs`, `Function_Item.cs`, 공유 `Shared/Reward/MasteryRules`
- 마스터리 경험치는 처치·던전 정산이 싣고 온 `masteryId` 로 서버가 적립한다. 그 무기 종류의 장비를 보유하지 않았으면 적립만 건너뛴다
- 스킬트리(SaveMasteryTree)는 **최종 상태**를 보내고 서버가 통째로 검증한다(`MasteryRules.ValidateTree`). 하나라도 어긋나면 전부 거절하고 클라가 dirty 를 되살린다. 클라의 한 번 조작 규칙(`MasteryProgress`)과 불변식이 같아야 하므로 규칙을 바꾸면 둘 다 고친다
- 소모품은 단발성만 있다(지금은 지식의 서 — UseSkillPointItem). 인벤토리 파괴는 ItemSpend 로 묶어 보낸다
- 레벨은 경험치에서 계산한다(`MasteryRules.CharacterLevelFromExp`). 서버가 저장하는 `level` 은 콘솔 표시용이다

### 퀘스트·출석·히어로패스 — `Function_Quest.cs`, `Function_DailyBonus.cs`, `Function_HeroPass.cs`
- 퀘스트 완료(QuestComplete)는 서버가 목표를 판정하고 보상을 굴린다. 알고 둔 한계: 처치 카운터는 클라 값을 믿는다(SaveQuestProgress 로 저장)
- 출석(DailyBonusClaim)은 서버 시간(KST 06시) 기준으로 오늘 수령 여부와 일차를 판정한다
- 히어로패스(HeroPassClaim)는 서버가 센 경험치로 레벨을 판정한다. 시즌은 35일, 시즌당 구매 1회. 알고 둔 한계: 드랍이 바닥에 남은 처치는 최대 60초까지 서버 경험치에 반영되지 않아, 막 오른 레벨을 수령하면 거절될 수 있다

### 랭킹 — `Function_Ranking.cs`, 공유 `Shared/Ranking/BattlePowerRules`
- 뒤끝 유저 리더보드를 쓴다. 점수는 **최고 전투력**이고, **전투력은 서버가 계산한다**(저장 데이터와 테이블만 사용). 클라가 보내는 값은 없다
- 테이블이 둘이다: `USER_RANKDATA`(비공개, 점수 컬럼 — 리더보드 대상은 비공개여야 한다) / `USER_PROFILE`(공개, 정보 스냅샷)
- 갱신(`RankOps.Refresh`)은 전투력이 바뀌는 펑션이 저장을 끝낸 뒤 스스로 부른다. 점수는 최고 기록일 때만 오르고, 스냅샷은 달라졌을 때만 쓴다. 갱신 실패는 본래 행동을 실패시키지 않는다
- 화면의 전투력(`BattlePowerCalculator`)과 서버 계산은 **구현이 따로**다. 영구 스탯 출처를 새로 추가하면 `BattlePowerRules` 에도 넣어야 두 값이 같게 유지된다
- 전 유저가 등록된다. 항목 삭제는 콘솔에서만 되므로 순위권 밖 정리는 만들지 않았다
- 클라(`BackndRankingProvider`)는 100위까지, 50명씩 받는다(RankList offset 0/50). 목록 5분 캐시, 유저 정보(RankProfile)는 누를 때마다 조회
- **랭킹을 하나 더 만들 때**: `USER_RANKDATA` 에 숫자 컬럼 추가 → 콘솔에 그 컬럼을 보는 리더보드 생성 → 점수가 바뀌는 펑션에서 `submitScore(리더보드 제목, 컬럼, 점수)` → 조회 펑션과 클라 Provider 를 보드별로 확장

### 우편 — `Function_Mail.cs`
- 뒤끝 관리자·랭킹 우편을 MailList / MailReceive 가 읽고 수령한다. 첨부는 콘솔 차트 `MailItem` 의 행 + 발송 수량이고, 서버가 수령하면서 지급한다
- 순서: 데이터 Load → 뒤끝 수령(되돌릴 수 없음) → `RewardApplier` → 저장. 저장이 실패하면 보상이 유실될 수 있지만 중복 지급은 없다. 에러에 우편과 첨부를 남긴다
- 뒤끝은 받은 우편을 목록에서 지우고 "읽음" 상태가 없다. 그래서 받은 우편은 기기 보관함(`MailArchive`, 계정별 최대 50통)에 두고, 삭제는 보관함에서만 한다. 재설치하면 보관함은 빈다
- 새 우편은 실시간 알림(`MailNotifier`, `Backend.Notification.OnNewPostCreated`)으로 감지해 메뉴 배지를 갱신한다
- 장비는 등급·품질이 고정되지 않아 우편 첨부에서 뺐다

## 8. 뒤끝 제약과 함정

**펑션 컨텍스트**
- `Backend.UID` 와 `Backend.UserInDate` 가 비어 있다. 내 행은 `new Where()` 로 다루고, 계정 식별이 필요하면 `GetUserInfoV2` 의 `gamerId` 를 쓴다
- 응답은 `Backend.StringToStream` 으로 만든다(`JsonToStream` 은 이중 인코딩)
- 펑션 한 번의 실행은 10초로 제한된다. 넘으면 `{"errorType":"Sandbox.Timedout",…}` 봉투가 오고, 클라는 이를 통신 실패로 다룬다. 한 펑션에서 DB 호출이 많아지면 트랜잭션으로 묶어 줄인다
- 워밍 컨테이너는 정적 상태를 재사용한다. 테이블은 한 번만 로드하고(`GameData`), 난수는 호출마다 새로 만든다(`ServerRandomSource`)
- 계정 API(닉네임 등)와 게임 데이터 저장은 한 트랜잭션으로 묶을 수 없다 — 순서를 정해 둔다(닉네임 절 참고)

**클라 SDK**
- 동기 `InvokeFunction` 을 스레드풀에서 부르면 `Create can only be called from the main thread` 가 난다 → `SendQueue`
- SDK 의 `UserNickName` 은 로그인 시점 캐시다

**리더보드**
- 대상 테이블이 공개면 갱신이 `400 bad public Table` 로 실패한다
- `UpdateMyDataAndRefreshLeaderboard` 로 갱신해야 반영된다(일반 Update 는 반영 안 됨). 행은 먼저 Insert 돼 있어야 한다
- `GetLeaderboard` 의 limit 은 1~50
- 항목 삭제는 콘솔에서만 된다. 테이블 행을 지워도 순위 정보는 남는다
- 초기화가 설정된 리더보드는 초기화 1시간 전부터 갱신이 실패한다

**차트**
- 컬럼명 `ID` 는 예약어라 쓸 수 없다. `테이블명+ID`(예: `MailItemID`)로 짓는다
- 차트 파일 ID 는 올릴 때마다 바뀐다. 이름으로 찾는다(`ChartUtil.ResolveChartFileId`)
- 게임 테이블은 서버에 bytes 로 동봉하므로, 차트는 우편 첨부처럼 **콘솔이 아이템을 골라야 하는 곳**에만 쓴다

**배포**
- 뒤끝 CLI 는 저장소가 아니라 전역 `%AppData%\AFI\BFunc\config.json` 하나만 읽는다. 다른 프로젝트에서 `backend config` 를 한 뒤라면 **다른 프로젝트 소스를 빌드해 다른 펑션에 배포한다.** 에러가 나지 않아 성공한 것처럼 보인다
  - 증상: 고쳐 배포했는데 옛 동작 그대로. `publish.zip` 수정 시각과 config 의 projectPath·functionName 을 확인한다
  - 해결: `Server/Functions/Setup.bat` 로 ProjectOne 값을 다시 넣고 `Build.bat`

**요금**
- 펑션 요금은 호출 수 기준이다(월 50,000회 무료, 이후 1회당 $0.0000333). 등록 인원은 무관
- 호출의 대부분은 `FieldSettle` 20초 주기다(유저 1명 1시간 사냥 = 180회)

## 9. 운영 절차

### 서버 배포
1. `Server/Functions/Setup.bat` — CLI 설정(최초 1회, 또는 다른 프로젝트를 배포한 뒤)
2. `Server/Functions/Build.bat` — `backend build` + `backend deploy`

배포가 필요한 경우: 서버 코드, 공유 코드(`Shared/**`), 테이블(`.bytes`) 중 하나라도 바뀌었을 때.

### 테이블 변경
`Shared/XLS/*.xlsx` 수정 → Excel 을 닫고 `Shared/Tools/ExcelDataTable/ExcelDataTable.exe --build`(전체 테이블의 `.bytes` 와 `Table_*.cs` 재생성) → Unity 리임포트 → 서버 재배포.
변환을 빼먹으면 로더는 조용히 옛 값을 읽는다.

### 우편 첨부 차트(MailItem) 갱신
1. `Shared/Backnd/MailItem.bat` 실행 → 같은 폴더에 `MailItem.csv`(테이블 `.bytes` 기준이라 엑셀을 고쳤으면 변환을 먼저)
   - 행: 재화 전부 + 장비를 뺀 아이템 전부. 컬럼 `MailItemID, RewardType, TargetID, Name`
2. 뒤끝 콘솔 차트 관리에 `MailItem` 이름으로 올리고 '우편 사용'을 켠다
3. 우편을 보낼 때 차트에서 행을 고르고 수량을 넣는다. 서버는 RewardType·TargetID·수량만 본다

아이템·재화를 추가·삭제하면 다시 내보내서 올린다. 테이블에 없는 첨부는 서버가 지급하지 않고 건너뛴다.

### 콘솔에 있어야 하는 것
- 3절의 `USER_*` 테이블 전부(`USER_PROFILE` 만 공개, 나머지 비공개)
- 유저 리더보드: 제목 `BattlePower`, 테이블 `USER_RANKDATA`, 컬럼 `BattlePower`, 내림차순. 서버는 제목으로 찾는다
- 차트 `MailItem`('우편 사용' 켬)
- 실시간 알림 활성화(새 우편 배지)
