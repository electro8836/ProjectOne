# 테이블 규약 설계

> 2D 탑다운 방치형 핵앤슬래시 (Unity, 싱글플레이) — 엑셀 테이블 작성 규약 및 변환 사양
> 관련 문서: 전체 시스템 설계 문서
> **이 문서는 현재 구현 상태를 기술한다.** 예시는 실제 테이블·생성 코드 기준이다.

---

## 1. 개요

### 1.1 이 문서의 범위

엑셀 → C# 코드/데이터 변환의 **공통 규약**을 소유한다.

| 다루는 것 | 다루지 않는 것 |
|---|---|
| 시트 구조, 마커, 타입 표기 | 각 테이블의 컬럼 의미 |
| 빈 칸·다형 컬럼·배열 규약 | 시스템별 검증 규칙 |
| ID 체계와 대역 | 게임 로직 |
| 생성 결과물의 형태와 로딩 | 런타임 캐시 정책 |

### 1.2 전제

- 모든 정적 데이터는 엑셀에 명시한다. 코드에 데이터를 하드코딩하지 않는다.
- 데이터를 넣는 사람과 코드를 짜는 사람이 같으므로, **규약은 최소로 두되 예외를 만들지 않는다.**

### 1.3 변환 파이프라인

```
Shared/XLS/*.xlsx
   │  Shared/Tools/ExcelDataTable/ExcelDataTable.exe   (AutoBuild.bat)
   ├─→ ProjectOne/Assets/Project/Scripts/Core/ExcelData/*.cs    코드
   └─→ ProjectOne/Assets/Project/Data/Tables/edt_*.bytes        데이터
```

- **생성물은 전부 자동 생성이며 손으로 고치지 않는다.** `Core/ExcelData/` 폴더 전체가 대상이다.
- **xlsx 를 고쳤으면 변환을 돌려야 한다.** 돌리지 않으면 테이블 값이 조용히 옛 값으로 남는다.
- `.bytes` 는 `AddressableAutoMarker` 가 `Data_Tables` 그룹 / `Tables` 라벨로 자동 등록한다. 테이블을 새로 추가했으면 리임포트만 하면 된다.

## 2. 시트 구조

### 2.1 레이아웃

**A열은 마커 전용, B열부터 데이터**다.

```
      A열            B열        C열                  D열
────────────────────────────────────────────────────────────────
1   !EnumTable   |  Skill
2                |  !ID      |  CastingType        |  ScanRange      ← 필드명
3                |  !Skill   |  !SkillCastingTypes |  !float         ← 타입
4                |  Skill_…  |  Instant            |  2.5            ← 데이터
5                |  Skill_…  |  Casting            |  0
```

| 행 | 역할 |
|---|---|
| 1 | 시트 마커 + 테이블명 |
| 2 | 필드명 |
| 3 | 타입 |
| 4 이후 | 데이터 |

A열을 비워두는 이유는 **마커와 데이터를 시각적으로 분리**하고, 엑셀에서 행 전체를 복사할 때 마커가 섞이지 않게 하기 위함이다.

### 2.2 시트 마커

| 마커 | 의미 | ID 타입 |
|---|---|---|
| `!Table` | 일반 테이블 | `int` |
| `!EnumTable` | 데이터 + C# enum을 동시에 생성 | `string` |
| `!Enum` | enum 정의 블록 (한 시트에 여러 블록 가능) | — |

**`#시트명`** 으로 시작하는 시트만 변환 대상이다. `#` 없는 시트는 작업용 메모·계산표로 자유롭게 쓴다.

> **`!EnumTable` 을 언제 쓰는가**
>
> 코드가 특정 값을 이름으로 지목해야 할 때다. `Dungeon` 은 `DungeonType` 으로 코드 분기하므로 EnumTable이고, `Map` 은 코드가 특정 맵을 이름으로 알 필요가 없으므로 `!Table` 이다.
>
> 판단 기준: **`if (x == Something)` 을 코드에 쓸 일이 있는가.**

### 2.3 컬럼 순서

변환기는 **컬럼 이름으로 매핑**한다. 순서를 바꾸거나 중간에 삽입해도 안전하다.

따라서 **지금 쓰지 않는 컬럼을 자리만 잡아 둘 필요가 없다.** 필요해질 때 추가한다.

## 3. 타입 표기

### 3.1 원시 타입

| 표기 | C# |
|---|---|
| `!int` | int |
| `!float` | float |
| `!bool` | bool (TRUE / FALSE) |
| `!string` | string |

### 3.2 참조 타입

| 표기 | 의미 |
|---|---|
| `!ID` | 이 테이블의 기본 키 |
| `!Xxx` | `Xxx` 테이블 또는 enum 참조. **변환기가 실존 여부를 검증한다** |

`!Xxx` 는 타입 안전성을 얻는 대신 **하나의 대상만 가리킬 수 있다.** 여러 타입을 담아야 하는 컬럼은 5장을 따른다.

### 3.3 배열

배열 여부는 **변환 툴에서 컬럼별로 설정**한다. 생성 코드는 `T[]` 필드가 되고, 바이너리는 `길이(int) + 원소` 순으로 직렬화된다.

문서에서는 `!int[]` / `!Skill[]` 처럼 `[]` 를 붙여 표기한다.

**현재 배열 컬럼은 4개뿐이다**

| 테이블 | 컬럼 | 타입 |
|---|---|---|
| `DungeonStage` | `MonsterSpawnGroupIDs` | `!int[]` |
| `SkillEffect` | `ChainEffectIDs` | `!SkillEffect[]` |
| `Buff` | `BlockFlags` | `!ActionBlockType[]` |
| `WeaponMastery` | `Dev_SkillIDs` | `!Skill[]` (개발용) |

> 배열은 **길이가 의미를 갖는 곳에만** 쓴다. `DungeonStage.MonsterSpawnGroupIDs` 는 길이가 곧 웨이브/페이즈 수다.
>
> 반대로 고정 개수의 슬롯은 배열이 아니라 번호 컬럼으로 둔다 (`EffectID_01` / `_02`, `Opt1~4_ID`). 슬롯마다 다른 컬럼(값·스텝)이 따라붙기 때문이다.

## 4. 빈 칸 규칙

### 4.1 전역 규칙

> **빈 칸은 언제나 `None` 이다. 이 규칙은 바뀌지 않는다.**

| 슬롯 종류 | 빈 칸일 때 |
|---|---|
| 참조 / enum | `None` (0) |
| `!int` `!float` | 0 |
| `!bool` | FALSE |
| `!string` | 빈 문자열 |

변환기가 코드 생성 시 모든 enum에 `None = 0` 을 자동으로 붙인다. 실제 값은 **1부터** 시작한다.

### 4.2 "비면 에러"는 전역 규칙이 아니다

**필수 여부는 컬럼별 검증 규칙으로 내린다.**

전역 에러로 두면 빈 칸이 정상인 컬럼이 통째로 에러가 난다. 실제로 그런 컬럼이 여럿 있다.

| 컬럼 | `None` 의 의미 |
|---|---|
| `Equipment.WeaponType` | 무기가 아니다 (방어구·장신구·유물) |
| `Npc.NpcType` | 기능이 없는 퀘스트·대화 전용 NPC |
| `EquipPromotion.ToGrade` | 승급 불가 — 이 등급이 한계다 |
| `RewardItemPool.SubCategory` | 전체 |
| `Quest.QuestParam_3` (KillMonster) | 지역 무관 |
| `Quest.QuestParam_2` (EquipItem*) | 슬롯 무관 |
| `DungeonStage.MonsterLevel` | 오버라이드하지 않음 |
| `Consumable.CooldownGroup` | 이 아이템만 독립 쿨다운 |
| `Stat.MinValue` / `MaxValue` | 제한 없음 |
| `SkillTreeNode.PrevNodeID` | 선행 노드 조건 없음 |
| `SkillTreeNode.Option_02` | 두 번째 옵션 슬롯 미사용 |
| `Monster.RewardGroupID` | 고유 드랍 없음 |
| `Skill.EffectID_02` | 두 번째 효과 슬롯 미사용 |

**`None` 의 의미가 컬럼마다 다르므로, 각 시스템 문서의 컬럼 정의에 한 줄씩 명시한다.**

### 4.3 `None` 이 두 뜻을 가지면 컬럼을 나눈다

빈 칸이 **"설정 안 함"과 "0이라는 값"** 두 가지로 읽히는 컬럼은 판정이 불가능하다. 이런 경우 자동 폴백을 만들지 않고 **명시적 컬럼이나 필수 규칙으로 분리**한다.

| 사례 | 문제 | 해결 |
|---|---|---|
| `NpcSpawn.SpawnEndQuestID` | 판정식이 `Cleared >= End` 인데 0이면 항상 참 → 모든 NPC가 즉시 소멸 | **`UseSpawnEnd`** 플래그 신설 |
| `Reward.Chance` | 0을 확정 지급으로 읽으면 "확률 0 봉인"을 표현 불가 | **필수 컬럼**으로 승격. 0=봉인 / 1=확정 |
| `Reward.EquipGradeWeightID` | 자동 폴백을 두면 의도와 실수가 구분 안 됨 | **필수(오류)** 로 승격 |
| `Reward.MaxCount` | 0과 "미지정"이 같음 | 0 = `MinCount` 고정으로 **의미를 확정** |
| `Stat.MinValue` | 0을 하한으로 쓰면 "제한 없음"과 구분 불가 | 0 = 제한 없음으로 **의미를 확정**. 음수 방지는 계산부가 처리 |

> **자동 폴백을 만들지 않는다는 것이 이 프로젝트의 원칙이다**
>
> 값이 자동으로 메워지면 **데이터 누락을 아무도 눈치채지 못한다.** 안 나오면 바로 보이는 쪽이 낫다. `Stat.DefaultValue` 컬럼을 두지 않은 것도 같은 판단이다 (`기반테이블_설계.md` 4.3).

## 5. 다형 컬럼 규약

### 5.1 규약

**하나의 컬럼이 여러 타입을 담아야 하면 `!string` 으로 두고, 판별 컬럼에 따라 파싱·검증한다.**

```
판별 컬럼  +  !string 파라미터 슬롯  →  타입별 파싱 + 실존 검증
```

`!Xxx` 참조 타입은 하나의 대상만 가리킬 수 있으므로 쓸 수 없고, `!int` 로 두면 문자열 EnumTable을 순번으로 적는 매직넘버가 된다.

### 5.2 적용 사례

| 테이블 | 판별 컬럼 | 파라미터 | 해석 시점 |
|---|---|---|---|
| `SkillEffect` | `EffectType` | `EffectParam_1~5` | 부팅 시 `SkillParamCatalog` + 런타임 `SkillEffectParams` |
| `Quest` | `QuestTargetType` | `QuestParam_1~3` | 부팅 시 `QuestCatalog.BakedQuest` |
| `Consumable` | `ConsumeEffect` | `EffectParam_1~2` | 런타임 `ConsumableUser` |
| `Reward` | `RewardType` | `TargetID` | 부팅 시 `RewardCatalog` |
| `Option` | `OptionType` | `OptionTarget` | 부팅 시 `OptionCatalog` |
| `SkillModifier` | `Scope` + `ParamKey` | `RefValue` | 부팅 시 `SkillModifierCatalog` |

> **문자열은 부팅 때 한 번만 해석한다.** 전 사례가 `Build()` 시점에 강타입으로 굽고, 이후 런타임은 문자열을 만지지 않는다. 오타는 부팅 로그에서 드러난다.

### 5.3 파라미터 순서 — 필수는 앞, 선택은 뒤

**중간에 빈 칸이 생기지 않게 배치한다.**

선택 항목을 앞에 두면 가장 흔한 타입에서 첫 칸이 자주 비고, 시트에서 한 칸씩 밀려 적는 사고가 난다.

### 5.4 타입 간 공통 의미를 부여하지 않는다

`SkillParamDef` 에서 `Damage` 의 1번 슬롯은 `Ratio` 이고 `Buff` 의 1번 슬롯은 `RefID` 다. 슬롯 번호에 "항상 대상", "항상 수치" 같은 의미를 억지로 맞추면 표현할 수 없는 조합이 생긴다.

**슬롯의 뜻은 각 문서의 매핑표가 전부다.**

### 5.5 정의 시트를 만드는 기준

`SkillEffect` 만 `SkillParamDef` 시트를 갖고, 나머지는 문서의 표로만 정의한다.

| | SkillEffect | 그 외 |
|---|---|---|
| 타입 수 | 9종 × 5슬롯 | 3~6종 × 1~3슬롯 |
| 런타임 지목 | `SkillModifier.ParamKey` 가 슬롯을 **문자열로 지목해 값을 바꾼다** | 없음 |
| 정의 위치 | 시트 필요 | 문서 + 파싱 코드 |

**런타임에 슬롯을 이름으로 찾아야 하는가**가 기준이다. 그렇지 않으면 시트를 늘리지 않는다.

### 5.6 오타 탐지

자유 형식 컬럼은 타입 검증이 약하므로, **정의되지 않은 슬롯에 값이 있으면 경고**를 낸다. 한 칸 밀려 적은 데이터를 잡는 유일한 장치다.

## 6. ID 체계

### 6.1 `!Table` — 정수 ID는 대역으로 의미를 표현한다

| 테이블 | 형식 | 예 |
|---|---|---|
| `Item` (장비) | `1` + MM(2) + SS(2) + TT(2) + NNN(3) | `1010306001` |
| `Item` (그 외) | `1` + MM(2) + SS(2) + NNNNN(5) | `1030100001` |
| `Map` (마을) | `1` | `1` |
| `Map` (필드) | `2` + 액트(2) + 순번(2) | `20101` |
| `Map` (던전) | 던전종류(1) + `001` | `2001` (골드) / `3001` (균열) |
| `Act` | 연속 | `1` ~ `5` |
| `Field` | **`Map.ID` 와 동일** | `20101` |
| `Quest` (메인) | **10 단위 증가** | `1000010` |
| `Quest` (서브) | 연속 부여 | `2000010` |
| `Reward.GroupID` | `1xxx` | |
| `RewardItemPool.PoolID` | `2xxx` | |
| `EquipGradeWeight` | `1xxxx` / `2xxxx` / `3xxxx` | |

### 6.2 대역 번호는 enum 순서와 분리한다

> **ID에 인코딩하는 번호는 enum 선언 순서가 아니라 문서에 고정된 대역표다.**

한 번 부여한 번호는 재사용하지 않고, enum은 읽기 좋은 순서로 자유롭게 정렬한다.

이 규칙은 실제 사고에서 나왔다. `ItemSubCategory` 재정렬 한 번에 **모든 소모품 ID가 한 칸씩 어긋났다.** 발급된 아이템 ID는 세이브 데이터에 박히므로 사후 수정이 불가능하다.

대역표는 ID 생성 규칙이자 **유효 조합 검증표**로 함께 쓴다 (`아이템시스템_설계.md` 2.2).

### 6.3 참조 대상이 ID 대소 비교에 쓰이는 경우

`Quest` 메인 체인은 `ClearedMainQuestID >= ReqQuestID` 로 진행을 판정하므로 **ID 자체가 순서 데이터**다. 10 단위로 부여해 중간 삽입 여유를 남긴다.

> **한계** — 이미 `1000020` 을 클리어한 세이브에 `1000015` 를 삽입하면 영영 스킵된다. 출시 후 메인 퀘스트 중간 삽입은 불가능하다고 보아야 한다.

### 6.4 `!EnumTable` — 문자열 ID는 접두로 소속을 드러낸다

| 테이블 | 접두 | 실제 예 |
|---|---|---|
| `Stat` | `Stat_` | `Stat_Atk` |
| `StatDetail` | `StatDetail_` | `StatDetail_Atk_Add` |
| `Option` | `OPT_` | `OPT_ATK_ADD` |
| `Skill` | `Skill_` | `Skill_DualBlades_Active_01` |
| `SkillEffect` | `SE_` | `SE_DualBlades_Attack_Damage` |
| `SkillModifier` | `SKM_` | `SKM_DualBlades_Active_01_Ratio` |
| `Projectile` | `PJT_` | `PJT_CrossBow_Bolt` |
| `Summon` | `Summon_` | `Summon_Spark` |
| `Buff` | `BUFF_` | `BUFF_Stun` |
| `WeaponMastery` | `Mastery_` | `Mastery_DualBlades` |
| `SkillPoint` | `SkillPoint_` | `SkillPoint_Item` |
| `Dungeon` | 없음 | `Gold` / `Rift` |
| `Currency` | 없음 | `Gold` / `Dia` / `Ruby` |
| `EquipPurity` | `Purity_` | `Purity_1` |
| `EquipEnhanceTier` | `Tier_` | `Tier_1` |
| `DropTier` | `Tier_` | `Tier_1` |

**접두 이후의 형식은 관례이며 변환기가 강제하지 않는다.** 변환기는 참조 실존만 검증한다. **ID 문자열을 파싱해 의미를 추출하는 로직은 만들지 않는다.**

`Skill` 은 소유자에 따라 접두 뒤를 구분한다.

| 소유자 | 형식 | 실제 예 |
|---|---|---|
| 무기 마스터리 | `Skill_{WeaponType}_{Attack\|Active_NN\|Passive_NN}` | `Skill_RuneSword_Passive_01` |
| 몬스터 | `Skill_Monster_{종류}_{NN}` | `Skill_Monster_RangeAttack_01` |
| 보스 | `Skill_Monster_Boss_{이름}_{NN}` | `Skill_Monster_Boss_Doom_01` |
| 소환물 | `Skill_{소환물}_{동작}` | `Skill_SummonSpark_Attack` |

## 7. 참조 방향

### 7.1 정방향 원칙

> **"쓰는 쪽"이 "쓰이는 쪽"을 가리킨다.**

역참조(쓰이는 쪽이 자신을 쓰는 것들의 목록을 보유)는 두 가지 문제를 낳는다.

- 대상을 추가할 때 **두 곳을 고쳐야** 하고, 한쪽만 고치면 조용히 깨진다
- 목록 안의 원소마다 다른 값을 줄 수 없다

**"나를 쓰는 것들의 목록"을 갖는 컬럼은 만들지 않는다.**

### 7.2 예외 — 배치 데이터

배치는 씬과 테이블 중 **조건을 가진 쪽이 주도**한다. 그래서 방향이 셋으로 갈린다.

| 대상 | 방향 | 이유 |
|---|---|---|
| 필드 몬스터 (`MonsterSpawnPoint`) | **씬 → 테이블** — 마커가 `SpawnGroupId` 를 지정 | 좌표는 씬이, 조합은 테이블이 관리 |
| 던전 몬스터 (`DungeonSpawnSlot`) | **익명 슬롯** — 마커는 `SlotIndex` 만, 구성은 `DungeonStage` 가 결정 | 단계마다 같은 자리에 다른 몬스터가 나와야 한다 |
| NPC (`NpcSpawnPoint`) | **테이블 → 씬** — `NpcSpawn(MapID, SpawnPointID)` 가 마커를 지목 | 등장 조건(퀘스트 진행도)이 테이블에 있다 |

**세 방향이 다른 것은 의도적이다.**

> **스폰 포인트에 고유 ID를 두지 않는 이유** — 필드 스폰은 재배치·복제가 잦다. 씬 오브젝트가 ID를 들고 있으면 유니티가 복제 시 이름을 자동 변경(`(1)` 접미)해도 에러 없이 몬스터만 안 나온다. NPC는 배치가 고정이라 ID를 둔다.

### 7.3 ID 공유 패턴

통합 테이블 + 상세 테이블이 **같은 ID를 쓴다.**

```
Item ──(동일 ID)── Equipment
     ──(동일 ID)── Consumable

Map  ──(동일 ID)── Field
```

참조하는 쪽이 `타입 + ID` 두 컬럼을 들고 분기할 필요가 없어진다. `Field` 는 `MapID` 컬럼을 갖지 않고 자기 `ID` 가 곧 `Map.ID` 다.

**단, 상세가 "진행 단위"이고 씬을 공유하면 ID를 나눈다.** `DungeonStage` 는 `Map` 과 ID를 공유하지 않고 `MapID` 로 참조한다 — 공유하면 단계 하나당 맵 하나가 강제된다.

> **ID 공유 테이블은 세트로 만든다.** `Item` 행만 만들고 `Equipment` / `Consumable` 행을 빠뜨리면 드랍·사용 시 실패한다.

## 8. 검증

### 8.1 검증은 두 단계에 걸쳐 있다

| 단계 | 담당 | 실패 시 |
|---|---|---|
| 변환 시 | `ExcelDataTable.exe` — 타입·참조 실존 | 변환 실패 |
| 부팅 시 | 각 `Catalog.Build()` — 조합·정합성 | 로그 (에러/경고) |

**부팅 시 검증이 실질적인 안전망이다.** `StatCatalog` / `OptionCatalog` / `SkillParamCatalog` / `SkillModifierCatalog` / `MonsterCatalog` / `RewardCatalog` / `EquipmentCatalog` / `QuestCatalog` 가 각각 자기 테이블을 훑으며 정합성을 확인하고 콘솔에 남긴다.

따라서 **데이터를 넣은 뒤에는 한 번 실행해 부팅 로그를 확인한다.** 빌드가 통과했다고 데이터가 맞는 것이 아니다.

### 8.2 오류 / 경고 분류

| 분류 | 기준 |
|---|---|
| **오류** | 참조가 깨졌거나, 런타임에 예외·붕괴가 발생한다 |
| **경고** | 동작은 하지만 의도와 다를 가능성이 높다 |

**"조용히 아무 일도 안 일어남"은 오류로 분류한다.** 예외가 나면 즉시 발견되지만, 아무 일도 안 일어나면 몇 주 뒤에 발견된다.

| 사례 | 분류 |
|---|---|
| 존재하지 않는 `Skill` 참조 | 오류 |
| `Reward.Chance` 빈 칸 | 오류 (전부 봉인됨) |
| `MonsterStat` 에 `AtkSpeed_Base` 없음 | 오류 (0 나눗셈) |
| `Option.OptionTarget` 을 해석하지 못함 | 오류 (옵션이 조용히 안 먹힌다) |
| `SkillModifier.ParamKey` 가 정의되지 않은 슬롯 | 오류 (모디파이어가 조용히 안 먹힌다) |
| 어느 스폰에도 없는 몬스터를 목표로 하는 퀘스트 | 경고 (완료 불가지만 데이터는 정합) |
| 조건에 매칭되는 아이템이 0개인 드랍 풀 | 경고 |
| 어디서도 참조되지 않는 데이터 | 경고 (죽은 데이터) |

### 8.3 실행 순서

```
[1] 시트 파싱          마커·타입행 형식, 필드명 중복
[2] 테이블 내 검증      ID 중복, 값 범위, 필수 컬럼
[3] 파일 내 참조        같은 xlsx 안의 !Xxx 참조
[4] 파일 간 참조        Reward → Item / Equipment 등
[5] 다형 컬럼 파싱      판별 컬럼별 타입 검증
[6] 조합·의미 검증      (MainCategory, SubCategory) 조합, 대역표 일치
[7] 도달 가능성 검증     죽은 데이터, 완료 불가 퀘스트 (경고)
```

**[1]~[2]에서 실패하면 이후 단계를 돌리지 않는다.** 파싱이 깨진 상태의 참조 에러는 노이즈다.

### 8.4 파일 간 참조

한 xlsx 안에서 닫히지 않는 참조가 다수 존재한다.

```
Reward.xlsx      → Item.xlsx (조건 매칭) / Equipment.xlsx (EquipGradeWeight)
Consumable.xlsx  → Item.xlsx / Skill.xlsx / Reward.xlsx / Mastery.xlsx
Mastery.xlsx     → Skill.xlsx / Option.xlsx / Stat.xlsx
Quest.xlsx       → Monster.xlsx / Map.xlsx / Npc.xlsx / Reward.xlsx
Monster.xlsx     → Skill.xlsx / Stat.xlsx / Reward.xlsx
Skill.xlsx       → Stat.xlsx / Option.xlsx
```

**변환기는 전체 xlsx를 한 번에 로드한 뒤 검증한다.** 파일 단위로 개별 변환하면 파일 간 참조를 검증할 수 없다.

### 8.5 변환기의 책임 범위

> **엑셀 변환기는 씬을 읽지 않는다.**

| 검증 | 담당 |
|---|---|
| `MonsterSpawn.GroupID` 실존 | 엑셀 변환기 |
| 씬의 스폰 포인트가 참조하는 `GroupID` 실존 | 씬 순회 (미구현) |
| `NpcSpawn` 행의 참조 정합성 | 엑셀 변환기 |
| `(MapID, SpawnPointID)` 마커가 씬에 존재 | 런타임 경고 (`NpcSpawner`) |
| `Map.MapPrefab` 주소가 실존 | 런타임 로드 실패로 드러남 |

씬 쪽 검증은 **현재 별도 툴이 없고 런타임 경고 로그에 의존한다.**

## 9. 미결 / 다음 작업

- **씬 순회 검증 툴 없음** — 스폰 마커·맵 프리팹 주소 정합성이 실행 전에 확인되지 않는다. 현재는 실행 중 경고 로그로만 드러난다.
- **`Map.MapPrefab` 과 실제 어드레서블 주소 불일치** — 테이블 값과 등록된 맵 주소가 어긋난 행이 있다. `Map.xlsx` 수정이 필요하다.
- **변환기 검증 범위가 문서와 대조되지 않았다** — 8.3의 [5]~[7] 단계가 실제로 도는지 확인되지 않았다. 현재 실질 검증은 부팅 시 Catalog 계층이 담당한다.
- **`SkillPoint.SourceType` 값이 비어 있음** — 검증 근거로만 쓰이는 컬럼이라 값이 없으면 그 검증이 동작하지 않는다.
- **enum 값 삭제 정책** — 대역 번호는 재사용하지 않기로 했으나, `!Enum` 에서 값을 지웠을 때 생성 코드와 기존 세이브의 정수값이 어긋나는 문제는 정리되지 않았다. `!EnumTable` 은 문자열이라 무관하다.
- **로컬라이징** — 전 테이블이 `Name` / `Desc` / `Text` 를 직접 텍스트로 둔다. 키 방식으로 전환하면 이 문서에 규약을 추가한다.
