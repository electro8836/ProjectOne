# 보상 시스템 설계

> 2D 탑다운 방치형 핵앤슬래시 (Unity, 싱글플레이) — 퀘스트 / 던전 / 몬스터 / 상점 / 출석 / 패스 공용 보상
> 관련 문서: `아이템시스템_설계.md`, `몬스터시스템_설계.md`, `맵시스템_설계.md`, `뒤끝서버시스템_설계.md`
> **이 문서는 현재 구현 상태를 기술한다.** 컬럼·행 수는 실제 테이블 기준, 동작 서술은 `Contents/Reward/` 와 클라·서버 공용 코어 `Core/Network/Shared/Reward/` 구현 기준이다.

### 1.2 핵심 설계 원칙

> **보상은 "누가 주느냐"로 나누지 않는다. 퀘스트·던전·몬스터·상점·출석·패스가 같은 테이블 하나를 쓴다.**

```
Quest.RewardGroupID                         ─┐
GoldDungeon.RewardGroupID                   ─┤
LabyrinthDungeon.ClearRewardGroupID / Chest ─┤
RuinsDungeon.ClearRewardGroupID             ─┤
MonsterSpawn.RewardGroupID                  ─┼─→ Reward.GroupID ─→ RewardRoller
Monster.RewardGroupID                       ─┤
ShopGoods.RewardGroupID                     ─┤
DailyBonus.RewardGroupID                    ─┤
HeroPass.RewardGroupID_Normal / _Advanced   ─┘
```

주체별로 테이블을 나누면 골드 지급 코드가 여러 벌 생기고, 새 콘텐츠가 붙을 때마다 또 늘어난다. 보상은 **"무엇을 얼마나 어떤 확률로"** 로만 나뉜다.

### 1.3 경험치는 보상 그룹에 넣지 않는다

`GoldDungeon.RewardExp`, `Monster.BaseExp` / `PerLevelExp` — **각 소비처가 자기 경험치 컬럼을 갖는다.**

`RewardType` 에 `Exp` 를 추가하면 그룹 재사용성이 죽는다. 같은 아이템 보상을 주는 두 퀘스트가 경험치만 다르면 그룹을 복제해야 한다.

### 1.4 확률은 독립 판정만 쓴다

`Reward` 행마다 `Chance` 로 **독립 판정**한다. "N개 중 하나를 뽑는" 가중치 추첨은 `RewardItemPool` 안에서만 일어난다.

그룹 단위의 `RollType` / `PickCount` 같은 메타 컬럼은 두지 않는다. 독립 판정만으로 대부분의 요구가 표현되고, 메타 테이블이 하나 더 생기면 그룹을 만들 때마다 두 곳을 채워야 한다.

## 2. Enum

```
!Enum   RewardType
        Item            특정 아이템 (정확히 지정)
        ItemPool        조건에 맞는 것 중 랜덤
        Currency        재화 (아이템이 아님)

!Enum   DropTier        // Item.xlsx에 정의
        Tier_1
        Tier_2
        Tier_3
```

> `None = 0` 이 자동 생성된다. **`DropTier` 의 `None`(빈칸)이 곧 "일반 드랍 제외"** 를 뜻한다.

## 3. `Reward` 테이블 (10컬럼)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 행 고유 |
| `GroupID` | `!int` | 묶음 키. 소비처가 이 값을 참조 |
| `RewardType` | `!RewardType` | 판별 컬럼 |
| `TargetID` | `!string` | Item→`Item.ID` / ItemPool→`PoolID` / Currency→`Currency` enum |
| `EquipGradeWeightID` | `!int` | → `EquipGradeWeight.ID`. 지급 대상이 **장비일 수 있으면 필수** |
| `MinCount` | `!int` | 최소 수량 |
| `MaxCount` | `!int` | `0` 이면 `MinCount` 고정. 값이 있으면 `MinCount`~`MaxCount` 난수 |
| `Chance` | `!float` | **필수.** `0`=봉인 / `1`=확정 지급 |
| `FixedGrade` | `!ItemGradeType` | 확정 등급. 있으면 등급 추첨을 건너뛴다 |
| `FixedQuality` | `!int` | 확정 품질. **정수 퍼센트**(1~100)로 적고 코드가 0.1% 단위로 바꾼다 |

> **`TargetID` 가 `!string` 인 이유**
>
> 담는 값의 타입이 `RewardType` 마다 다르다. `Item` 과 `ItemPool` 은 정수지만 `Currency` 는 문자열 EnumTable(`Gold` / `Dia` / `Ruby` …)이다. `!int` 로 두면 재화를 순번으로 적어야 해서 매직넘버가 되고 실존 검증도 할 수 없다.

> **`Chance` 를 필수로 두는 이유**
>
> 빈칸은 `None`(0)이므로 "빈칸이면 확정 지급"으로 해석하면 **`0` 으로 봉인하는 것을 영영 표현할 수 없다.** 반대로 `0`=봉인으로 정하면 안 채운 행이 조용히 안 나온다.
>
> 그래서 값 자체를 필수로 만든다. 확정 지급도 `1` 을 적게 하면, `0` 은 오직 의도적 봉인일 때만 나타난다.

### 3.1 `Fixed*` 2컬럼 — 확정 지급 상품

등급·품질을 전부 지정하면 **추첨이 끼지 않는다.** 같은 인자로는 항상 같은 인스턴스가 나오므로, **상품 미리보기와 실제 지급이 같은 값을 쓴다.**

```
ID 10 | GroupID 3001 | Item | 1010101001 | ... | FixedGrade Rare | FixedQuality 80
```

`FixedGrade` 가 비어 있으면 `EquipGradeWeightID` 로 추첨한다. 둘 중 하나는 있어야 한다.

### 3.2 RewardType의 역할 구분

- **`Item`** — 특수 아이템, 퀘스트 보상처럼 **정확히 지정**해야 하는 것. **펫·코스튬도 이 타입으로 준다** — 수집품 아이템(`MainCategory = Collection`)은 지급 단계에서 인벤토리 대신 "보유"로 전환된다 (`CollectionRules`)
- **`ItemPool`** — 조건에 맞는 것 중 **아무거나**
- **`Currency`** — 재화. 아이템 테이블에 없으므로 타입을 분리한다

### 3.3 현재 그룹 대역

`GroupID` 는 4자리이고 **앞 두 자리가 용도**다.

| 대역 | 용도 | 참조하는 곳 |
|---|---|---|
| `100` | 최초 지급 (무기 4종·시작 재화·열쇠) | 서버 코드 — 계정 생성 시 1회 굴린다 |
| `30xx` | 묶음 상품 (장비·재화 일괄) | `ShopGoods` (Package) |
| `40xx` | 재화 단품 (다이아·골드·루비) | `ShopGoods` (Currency) |
| `41xx` | 펫 | `ShopGoods` (Item) |
| `42xx` | 코스튬 | `ShopGoods` (Item) |
| `43xx` | 지식의 서 (1 / 5 / 10개) | `ShopGoods` (Item) |
| `50xx` | 상점 보물상자 등급별 (일반 / 고급 / 최고급) | `ShopGoods` (Box) |
| `60xx` | 퀘스트 보상 | `Quest` |
| `71xx` / `72xx` | 주간 / 월간 출석 | `DailyBonus` |
| `75xx` / `76xx` | 히어로패스 일반 / 고급 | `HeroPass` |
| `80xx` | 미궁 상자 등급별 | `LabyrinthDungeon.ChestRewardGroupID_*` |
| `81xx` | 미궁 클리어 | `LabyrinthDungeon.ClearRewardGroupID` |
| `83xx` | 골드 던전 단계별 | `GoldDungeon.RewardGroupID` |
| `90xx` | 몬스터 고유 드랍 | `Monster.RewardGroupID` |
| `91xx` | 보스 고유 드랍 | `Monster.RewardGroupID` |

> **참조처가 없는 그룹이 남아 있다** — `2001`(구 일반 드랍), `82xx`(구 유적 상자)는 현재 어디서도 가리키지 않는다 (10장).

## 4. `RewardItemPool` 테이블 (6컬럼)

**한 행이 아이템 하나가 아니라 조건 하나다.**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 행 고유 |
| `PoolID` | `!int` | 묶음 키 |
| `DropTier` | `!DropTier` | 대상 티어. **정확히 일치**하는 아이템만 |
| `MainCategory` | `!ItemMainCategory` | 빈칸이면 전체 |
| `SubCategory` | `!ItemSubCategory` | 빈칸이면 전체 |
| `Weight` | `!int` | 같은 `PoolID` 안에서의 추첨 가중치 |

**현재 3개 풀**

```
1001  Tier_1 Equipment(전체)         400
      Tier_1 Material/Enhance        600
2001  Tier_2 Equipment(전체)         500
      Tier_2 Material/Enhance        490
      Tier_3 Consumable/SkillBook     10   ← 지식의 서
3001  Tier_1 Equipment(전체)        1000
```

### 4.1 열거식을 쓰지 않는 이유

아이템 ID를 하나하나 나열하면 장비가 늘어날 때 유지가 안 된다. 조건형이면 **신규 아이템에 `DropTier` 만 적으면 자동으로 드랍 풀에 편입**되고 보상 테이블은 손댈 필요가 없다.

부수 효과로 **카테고리 간 비율을 기획에서 직접 조정**할 수 있다. 장비가 나올지 재료가 나올지를 `Weight` 로 통제한다. 열거식으로는 이것이 안 된다.

### 4.2 "정확히 일치" 규칙

`DropTier` 는 **이하 포함이 아니라 정확히 일치**로 판정한다. 아이템 종류가 적어 티어당 몇 개뿐이므로, 이하 포함이면 후반 풀이 초반 아이템으로 희석된다.

초반 아이템을 섞고 싶으면 행을 하나 더 추가해 비율을 직접 통제한다.

### 4.3 `Item.DropTier`

| 값 | 의미 |
|---|---|
| 빈칸 (`None`) | **일반 드랍 대상 아님.** 명시 지급(`RewardType=Item`)으로만 획득 |
| `Tier_1` ~ `Tier_3` | 드랍 대역 |

**왜 `Normal`/`Elite`/`Boss` 가 아니라 숫자 티어인가**

- 몬스터 격 차등은 이미 `EquipGradeWeight` 가 담당한다. 같은 축을 두 컬럼이 관리하면 안 된다.
- **재료·소모품에는 등급 추첨이 없어 티어밖에 없다.** "중급 강화석"을 `Normal/Elite/Boss` 로는 표현할 수 없다.
- 티어가 늘어나면 `Tier_4` 만 붙이면 되지만, `Normal/Elite/Boss` 는 중간 삽입 시 체계가 무너진다.

**`DropTier` 가 `Item` 테이블에 있는 이유** — `RewardItemPool` 이 조건형이려면 아이템이 자기 분류를 스스로 갖고 있어야 한다. 풀 쪽에 넣으면 다시 열거식으로 회귀한다.

> **현재 드랍 대상 아이템이 매우 적다.** `DropTier` 가 채워진 것은 장비 18종(전부 `Tier_1`)과 지식의 서(`Tier_3`)뿐이다. 강화 재료는 아이템이 아니라 재화로 옮겨졌으므로 **`1001` / `2001` 풀의 `Material/Enhance` 조건은 매칭 0개**다. 실제로 쓰이는 풀은 `3001`(Tier_1 장비 전체) 하나다.

## 5. 등급 가중치 — `EquipGradeWeight` 참조

**보상 시스템은 등급 가중치표를 소유하지 않는다.** `Equipment.xlsx` 의 `EquipGradeWeight` 를 참조만 한다. 상세는 `아이템시스템_설계.md` 3.10절.

```
Reward.EquipGradeWeightID  →  EquipGradeWeight.ID
```

| ID 대역 | 용도 |
|---|---|
| `1xxxx` | 필드 (초반 / 중반 / 후반) |
| `2xxxx` | 보스 (초반 / 중반 / 후반) |
| `3xxxx` | 던전 (최상위) |
| `4xxxx` | 상자 (일반 / 고급 / 최고급) |

### 5.1 왜 장비 파일에 두는가

**등급이 추첨되는 것은 장비뿐이다.**

| | 등급 | 결정 방식 |
|---|---|---|
| 장비 | Normal ~ Mythic | **생성 시 추첨**, 승급으로 상승 |
| 재료·소모품·수집품 | 고정 | `Item.Grade` 값 그대로 |

지식의 서(`Mythic`)는 언제 어디서 나오든 항상 신화다. 추첨할 대상이 없다.

파일 위치를 장비 쪽으로 정한 근거는 세 가지다.

1. **등급 축이 전부 장비 쪽에 있다** — `Item.Grade`, `Equipment.MaxGrade`, `ItemPromotion`.
2. **장비 생성이 보상 전용이 아니다** — 상점·확정 지급에서도 등급 추첨이 필요하다.
3. 이름이 `Equip*` 인 것이 적용 범위를 알려준다. `ItemGradeWeight` 라고 부르면 "재료에도 등급 추첨이 되나"라는 오해를 부른다.

### 5.2 왜 `Reward` 행이 참조하는가 (풀이 아니라)

**"어떤 아이템이 나오는가"와 "어떤 등급으로 나오는가"는 서로 다른 축이 결정한다.**

- 아이템 종류 ← **지역**이 결정 (`RewardItemPool` 의 `DropTier`)
- 등급 확률 ← **몬스터 격 / 콘텐츠 급**이 결정 (`EquipGradeWeightID`)

같은 지역의 일반 몬스터와 보스는 같은 장비 풀에서 나와야 하지만 등급 확률은 달라야 한다. 등급을 풀에 묶으면 조합이 곱셈으로 늘어난다.

| | 분리 (채택) | 풀에 결합 |
|---|---|---|
| 1지역 × 2격 | 조건 3행 + 등급표 2개 | 조건 **6행** |
| 3지역 × 3격 | 조건 9행 + 등급표 3개 | 조건 **27행** |

## 6. 지급 로직

### 6.1 추첨(Roll)과 지급(Apply)이 분리되어 있다

**추첨 규칙은 공유 코어가 소유한다.** `RewardRoller.Roll` 은 굴리기만 하고, 인벤/지갑 반영은 클라(`RewardGranter`)와 서버가 각자 한다. 같은 테이블·같은 규칙을 양쪽이 코드 한 벌로 돌리므로 확률이 어긋날 수 없다.

```
[공유]  RewardRoller.Roll(groupId, currencyBonusPermille, rng, buffer, log)   굴리기만 — RolledReward 목록

[클라]  RewardGranter.Roll(groupId, context, buffer)                굴리기만 — 인벤/지갑에 손대지 않는다
        RewardGranter.RollWith(groupId, bonusPermille, rng, buffer) 시드 난수로 굴린다 (서버 재현용)
        RewardGranter.ApplyAll(buffer, autoDecompose)               실제 반영 + 변경 이벤트 발행
        RewardGranter.ApplyRange(buffer, startIndex, autoDecompose) 목록 일부만 반영
        RewardGranter.Grant(groupId, context, buffer)               Roll + Apply 를 한 번에
        RewardGranter.FromServer(rewards, equipments, buffer)       서버가 지급한 결과를 로컬 모델로 변환
```

**분리한 이유는 바닥 드랍과 서버 재현이다.** 몬스터 처치는 즉시 굴리되 실제 지급은 히어로가 획득 범위에 들어왔을 때 일어나고, 서버는 같은 시드로 같은 추첨을 다시 굴려 정산한다.

`buffer` 는 **비우지 않고 누적**한다. 고유 드랍과 지역 드랍처럼 두 그룹을 이어 굴릴 수 있다.

`autoDecompose` 가 켜진 경로(드랍·던전 보상)에서는 장비를 인벤에 넣기 전에 자동 분해 조건을 묻고, 맞으면 장비 대신 환급 재화를 지급한다 (`아이템시스템_설계.md` 6.5).

**결과 1건 (`GrantedReward`)**

| 필드 | 설명 |
|---|---|
| `type` | `RewardType` |
| `itemId` | Item / ItemPool 결과 |
| `currency` | Currency 결과 |
| `count` | 수량 |
| `equipment` | **장비면 만들어진 인스턴스.** 등급·품질이 여기 들어 있다 |

### 6.2 맥락 (`RewardContext`)

`Reward` 테이블은 "무엇을 얼마나" 만 갖고 **누가 왜 주는지는 모른다.** 같은 보상 그룹이 몬스터 드랍과 퀘스트 보상 양쪽에 쓰일 수 있으므로 테이블만으로는 구분할 수 없다.

```
RewardContext = None | MonsterKill | QuestComplete | DungeonClear | DailyBonus | HeroPass
```

**`MonsterKill` 일 때만** 골드 기준 수량에 `Stat_GoldDropBonus` 를 곱한다. 이 규칙은 데이터가 아니라 코드가 소유한다 (`기반테이블_설계.md` 8.1). 공유 코어는 맥락을 모르고 **재화 보너스 퍼밀(‰) 정수**만 받는다 — 맥락을 배율로 바꾸는 것은 호출자 몫이다.

### 6.2.1 결정적 추첨 — 서버가 같은 결과를 재현한다

보상의 정본은 서버지만, 화면 반응을 위해 클라가 먼저 굴려 보여준다. 둘의 결과가 같으려면 추첨이 **플랫폼과 무관하게 결정적**이어야 한다.

| 장치 | 내용 |
|---|---|
| 난수 | `DeterministicRandom`(SplitMix64). `UnityEngine.Random` / `System.Random` 은 구현이 달라 쓸 수 없다 |
| 확률 비교 | `Chance`(0~1)를 **백만분율(ppm) 정수**로 바꿔 비교한다. 실수 비교는 플랫폼 오차가 결과를 가를 수 있다 |
| 보너스 | 골드·경험치 보너스는 **퍼밀(‰) 정수**로 주고받는다 (`Permille`) |
| 품질 | 0.1% 단위 정수 (`EquipmentQuality`) |
| 시드 | 필드 처치는 세션 시드에서 **처치마다 독립 시드**를 파생한다(`KillSeed`). 한 수열을 이어 쓰면 한 번 어긋났을 때 이후가 전부 틀어진다 |

경로별 정산 방식은 `뒤끝서버시스템_설계.md` 7장이 소유한다 — 필드 처치는 배치 정산(`FieldSettle`), 던전은 입장 시 런 시드를 받아 종료 때 일괄 정산, 상점·퀘스트·출석·패스는 요청 즉시 서버가 굴려 지급한다.

### 6.3 처리 순서

```
Reward 행마다:
  1. Chance 판정 (0이면 지급하지 않음)
  2. MaxCount = 0 이면 MinCount 고정, 아니면 MinCount ~ MaxCount 난수
     → Currency 면 여기에 재화 보너스(퍼밀)를 곱한다 — MonsterKill 맥락의 GoldDropBonus
  3. RewardType 분기
     Currency  → 재화
     Item      → 해당 ItemID
     ItemPool  → 수량만큼 반복:
                   a. PoolID 안에서 Weight로 조건 행 1개 선택
                   b. 그 조건에 맞는 아이템 중 균등 1개
  4. 지급 대상이 장비면 인스턴스 생성 (6.4)
```

### 6.4 장비 인스턴스 생성

**`RewardType` 이 무엇이냐가 아니라 최종 지급 대상이 장비냐가 기준이다.** `Equipment` 테이블에 해당 ID가 있는지로 판정한다.

```
FixedGrade 가 있으면  → 등급·품질 확정 (FixedQuality 는 정수 퍼센트)
그 외                → EquipmentRoll 로 추첨 (EquipGradeWeightID)
                         1. Item.Grade ~ Equipment.MaxGrade 구간만 유효
                         2. 그 구간의 가중치만 합산해 추첨
                         3. 합이 0이면 → 드랍 스킵
                         4. 품질은 EquipQuality 구간 → 구간 내 균등
→ 정해진 등급·품질로 EquipmentFactory.CreateExact(itemId, grade, quality)
```

추첨 결과(`RolledReward`)에는 등급·품질까지만 들어 있다. **인스턴스 생성과 UID 채번은 반영하는 쪽 몫**이다 — UID 대역은 `아이템시스템_설계.md` 4.2.

장비는 인스턴스 단위라 **개수만큼 각각 굴린다.** 2개면 서로 다른 등급이 나올 수 있다.

> **`EquipGradeWeightID` 가 비어 있으면 안 된다**
>
> "비었으면 `Item.Grade` 로 고정 생성" 같은 자동 폴백을 두지 않는다. 폴백이 있으면 **의도적 고정인지 안 채운 실수인지 구분할 수 없다.**
>
> 등급을 고정하고 싶으면 `FixedGrade` 를 쓰거나, 단일 등급에 가중치를 몰아준 행을 만든다.

**티어 필터로 한 번, 등급 가중치로 또 한 번 걸러진다.** 일반 몬스터가 전설 전용 장비를 떨구는 사고가 이중으로 막힌다.

### 6.5 성능

로딩 시 공유 `RewardTable` 이 `(DropTier, MainCategory, SubCategory) → List<ItemID>` 캐시를 구축한다(클라·서버 공용). 정합성 검증과 경고 로그는 클라 `RewardCatalog` 가 맡는다. 런타임에 아이템 테이블을 매번 필터링하지 않는다.

**후보가 0개인 조건 행은 뽑히면 안 된다.** 뽑히면 그 회차가 통째로 날아간다 — `RewardCatalog.Build()` 가 부팅 시 경고를 낸다.

## 7. 드랍 획득 흐름

**몬스터 처치 보상은 즉시 인벤토리에 들어가지 않는다.** 바닥에 떨어지고 주워야 한다.

```
몬스터 사망
  └ MonsterKillReward         Monster.RewardGroupID + MonsterSpawn.RewardGroupID 를 처치 시드로 둘 다 Roll
      │                       + 처치를 FieldKillLedger 에 기록 (서버 배치 정산용)
      └ DropManager           사망 위치 주변에 산포 스폰 (굴려 둔 결과를 실어 보낸다)
          └ RewardDrop        히어로가 획득 범위에 들어오면 ApplyAll → 인벤/지갑 반영
              └ HeroMagnet    Stat_PickupRange 반경 안의 드랍을 끌어당긴다 (자석 펫)
```

- **지급 시점은 획득 시점이다.** 굴리는 시점과 인벤에 들어가는 시점이 다르다.
- **인벤토리가 가득 차면 장비 드랍은 줍지 못한다.** 바닥에 남고 `InventoryFullEvent` 로 알린다 (`아이템시스템_설계.md` 4.2).
- 던전이 끝나면 바닥에 남은 드랍을 일괄 획득·정리한다. 풀째 파괴된 드랍은 미획득으로 확정한다.
- 필드보스·퀘스트·상점·출석·패스 보상은 바닥을 거치지 않고 **서버 응답을 받아 즉시 지급**한다.
- 던전 보상 상자(`DungeonChest`)는 열 때 클라가 바로 지급하고 런 종료에 서버가 같은 값으로 저장한다.
- `DropManager` 는 회복 오브(`HealOrb`)와 전투 룬(`BuffRune`)도 함께 스폰한다. 이 둘은 보상 테이블과 무관한 월드 오브젝트다.

## 8. 참조 관계

```
Reward.GroupID       ←  Quest.RewardGroupID
                     ←  GoldDungeon.RewardGroupID
                     ←  LabyrinthDungeon.ClearRewardGroupID / ChestRewardGroupID_Normal / _Advanced / _Premium
                     ←  RuinsDungeon.ClearRewardGroupID
                     ←  Monster.RewardGroupID
                     ←  MonsterSpawn.RewardGroupID
                     ←  ShopGoods.RewardGroupID
                     ←  DailyBonus.RewardGroupID
                     ←  HeroPass.RewardGroupID_Normal / _Advanced

Reward.TargetID      →  Item.ID            (RewardType = Item)
                     →  RewardItemPool.PoolID (RewardType = ItemPool)
                     →  Currency.ID        (RewardType = Currency)

Reward.EquipGradeWeightID → EquipGradeWeight.ID   (Equipment.xlsx)

RewardItemPool       →  Item  (DropTier + MainCategory + SubCategory 조건 매칭)
```

## 9. 검증 규칙

### 참조 무결성

- `TargetID` 가 `RewardType` 에 맞는 대상으로 파싱되고 실존하는가 (오류)
- `EquipGradeWeightID` 가 `EquipGradeWeight` 에 존재하는가 (오류)
- `RewardItemPool.PoolID` 가 실존하는가 (오류)
- 소비처(8장의 참조 목록)가 가리키는 `GroupID` 가 실존하는가 (오류)

### 값 범위

- `Chance` 가 비어 있음 (오류 — 전부 봉인된다)
- `Chance` 가 0 초과 1 미만이 아닌데 1도 아님 (오류 — 확률은 0~1 배율)
- `MinCount` 가 0 이하 (오류)
- `MaxCount` 가 0이 아닌데 `MinCount` 보다 작음 (오류)
- `FixedQuality` 가 1~100 범위 밖 (오류)

### 조건형 특유의 사고 방지

- 조건에 매칭되는 아이템이 **0개**인 풀 행 (경고 → 런타임 경고로 드러난다)
- 지급 대상에 장비가 포함될 수 있는데 `EquipGradeWeightID` 와 `FixedGrade` 가 **둘 다 비었음** (오류)
- `(MainCategory, SubCategory)` 조합이 아이템 ID 대역표에 없는 조합 (오류)

## 10. 미결 / 다음 작업

- **존재하지 않는 `EquipGradeWeightID` 참조** — `Reward` ID 4 (GroupID `2001`)가 `9002` 를 가리키는데 `EquipGradeWeight` 에 그런 행이 없다. 다만 `2001` 그룹은 참조처가 없어 실제로 굴려지지 않는다.
- **존재하지 않는 아이템 참조** — 묶음 상품 `3001` / `3002` 가 `1020200001` ~ `1020200003`(구 강화 재료 아이템)을 가리키는데 `Item` 에 그런 행이 없다. 강화 재료가 재화로 옮겨졌으므로 `RewardType = Currency` 로 바꿔야 한다. **수정 필요.**
- **참조처가 없는 그룹** — `2001`(구 일반 드랍)과 `82xx`(유적 상자 시스템을 걷어내며 남은 것)는 어디서도 가리키지 않는다.
- **비어 있는 소비처** — `MonsterSpawn.RewardGroupID`(지역 드랍) 전 행, `RuinsDungeon.ClearRewardGroupID` 전 행, 신규 유저 출석(`DailyBonusType = Newbie`) 10행이 보상 그룹 없이 비어 있다.
- **`DropTier` 가 채워진 아이템이 장비 18종 + 지식의 서뿐이다** — `Material/Enhance` 조건 행은 매칭 0개다.
- **`Tier_2` 이상 장비가 없다** — 전 장비가 `Tier_1` 이라 `2001` 풀의 `Tier_2` 조건도 매칭 0개다.
- **재료 등급 표시 여부** — 재료는 등급 추첨 대상이 아니므로 `Item.Grade` 가 무해하지만, 재료에 등급을 표시할 것인지 정책 결정이 필요하다.
