# 소모품 시스템 설계

> 2D 탑다운 방치형 핵앤슬래시 (Unity, 싱글플레이) — 소모품 사용 효과
> 관련 문서: `테이블규약_설계.md`, `아이템시스템_설계.md`, `스킬시스템_설계.md`, `보상시스템_설계.md`, `무기마스터리시스템_설계.md`
> **이 문서는 현재 구현 상태를 기술한다.** 컬럼·행 수는 실제 테이블 기준, 동작 서술은 `Contents/Consumable/` 구현 기준이다.

---

## 1. 개요

### 1.1 구성 요소

| 대상 | 파일 | 시트 | 현재 행 수 |
|---|---|---|---|
| 소모품 | `Consumable.xlsx` | `Consumable` | 6 |

| 런타임 | 파일 |
|---|---|
| 사용 진입점 | `Contents/Consumable/ConsumableUser.cs` |
| 테이블 캐시 | `Contents/Consumable/ConsumableCatalog.cs` |
| 정보 팝업 | `UI/Popup/` 의 소모품 정보 팝업 |

`Item` 과 **ID를 공유하는 상세 테이블**이다. `Item ↔ Equipment` 와 동일한 패턴이며, `MainCategory=Consumable` 인 아이템은 반드시 이 테이블에 대응 행을 갖는다.

### 1.2 소모품의 정의

> **소모품 = 인벤토리에서 플레이어가 직접 "사용" 버튼을 눌러 소모하는 아이템**

이 한 줄이 소모품과 재료를 가른다.

| | 재료 (Material) | 소모품 (Consumable) |
|---|---|---|
| 소비 시작점 | 시스템 화면 (강화창·제작창) | 인벤토리에서 사용 |
| 참조 방향 | 소비하는 시스템이 아이템을 지목 | **아이템이 자기 효과를 소유** |
| 효과 정의 | 불필요 | `Consumable` 행 필요 |
| 예 | 강화석 (`EquipEnhance.CostItemID`) | 물약, 상자, 지식의 서 |

**지식의 서가 소모품인 이유**도 여기서 나온다. 사용 지점이 마스터리 화면이라는 것은 카테고리가 아니라 UI 동선의 문제다. 판단 기준은 "아이템이 자기 효과를 소유하는가"이고, 지식의 서는 소유한다.

### 1.3 티켓을 두지 않는다

`ItemSubCategory` 에서 `Ticket` 을 삭제했다.

- 던전은 **입장 비용 개념이 없다.** 재화도 입장권도 소모하지 않고 던전별 일일 카운터만 존재한다 (`맵시스템_설계.md` 8.2절).
- 레이드는 아직 `MapType` 조차 없는 미정 콘텐츠다.

**나중에 레이드 입장권이 생겨도 소모품이 아니다.** 티켓은 사용 버튼이 없고, 레이드 입장 시 시스템이 차감한다. 소비 주체가 다르므로 `Item.SubCategory` 로 분류만 하고 소모 규칙은 레이드 시스템이 갖는다. 강화 재료를 `EquipEnhance` 가 소모하는 것과 같은 구조다.

## 2. 핵심 설계 — 효과 시스템을 새로 만들지 않는다

포션(회복), 비약(버프), 폭탄(데미지)은 **전부 `SkillEffect` 가 이미 표현할 수 있다.**

```
하급 회복 물약  →  Skill(Instant, Self) → SkillEffect(Heal)
공격력 비약     →  Skill(Instant, Self) → SkillEffect(Buff)
```

소모품 전용 효과 컬럼(`HealAmount`, `BuffID`, `Duration` …)을 만들면 `SkillEffect` 와 평행하게 자라다가 결국 같은 것을 두 벌 관리하게 된다. **소모품은 "무엇을 발동하는가"만 갖고, 효과는 기존 시스템에 위임한다.**

이 판단의 결과로 소모품 효과 타입은 3개면 충분하다.

---

## 3. Enum

```
!Enum   ConsumeEffect
        Skill           스킬 시전 (회복 / 버프 / 공격 전부)
        Reward          보상 그룹 지급 (상자)
        SkillPoint      스킬포인트 지급 (지식의 서)
```

> **enum 값 규칙**: 컨버터가 `None = 0` 을 자동으로 붙인다. 실제 값은 1부터 시작하고, 테이블의 빈칸은 `None` 으로 해석된다.

## 4. `Consumable` 테이블

| 컬럼 | 타입 | 설명 |
|---|---|---|
| ID | !int | **`Item.ID` 와 동일** |
| ConsumeEffect | !ConsumeEffect | 판별 컬럼 |
| EffectParam_1 | !string | 타입별 파라미터. 4.2 참조 |
| EffectParam_2 | !string | |
| CooldownGroup | !int | None이면 자기 자신만 |
| Cooldown | !float | None이면 쿨다운 없음 |

### 4.1 `Name` / `Category` 컬럼을 두지 않는다

`Item` 과 ID를 공유하므로 이름·설명·아이콘·카테고리는 전부 `Item` 에서 읽는다. `Equipment` 테이블에 `Name` 이나 `SubCategory` 가 없는 것과 같은 이유다.

`Item.SubCategory` 를 여기에 복사해 두면 두 값이 어긋날 수 있는 여지만 생긴다. 소모품의 종류 구분이 필요하면 `Item.SubCategory` 를 보고, 동작 분기가 필요하면 `ConsumeEffect` 를 본다.

**`ConsumableType` 같은 별도 분류 enum도 두지 않는다.** `Item.SubCategory` 의 `Usable` / `Box` / `SkillBook` 과 같은 축을 이중 정의하게 된다.

### 4.2 EffectParam — 효과 파라미터

`Quest.QuestParam` 과 동일하게 **필수는 앞, 선택은 뒤** 규칙을 따른다.

| ConsumeEffect | EffectParam_1 (필수) | EffectParam_2 |
|---|---|---|
| `Skill` | `Skill.ID` | — |
| `Reward` | `Reward.GroupID` | 반복 횟수 (None이면 1회) |
| `SkillPoint` | `SkillPoint` enum ID | 지급 포인트 수 |

**타입 간 공통 의미를 부여하지 않는다.** 슬롯의 뜻은 위 표가 전부다.

`Reward` 의 반복 횟수가 있으면 "10연 상자"를 행 하나로 만들 수 있다. 없으면 같은 보상 그룹을 10줄 복제해야 한다.

### 4.3 쿨다운

| 컬럼 | 역할 |
|---|---|
| `CooldownGroup` | 같은 그룹의 소모품이 쿨다운을 공유한다 |
| `Cooldown` | 초 단위 |

하급·상급 물약이 같은 그룹을 쓰면 **번갈아 연타할 수 없다.** 방치형이라 이 통제가 없으면 물약 스택이 곧 무한 생존이 된다.

`CooldownGroup` 이 None이면 그 아이템 하나만 쿨다운을 갖는다. 상자처럼 쿨다운이 필요 없는 것은 둘 다 비운다.

### 4.4 데이터 예시

| ID | ConsumeEffect | Param_1 | Param_2 | CdGroup | Cd |
|---|---|---|---|---|---|
| `1030100001` | `Skill` | `Skill_Item_HealSmall` | | 1 | 5 |
| `1030100002` | `Skill` | `Skill_Item_HealLarge` | | 1 | 5 |
| `1030100003` | `Skill` | `Skill_Item_AtkBuff` | | 2 | 60 |
| `1030200001` | `Reward` | `1001` | | | |
| `1030200002` | `Reward` | `1001` | 10 | | |
| `1030300001` | `SkillPoint` | `SkillPoint_Item` | 1 | | |

## 5. 타입별 동작

### 5.1 `Skill`

`EffectParam_1` 의 스킬을 **시전자 = 사용자**로 즉시 실행한다.

- 대상 탐색·효과 적용은 전부 스킬 시스템이 처리한다. 소모품 쪽에 추가 규칙이 없다.
- `CastingType` 은 `Instant` 또는 `Casting` 만 허용한다. `OnHit` · `OnCombo` 같은 **조건 발동형은 아이템으로 켤 수 없다.**
- 스킬 ID는 `Skill_Item_*` 접두를 쓴다. 마스터리 스킬과 섞이지 않게 한다.

> `CastingType` 검증이 없으면, 소모품 스킬을 실수로 `OnHit` 으로 만들었을 때 **사용해도 아무 일이 안 일어나고 에러도 안 난다.**

> **[현재] 물약 3종이 동작하지 않는다** — `Skill_Item_HealSmall` / `Skill_Item_HealLarge` / `Skill_Item_AtkBuff` 가 `Skill` 테이블에 없다. 세 물약은 사용해도 `NoData` 로 실패한다.

**소모품 스킬은 `SkillContainer` 에 등록하지 않는다.** 보유 스킬이 아니고 쿨다운은 아이템이 갖는다. 공속 사이클도 타지 않으므로 `useSpeed` 는 1 고정이다.

### 5.2 `Reward`

`EffectParam_1` 의 보상 그룹을 `EffectParam_2` 회 굴려 지급한다.

- 보상 그룹의 규칙(확률·수량·등급 추첨)은 전부 `보상시스템_설계.md` 가 소유한다.
- 인벤토리가 가득 찼을 때의 처리는 인벤토리 시스템 몫이다. 소모품 테이블에 조건을 두지 않는다.

### 5.3 `SkillPoint`

`EffectParam_1` 의 스킬포인트 출처에 `EffectParam_2` 만큼 포인트를 더한다.

```
Consumable  1030300001  SkillPoint / SkillPoint_Item / 1
                          ↓
Mastery.xlsx #SkillPoint  SkillPoint_Item  MaxPoint 15  SourceType Item
```

- 대상 마스터리는 **현재 열려 있는 스킬 트리 화면**이 결정한다. 테이블에 두지 않는다. 지정이 없으면 현재 장착 무기의 마스터리로 폴백하고, 무기를 들지 않았으면 실패한다.
- `MaxPoint` 상한은 런타임 카운터가 막는다.
- `SourceType=Item` 인 출처만 지목할 수 있다.

> **이 구조가 `SkillPoint.SourceRefIDs` 를 대체했다**
>
> 이전에는 스킬포인트 테이블이 "나에게 포인트를 주는 아이템 목록"을 들고 있는 역참조였다. 그 구조에서는 목록 안의 모든 아이템이 1포인트로 동일해서, 상위 서적(3포인트)을 만들려면 별도 테이블로 승격해야 했다.
>
> 정방향으로 뒤집으면서 `EffectParam_2` 하나로 지급량 차등이 표현된다.

## 6. 참조 관계

```
Item.ID ──(동일 ID)──→ Consumable.ID     ★ MainCategory=Consumable

Consumable.EffectParam_1
  ├ ConsumeEffect=Skill       → Skill.ID
  ├ ConsumeEffect=Reward      → Reward.GroupID
  └ ConsumeEffect=SkillPoint  → SkillPoint (Mastery.xlsx)

Consumable.EffectParam_2
  ├ ConsumeEffect=Reward      → 반복 횟수 (수치)
  └ ConsumeEffect=SkillPoint  → 지급 포인트 (수치)
```

**스킬 참조원으로 등록된다.** 스킬 문서 13.4절 37번(획득 경로가 없는 스킬 경고)은 `SkillTreeNode` · `MonsterSkillSet` · `Summon.SkillID_*` · `Consumable.EffectParam_1` 을 전부 참조원으로 본다. 빠뜨리면 아이템용 스킬이 전부 경고로 뜬다.

## 7. ID 대역

아이템 문서 2장 규칙을 따른다. 소모품은 뒤 5자리가 순수 순번이다.

| 대역 | 서브 카테고리 | 예 |
|---|---|---|
| `1 03 01 NNNNN` | Usable (물약·비약) | `1030100001` |
| `1 03 02 NNNNN` | Box (아이템 상자) | `1030200001` |
| `1 03 03 NNNNN` | SkillBook (스킬포인트) | `1030300001` |

**장비와 달리 슬롯 자리가 없다.** `1030101001` 처럼 적으면 장비 규칙을 잘못 적용한 것이다.

## 8. 사용 절차

`ConsumableUser.Use(itemId, pointTarget)` 가 **단일 진입점**이다. UI 버튼은 이것 하나만 부른다.

```
1. Consumable 행 조회 + 파라미터 해석
2. 보유 수량 확인
3. 쿨다운 확인
4. 효과 실행                 ★ 먼저
5. 성공했을 때만 1개 차감 + 쿨다운 시작
```

> **효과를 먼저 굴리고 성공했을 때만 차감한다.** 지식의 서가 포인트 상한에 막혔는데 아이템이 사라지면 복구할 방법이 없다.

실패 사유는 `ConsumableUseResult` 로 돌려준다 — `NoData`(행 없음·파라미터 해석 실패) / `NotOwned` / `Cooldown` / `NoTarget`(마을·로딩 중이라 시전할 히어로가 없음) / `Failed`(효과 자체 실패).

## 9. 검증 규칙

### 구조

- `Consumable.ID` 가 `Item` 에 존재하고 `MainCategory=Consumable` 인지 (오류)
- `MainCategory=Consumable` 인 `Item` 에 `Consumable` 행이 있는지 (오류)
- `Item.MaxStack` 이 1인 소모품은 경고 (스택 불가는 대개 실수다)

### 파라미터

| ConsumeEffect | 검증 |
|---|---|
| `Skill` | P1이 `Skill` 에 존재 / 그 스킬의 `CastingType` 이 `Instant` 또는 `Casting` (오류) |
| `Reward` | P1이 `Reward.GroupID` 에 존재 / P2는 비었거나 1 이상 정수 |
| `SkillPoint` | P1이 `SkillPoint` 에 존재하고 `SourceType=Item` (오류) / P2는 1 이상 정수 |

- 정의되지 않은 파라미터 슬롯에 값이 있으면 경고 — 자유 형식 컬럼의 오타를 잡는 유일한 장치다

### 기타

- 같은 `CooldownGroup` 의 `Cooldown` 값이 서로 다르면 경고

## 10. 미결 / 다음 작업

- **선택형 상자** — "N개 중 1개 고르기"가 필요해지면 `ConsumeEffect` 에 값 하나를 추가한다. 현재 구조로 확장 가능하다.
- **일괄 사용** — 상자 10개 한 번에 열기는 UI·코드 영역이다. 테이블 변경 없음.
- **자동 사용** — 방치형이므로 "HP 30% 이하 자동 포션"이 나올 가능성이 크다. 이는 유저 설정이지 소모품 데이터가 아니다.
- **`Reward.RewardType` 에 `SkillPoint` 추가 여부** — 상자로 스킬포인트를 주려면 필요하다. 현재는 지식의 서 하나뿐이라 미룬다.
- **아이템용 스킬 데이터 없음** — `Skill_Item_HealSmall` / `Skill_Item_HealLarge` / `Skill_Item_AtkBuff` 3종이 `Skill` 테이블에 없다. **물약 3종이 실제로 동작하지 않는다.**
- **상자가 참조하는 `1001` 그룹의 재료 조건이 매칭 0개다** — 강화 재료의 `Item.DropTier` 가 비어 있어 상자를 열면 장비만 나온다 (`보상시스템_설계.md` 4.3).
- **사용 위치 제한** — "전투 중 사용 불가" 같은 규칙이 필요해지면 `UsableInBattle` 플래그를 추가한다. 지금은 요구사항이 없어 넣지 않는다.
