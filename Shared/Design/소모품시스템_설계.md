# 소모품 시스템 설계

> 2D 탑다운 방치형 핵앤슬래시 (Unity, 싱글플레이) — 소모품 사용 효과
> 관련 문서: `테이블규약_설계.md`, `아이템시스템_설계.md`, `뒤끝서버시스템_설계.md`
> **이 문서는 확정된 설계를 기술한다.** 아직 코드·테이블에 반영되지 않은 항목은 10장에 모았다.

---

## 1. 개요

### 1.1 구성 요소

| 대상 | 파일 | 시트 | 행 수 |
|---|---|---|---|
| 소모품 | `Consumable.xlsx` | `Consumable` | 0 |

| 런타임 | 파일 |
|---|---|
| 사용 진입점 | `Contents/Consumable/ConsumableUser.cs` |
| 테이블 캐시 | `Contents/Consumable/ConsumableCatalog.cs` |
| 정보 팝업 | `UI/Popup/ConsumableInfoPopup.cs`, `ConsumableInfoPresenter.cs` |
| 파괴(버리기) 묶음 전송 | `Core/Network/ItemSpendSender.cs` |

`Item` 과 **ID를 공유하는 상세 테이블**이다. `Item ↔ Equipment` 와 동일한 패턴이며, `MainCategory=Consumable` 인 아이템은 반드시 이 테이블에 대응 행을 갖는다.

**현재 소모품은 없다.** 추가할 아이템은 미정이다. 이 문서는 소모품을 추가할 때 따를 틀을 정한다.

### 1.2 소모품의 정의

> **소모품 = 인벤토리에서 플레이어가 직접 "사용" 버튼을 눌러 소모하는 아이템**

이 한 줄이 소모품과 재료를 가른다.

| | 재료 (Material) | 소모품 (Consumable) |
|---|---|---|
| 소비 시작점 | 시스템 화면 (강화창·제작창) | 인벤토리에서 사용 |
| 참조 방향 | 소비하는 시스템이 아이템을 지목 | **아이템이 자기 효과를 소유** |
| 효과 정의 | 불필요 | `Consumable` 행 필요 |
| 예 | 보물상자 열쇠 (`ShopGoods.PriceParam`) | 능력치 영구 증가 아이템 (예정) |

사용 지점이 특정 시스템 화면이더라도 그것은 카테고리가 아니라 UI 동선의 문제다. 판단 기준은 **"아이템이 자기 효과를 소유하는가"** 이다.

### 1.3 티켓을 두지 않는다

`ItemSubCategory` 에 `Ticket` 이 없다.

- 던전은 **입장 비용 개념이 없다.** 재화도 입장권도 소모하지 않고 던전별 일일 카운터만 존재한다 (`맵시스템_설계.md` 8.2절).
- 레이드는 아직 `MapType` 조차 없는 미정 콘텐츠다.

**나중에 레이드 입장권이 생겨도 소모품이 아니다.** 티켓은 사용 버튼이 없고, 레이드 입장 시 시스템이 차감한다. 소비 주체가 다르므로 `Item.SubCategory` 로 분류만 하고 소모 규칙은 레이드 시스템이 갖는다. 보물상자 열쇠를 상점이 소모하는 것과 같은 구조다.

## 2. 핵심 설계 — 단발성 효과만 둔다

> **소모품은 누르는 순간 끝나는 효과만 갖는다.** 지속 버프(비약)·회복 물약·상자형(열면 보상)은 만들지 않는다.

- 지속 버프·회복은 밸런스 부담이 크고, 씬 전환 때 히어로가 다시 만들어지면서 버프가 사라지는 문제가 있다.
- 상자는 소모품이 아니라 **상점 상품**(`GoodsType = Box`)이다. 열쇠를 가격으로 받고 보상 그룹을 지급한다.
- 그래서 **쿨다운·지속시간 개념이 없다.** `CooldownGroup` / `Cooldown` 컬럼도 두지 않는다.

추가하는 소모품은 능력치 영구 증가 같은 단발성 아이템으로 한정한다.

---

## 3. Enum

```
!Enum   ConsumeEffect
        Reserved        미사용 자리 — 첫 소모품 효과를 추가할 때 교체한다
```

> **`Reserved` 는 효과가 아니다.** 변환기가 값이 하나도 없는 enum 을 거부해서 둔 자리 값이다. 이 값을 쓰는 `Consumable` 행은 사용 대상에서 빠진다.

> **enum 값 규칙**: 컨버터가 `None = 0` 을 자동으로 붙인다. 실제 값은 1부터 시작하고, 테이블의 빈칸은 `None` 으로 해석된다.

## 4. `Consumable` 테이블

| 컬럼 | 타입 | 설명 |
|---|---|---|
| ID | !int | **`Item.ID` 와 동일** |
| ConsumeEffect | !ConsumeEffect | 판별 컬럼 |
| EffectParam_1 | !string | 타입별 파라미터. 4.2 참조 |
| EffectParam_2 | !string | |

### 4.1 `Name` / `Category` 컬럼을 두지 않는다

`Item` 과 ID를 공유하므로 이름·설명·아이콘·카테고리는 전부 `Item` 에서 읽는다. `Equipment` 테이블에 `Name` 이나 `SubCategory` 가 없는 것과 같은 이유다.

`Item.SubCategory` 를 여기에 복사해 두면 두 값이 어긋날 수 있는 여지만 생긴다. 소모품의 종류 구분이 필요하면 `Item.SubCategory` 를 보고, 동작 분기가 필요하면 `ConsumeEffect` 를 본다.

**`ConsumableType` 같은 별도 분류 enum도 두지 않는다.** `Item.SubCategory` 와 같은 축을 이중 정의하게 된다.

### 4.2 EffectParam — 효과 파라미터

`Quest.QuestParam` 과 동일하게 **필수는 앞, 선택은 뒤** 규칙을 따른다.

| ConsumeEffect | EffectParam_1 (필수) | EffectParam_2 |
|---|---|---|
| (효과를 추가할 때 이 표에 슬롯의 뜻을 적는다) | | |

**타입 간 공통 의미를 부여하지 않는다.** 슬롯의 뜻은 위 표가 전부다.

문자열은 사용할 때마다 파싱하지 않고 **부팅 시 `ConsumableCatalog.Build()` 가 한 번 굽는다** (`BakedConsumable`). 해석에 실패한 행은 사용 대상에서 빠지고 부팅 로그에 경고가 남는다.

### 4.3 쿨다운

**없다.** 단발성 효과만 둔다 (2장).

## 5. 타입별 동작

효과 종류를 추가할 때 이 장에 동작을 적는다. 한 효과당 적을 내용은 다음과 같다.

| 항목 | 내용 |
|---|---|
| 대상 | 효과가 무엇을 바꾸는가 |
| 상한 | 사용 횟수·누적 상한이 있으면 그 기준과 카운터 위치 |
| 실패 조건 | 효과를 굴릴 수 없는 경우 (상한 도달 등) |
| 서버 반영 | 영속 상태를 바꾸면 어떤 펑션으로 저장하는가 |

```
  └ ConsumeEffect 별 해석 (4.2)
```

## 7. ID 대역

아이템 문서 2장 규칙을 따른다. 소모품은 뒤 5자리가 순수 순번이다.

| 대역 | 서브 카테고리 | 예 |
|---|---|---|
| `1 03 01 NNNNN` | Usable | 현재 행 없음 |
| `1 03 02 NNNNN` | — | 폐기된 번호(구 Box). 재사용하지 않는다 |
| `1 03 03 NNNNN` | — | 폐기된 번호(구 SkillBook). 재사용하지 않는다 |

**장비와 달리 슬롯 자리가 없다.** `1030101001` 처럼 적으면 장비 규칙을 잘못 적용한 것이다.

## 8. 사용 절차

`ConsumableUser.Use(itemId)` 가 **단일 진입점**이다. UI 버튼은 이것 하나만 부른다.

```
1. Consumable 행 조회 (부팅 때 구운 값)
2. 보유 수량 확인
3. 효과 실행                 ★ 먼저
4. 성공했을 때만 1개 차감
5. 서버에 같은 차감·변경을 저장하도록 요청
6. ConsumableUsedEvent 발행 (성공·실패 모두)
```

> **효과를 먼저 굴리고 성공했을 때만 차감한다.** 효과가 상한에 막혔는데 아이템이 사라지면 복구할 방법이 없다.

실패 사유는 `ConsumableUseResult` 로 돌려준다 — `NoData`(행 없음·파라미터 해석 실패) / `NotOwned` / `Failed`(효과 자체 실패 — 상한 등).

**서버 반영** — 영속 상태를 바꾸는 효과는 로컬에 반영한 뒤 서버가 같은 차감·변경을 저장하도록 요청한다. 효과마다 서버 검증(보유·상한)이 필요하다. 인벤토리에서 아이템을 **파괴(버리기)** 하는 경로는 `ItemSpendSender` 가 묶어서 `ItemSpend` 로 보낸다 (`뒤끝서버시스템_설계.md` 7장).

---

## 9. 검증 규칙

### 구조

- `Consumable.ID` 가 `Item` 에 존재하고 `MainCategory=Consumable` 인지 (오류)
- `MainCategory=Consumable` 인 `Item` 에 `Consumable` 행이 있는지 (오류)
- `Item.MaxStack` 이 1인 소모품은 경고 (스택 불가는 대개 실수다)

### 파라미터

- 효과별 검증은 4.2 표에 효과를 추가할 때 함께 정한다.
- 정의되지 않은 파라미터 슬롯에 값이 있으면 경고 — 자유 형식 컬럼의 오타를 잡는 유일한 장치다

---

## 10. 미결 / 다음 작업

- **단발성 소모품 추가** — 능력치 영구 증가(엘릭서) 같은 아이템이 후보다. `ConsumeEffect` 에 값 하나를 추가하고 `ConsumableUser.apply` 에 분기를 넣는다. 쿨다운·지속시간은 들이지 않는다 (2장).
- **보스소환석 (예정)** — 보스 구역에서 사용하면 그 보스가 즉시 리스폰한다. 전 보스 공용 1종, 획득처 미정 (`월드진행_설계.md` 8.2).
- **사용 위치 제한** — "전투 중 사용 불가" 같은 규칙이 필요해지면 `UsableInBattle` 플래그를 추가한다. 지금은 요구사항이 없어 넣지 않는다.
