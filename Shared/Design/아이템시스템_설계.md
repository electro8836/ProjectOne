## 1. 개요 및 설계 원칙

### 1.1 핵심 원칙

1. **`Item` 이 모든 아이템의 공통 메타데이터를 갖고, 타입별 상세는 같은 ID로 확장한다.**
2. **장비 인스턴스는 옵션 수치를 저장하지 않는다.** `(ItemID, Grade, Level, Purity, Quality)` 로 매번 재계산한다.
3. **옵션은 `Option` 을 경유한다.** 장비·스킬 트리·마스터리가 같은 옵션 목록을 공유한다.
4. **ID의 카테고리 번호는 enum 순서가 아니라 고정 대역표다.**

### 1.2 등급 체계

`ItemGradeType` — `Normal` / `Magic` / `Rare` / `Epic` / `Legendary` / `Mythic` (6종)

장비는 **인스턴스마다 현재 등급**을 갖고 승급으로 오른다. 재료·소모품은 변하지 않는 표시용 등급이다.

### 1.3 착용 슬롯

`EquipSlotTypes` — `Weapon` / `Helmet` / `Armor` / `Gloves` / `Boots` / `Ring` / `Amulet` / `Relic` (8종)

착용 슬롯은 배열 인덱스로 쓰이므로 **enum 중간 삽입이 기존 저장 데이터를 깨뜨린다.** 신규 항목은 끝에 추가한다.

### 1.4 런타임 구현 위치

| 대상 | 파일 |

## 2. 아이템 ID 체계

### 2.1 구조

모든 아이템 ID는 10자리 정수다. 앞 5자리는 공통이고, **뒤 5자리의 분할 규칙만 메인 카테고리별로 다르다.**

```
공통    :  1 MM SS -----
           │ │  └──────── 서브 카테고리 (2자리, 고정 번호)
           │ └─────────── 메인 카테고리 (2자리, 고정 번호)
           └───────────── 고정값 1 (선행 0 소실 방지)

장비    :  1 01 SS TT NNN
                    │  └─ 순번 (001 ~ 999)
                    └──── 슬롯 (EquipSlotTypes 순번, 01 ~ 08)

그 외   :  1 MM SS NNNNN
                    └──── 순번 (00001 ~ 99999)
```

**뒤 5자리에 슬롯을 인코딩하는 것은 장비뿐이다.**

> **자릿수 제약** — 10자리를 초과하면 Int32 범위(2,147,483,647)를 넘어간다. 순번 자릿수를 늘리려면 ID 타입을 `!long` 으로 바꿔야 한다.

### 2.2 카테고리 번호 — 고정 대역표

**`MM` · `SS` 는 enum의 선언 순서가 아니라 이 표에 고정된 번호다.**

| MM | 메인 카테고리 | SS | 서브 카테고리 |
|---|---|---|---|
| `01` | Equipment (장비) | `01` | Weapon (무기) |
| | | `02` | Armor (방어구) |
| | | `03` | Accessory (장신구) |
| | | `04` | Relic (유물) |
| `02` | Material (재료) | `01` | Crafting (제작 재료) |
| | | `02` | Enhance (강화 재료) |
| `03` | Consumable (소모품) | `01` | Usable (물약·비약) |
| | | `02` | Box (아이템 상자) |
| | | `03` | SkillBook (지식의 서) |
| `04` | Collection (수집품) | `01` | Costume (코스튬) |

**`SS` 는 메인 카테고리 안에서만 유니크하다.** `MM` 이 바뀌면 `01` 부터 다시 시작한다.

> **왜 enum 순서와 분리했는가** — 과거 `ItemSubCategory` 재정렬 한 번에 **모든 소모품 ID가 어긋난** 적이 있다. 이미 발급된 아이템 ID는 세이브 데이터에 박히므로 사후 수정이 불가능하다. enum은 읽기 좋은 순서로 자유롭게 정렬하고, ID는 이 표만 본다.

- 한 번 부여한 번호는 **재사용하지 않는다.**
- 이 표는 ID 생성 규칙이자 `(MainCategory, SubCategory)` **조합 검증표**다. 표에 없는 조합(`Material` + `Box` 등)은 오류다. `RewardItemPool` 의 조건 행에도 같은 검증을 적용한다.

### 2.3 장비의 슬롯 자리 (`TT`)

| TT | EquipSlotTypes | 소속 SS |
|---|---|---|
| `01` | Weapon | `01` 무기 |
| `02` | Helmet | `02` 방어구 |
| `03` | Armor | `02` 방어구 |
| `04` | Gloves | `02` 방어구 |
| `05` | Boots | `02` 방어구 |
| `06` | Ring | `03` 장신구 |
| `07` | Amulet | `03` 장신구 |
| `08` | Relic | `04` 유물 |

**`TT` 가 정해지면 `SS` 는 하나로 결정된다.** `SS` 가 사실상 중복 정보임에도 빼지 않는 이유는 다른 카테고리와 자릿수를 맞추기 위함이고, `1010306001` 을 봤을 때 "장신구"가 바로 읽히기 때문이다.

대신 두 가지를 검증한다.

- `(SS, TT)` 조합이 위 표에 존재하는가
- `TT` 가 그 아이템의 `Equipment.EquipSlotType` 과 일치하는가

두 번째가 특히 중요하다. ID를 손으로 적는 구조라 `1010306001` 을 `1010206001` 로 오타내기 쉽고, 이 검증이 없으면 아무도 모른다.

> **`NNN` 은 순수 순번이다.** 등급·세트·티어를 인코딩하지 않는다. 슬롯은 `Equipment.EquipSlotType`, 등급은 `Item.Grade`, 드랍 대역은 `Item.DropTier` 가 소유한다.

### 2.4 실제 예시

| ID | 분해 | 아이템 |
|---|---|---|
| `1010101001` | 1 · 01 장비 · 01 무기 · 01 Weapon · 001 | 쌍검 |
| `1010101003` | 1 · 01 장비 · 01 무기 · 01 Weapon · 003 | 석궁 |
| `1010202001` | 1 · 01 장비 · 02 방어구 · 02 Helmet · 001 | 강철 투구 |
| `1010205002` | 1 · 01 장비 · 02 방어구 · 05 Boots · 002 | 가죽 신발 |
| `1010306001` | 1 · 01 장비 · 03 장신구 · 06 Ring · 001 | 근접 반지 |
| `1010408001` | 1 · 01 장비 · 04 유물 · 08 Relic · 001 | 근접 유물 |
| `1020100001` | 1 · 02 재료 · 01 제작 · 00001 | 청동 열쇠 |
| `1020200001` | 1 · 02 재료 · 02 강화 · 00001 | 무기 강화 주문서 |

## 3. 테이블 명세

### 3.1 파일 구성과 테이블 관계

| 파일 | 시트 | 역할 |
|---|---|---|
| `Item.xlsx` | `#Enum` | `ItemMainCategory` / `ItemSubCategory` / `ItemGradeType` / `DropTier` |
| | `#Item` | 통합 아이템 (30행) |
| `Consumable.xlsx` | `#Enum` | `ConsumeEffect` |
| | `#Consumable` | 소모품 확장 (6행) → `소모품시스템_설계.md` |
| `Equipment.xlsx` | `#Enum` | `EquipSlotTypes` / `WeaponType` / `EquipEnhanceTier` / `EquipPurity` |
| | `#Equipment` | 장비 확장 (18행) |
| | `#EquipOption` | 등급별 옵션 (108행) |
| | `#EquipEnhance` · `#EquipEnhanceTier` | 강화 (48행 / 6행) |
| | `#EquipPromotion` | 승급 (48행) |
| | `#EquipQuality` · `#EquipPurity` · `#EquipGradeWeight` | 생성 시 추첨 (5 / 5 / 10행) |
| `Currency.xlsx` | `#Currency` | 재화 (3행) → `기반테이블_설계.md` |

```
Item ──(동일 ID)── Equipment ──(EquipOptionGroupID)── EquipOption ──(OptionID)── Option
  │                    │
  └──(동일 ID)── Consumable   ★ MainCategory=Consumable 인 아이템
                       │
                       ├── WeaponType ──→ [역참조] WeaponMastery   ★ 무기만
                       ├── EquipEnhance ──(EnhanceTier)── EquipEnhanceTier
                       ├── EquipPromotion
                       └── (생성 시) EquipGradeWeight / EquipPurity / EquipQuality
```

| MainCategory | 상세 테이블 |
|---|---|
| `Equipment` | `Equipment` (+ 옵션·강화·승급) |
| `Consumable` | `Consumable` |
| `Material` · `Collection` | 없음 — `Item` 행만으로 완결 |

> **ID 공유 테이블은 세트로 만든다.** `Item` 행만 만들고 `Equipment` / `Consumable` 행을 빠뜨리면 드랍·사용 시 실패한다.

### 3.2 Item — 통합 아이템

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 기본 키. 2장의 ID 규칙을 따른다 |
| `Name` | `!string` | 표시 이름 |
| `Desc` | `!string` | 설명 |
| `Icon` | `!string` | 아이콘 어드레서블 주소 |
| `MainCategory` | `!ItemMainCategory` | Equipment / Material / Consumable / Collection |
| `SubCategory` | `!ItemSubCategory` | Weapon / Armor / Accessory / Relic / Crafting / Enhance / Usable / Box / SkillBook / Costume |
| `Grade` | `!ItemGradeType` | 장비: **최소 드랍 등급** / 그 외: 고정 표시 등급 |
| `DropTier` | `!DropTier` | 일반 드랍 대역(`Tier_1~3`). **None이면 드랍 제외** |
| `MaxStack` | `!int` | 최대 스택. 0이면 무한 스택 |

> **`Grade` 의 이중 의미** — 장비에서 `Grade` 는 인스턴스의 현재 등급이 아니라 **드랍 가능한 최소 등급**이다. `Legendary` 로 설정된 장비는 전설~`MaxGrade` 범위에서만 생성된다. 재료·소모품은 변하지 않는 표시용 등급이다.

> **`MaxStack` 은 장비에서 무시된다.** 장비는 인스턴스 단위(UID)로 관리되므로 스택 개념이 없다. 관례상 `1` 을 적지만 코드는 이 값을 보지 않는다.

> **`DropTier`** — `RewardItemPool` 이 조건형으로 아이템을 고르기 위한 분류다. 조건 판정이 **정확히 일치**이므로 비우면 일반 드랍에서 완전히 제외된다 (`보상시스템_설계.md` 4장).

### 3.3 Equipment — 장비 확장

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 기본 키. `Item.ID` 와 동일한 값 |
| `EquipSlotType` | `!EquipSlotTypes` | 착용 슬롯 |
| `WeaponType` | `!WeaponType` | 무기 세부 종류. 무기 외 장비는 빈칸 |
| `MaxGrade` | `!ItemGradeType` | 승급 가능한 최대 등급 |
| `EquipOptionGroupID` | `!int` | `EquipOption.GroupID` 참조 |
| `WeaponSetAddress` | `!string` | **장착 시 캐릭터에 붙는 무기 외형 세트 주소.** 무기만 사용 |

> **무기는 착용 조건이 아니라 빌드 스위치다**
>
> ```
> 무기 장착 → Equipment.WeaponType → WeaponMastery 역참조
>              ├─ 기본공격     = NormalAttackSkill
>              ├─ 스킬 트리    = SkillTreeNodeGroupID
>              ├─ 근접/원거리  = RangeType
>              ├─ 애니메이터   = AnimControllerName
>              └─ 경험치 적립처 = 이 마스터리
> ```
>
> 무기를 바꾸면 스킬 구성이 통째로 바뀐다. 무기 교체에 비용·제약·손실은 없으며, 각 마스터리의 진행도는 독립적으로 보존된다.
>
> **무기를 착용하지 않으면 공격할 수 없다.** 기본공격도 스킬 트리도 없다. 다만 방어구·장신구 옵션과 캐릭터 기본 스탯은 정상 작동한다.

> **요구 직업·요구 레벨 컬럼이 없다.** 방어구·장신구·유물은 전부 공용이고, 무기는 `WeaponType` 자체가 빌드를 결정하므로 착용 제한이 불필요하다.

> **근접·원거리 전용 옵션에 주의** — `OPT_MELEE_DAMAGE_BONUS_ADD` / `OPT_RANGE_DAMAGE_BONUS_ADD` 는 장착 무기의 `RangeType` 에 따라 적용 여부가 갈린다. **무기를 바꾸면 즉시 사장된다.** 방어구·장신구에는 범용 `OPT_DAMAGE_BONUS_ADD` 를 권장한다. 무기 자체의 옵션으로 쓰는 것은 안전하다.

### 3.4 EquipOption — 등급별 옵션

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 기본 키(일련번호) |
| `GroupID` | `!int` | 옵션 그룹 식별자 |
| `ItemGrade` | `!ItemGradeType` | 적용 등급 |
| `Opt1~4_ID` | `!Option` | 기본 옵션 종류. 사용하지 않으면 빈칸 |
| `Opt1~4_Val` | `!float` | 기본값 (**0레벨 기준**) |
| `Opt1~4_Step` | `!float` | 강화 레벨당 증가량 |
| `UnlockOpt_ID` | `!Option` | 해당 등급 달성 시 해금되는 옵션 |
| `UnlockOpt_MinVal` | `!float` | 품질 0 기준값 |
| `UnlockOpt_MaxVal` | `!float` | 품질 100 기준값 |

> **실제 조회 키는 `(GroupID, ItemGrade)` 다.** 테이블의 기본 키는 `ID` 지만 런타임 조회는 항상 그룹+등급 조합이다. `EquipmentCatalog` 가 복합키 인덱스를 만든다.

**작성 규칙**

- 하나의 `GroupID` 는 **6개 등급 행을 모두** 가져야 한다. (현재 18그룹 × 6 = 108행)
- **`UnlockOpt` 는 Normal 행에도 넣는다.** 구현이 `Normal` 부터 누적하며 현재 데이터도 Normal 행에 해금 옵션을 갖고 있다.
- 등급이 오르면서 기본 옵션이 추가되는 것은 허용한다. 다만 **`Opt1` 이 등급마다 다른 옵션이 되어서는 안 된다.**
- 현재 데이터는 `EquipOptionGroupID = ItemID` 로 1:1 대응한다. 여러 장비가 한 그룹을 공유하는 것도 가능하다.

### 3.5 EquipEnhanceTier — 강화 티어

`!EnumTable`. 강화 레벨 구간과 등급을 매핑한다.

| ID | Grade | MinLevel | MaxLevel |
|---|---|---|---|
| `Tier_1` | Normal | 1 | 20 |
| `Tier_2` | Magic | 21 | 40 |
| `Tier_3` | Rare | 41 | 60 |
| `Tier_4` | Epic | 61 | 80 |
| `Tier_5` | Legendary | 81 | 100 |
| `Tier_6` | Mythic | 101 | 120 |

**두 방향으로 쓰인다.** 등급 → 레벨 상한(강화 가능 여부), 레벨 → 티어(비용 조회).

### 3.6 EquipEnhance — 강화 비용

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 일련번호 |
| `Category` | `!EquipSlotTypes` | 슬롯별로 비용이 다르다 |
| `EnhanceTier` | `!EquipEnhanceTier` | 비용 구간 |
| `CostItemID_1` / `CostItemCnt_1` / `CostItemMult_1` | `!int` / `!int` / `!float` | 재료 1 + 구간 내 증가 배율 |
| `CostItemID_2` / `CostItemCnt_2` / `CostItemMult_2` | | 재료 2 |
| `CostCurrencyID` | `!Currency` | 재화 종류 |
| `CostCurrencyValue` / `CostCurrencyMult` | `!int` / `!float` | 재화 기준량 + 증가 배율 |

**8슬롯 × 6티어 = 48행.** 재료 슬롯은 2개다.

### 3.7 EquipPromotion — 승급 비용

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 일련번호 |
| `Category` | `!EquipSlotTypes` | 슬롯 |
| `FromGrade` / `ToGrade` | `!ItemGradeType` | 승급 전/후. `ToGrade` 가 None이면 **승급 불가** |
| `CostItemID_1~4` / `CostItemCnt_1~4` | `!int` | 재료 4슬롯 |
| `CostCurrencyID` / `CostCurrencyValue` | `!Currency` / `!int` | 재화 |

**8슬롯 × 6등급 = 48행.** 승급은 1회성이라 **배율 컬럼이 없다.** 재료 슬롯은 강화(2개)보다 많은 4개다.

### 3.8 EquipPurity — 순도

`!EnumTable`. 인스턴스 생성 시 결정되는 **옵션 배율** 축이다.

| ID | DisplayName | OptionMultiplier | AssignWeight | ColorHex |
|---|---|---|---|---|
| `Purity_1` | D | 0.6 | 300 | `#FF4D4D` |
| `Purity_2` | C | 0.8 | 350 | `#FFA500` |
| `Purity_3` | B | 1.0 | 220 | `#FFFFFF` |
| `Purity_4` | A | 1.2 | 100 | `#4D94FF` |
| `Purity_5` | S | 1.4 | 30 | `#FFD700` |

`CalcRate` 컬럼은 엑셀 수식 기반의 **기획 확인용**이다. 런타임은 `AssignWeight` 합으로 직접 추첨한다.

> **ID와 표시명이 분리되어 있다.** ID는 `Purity_N`(번호), 표시는 `DisplayName`(D~S)이다. 등급 문자를 바꿔도 데이터가 어긋나지 않는다.

### 3.9 EquipQuality — 품질 구간

`!Table`. 인스턴스 생성 시 결정되는 **해금 옵션 보간값**(1~100) 축이다.

| ID | MinValue | MaxValue | AssignWeight |
|---|---|---|---|
| 1 | 1 | 30 | 500 |
| 2 | 31 | 70 | 350 |
| 3 | 71 | 90 | 120 |
| 4 | 91 | 99 | 28 |
| 5 | 100 | 100 | 2 |

**구간을 먼저 뽑고, 구간 안에서 균등 분포로 정수를 뽑는다.** 품질 자체에는 등급명·색상이 없다.

### 3.10 EquipGradeWeight — 등급 가중치 그룹

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 그룹 ID |
| `Desc` | `!string` | **필수.** 시트에서 의미를 읽는 유일한 수단 |
| `Normal` ~ `Mythic` | `!int` | 등급별 가중치 6개 |

**현재 10행**

| ID 대역 | 용도 | 행 |
|---|---|---|
| `1xxxx` | 필드 | 초반 / 중반 / 후반 |
| `2xxxx` | 보스 | 초반 / 중반 / 후반 |
| `3xxxx` | 던전 | 최상위 |
| `4xxxx` | 상자 | 일반 / 고급 / 최고급 |

가중치를 큰 숫자(합 1000)로 두는 이유는 **0.1% 단위를 정수로 표현**하기 위해서다. 소수를 쓰면 시트에서 합이 1이 되는지 눈으로 확인하기 어렵다.

이 테이블이 장비 파일에 있는 이유는 **등급 축이 전부 장비 소유**이고, 장비 생성이 보상 외 경로(상점·확정 지급)에서도 일어나기 때문이다. 보상 시스템은 참조만 한다.

### 3.11 Option — 옵션 정의

`Option.xlsx` 소유이며 **정의와 계산 규칙은 `기반테이블_설계.md` 6장이 갖는다.** 여기서는 장비가 어떻게 쓰는지만 적는다.

| OptionType | 장비에서의 쓰임 |
|---|---|
| `Stat` | `EquipmentAspect` 가 `StatContainer.AddModifier` 로 반영 |
| `SkillGrant` | 장비가 스킬을 부여 |
| `SkillLevel` `Modifier` | `SkillResolver` 로 전달 — **스탯 식에 들어가지 않는다** |

**값은 언제나 `EquipOption` 이 소유하고, `Option` 은 "무엇을 건드리는가"만 정의한다.**

### 3.12 지식의 서 — 스킬포인트 소모품

`1030300001` / `MainCategory = Consumable` / `SubCategory = SkillBook` / `Grade = Mythic` / `DropTier = Tier_3`

사용 지점이 마스터리 화면이라는 것은 카테고리가 아니라 UI 동선의 문제다. **판단 기준은 "아이템이 자기 효과를 소유하는가"** 이고 지식의 서는 소유한다 (`Consumable.ConsumeEffect = SkillPoint`). 상세는 `소모품시스템_설계.md`.

## 4. 인벤토리와 장비 인스턴스

### 4.1 장비 인스턴스

`Contents/Items/EquipmentInstance.cs` — **저장되는 동적 데이터는 이것이 전부다.**

| 필드 | 타입 | 설명 |
|---|---|---|
| `uid` | `long` | 인스턴스 고유 번호 |
| `itemId` | `int` | `Item.ID` / `Equipment.ID` |
| `grade` | `ItemGradeType` | 현재 등급 (승급으로 상승) |
| `level` | `int` | 강화 레벨 (1부터) |
| `purity` | `EquipPurity` | 순도 (생성 시 확정) |
| `quality` | `int` | 품질 1~100 (생성 시 확정) |
| `equippedSlot` | `EquipSlotTypes` | 착용 중인 슬롯. None이면 미착용 |

> **옵션 수치를 저장하지 않는다.** 매번 재계산하므로 승급은 `grade` 를 한 단계 올리는 것만으로 끝나고 레벨·순도·품질이 자연히 보존된다. 테이블 밸런스를 조정하면 이미 보유한 장비에도 즉시 반영된다.

### 4.2 인벤토리 구조

```
Account
  ├ Inventory   스택 아이템(OwnedItem: itemId + count) + 장비 인스턴스 목록
  ├ Loadout     캐릭터 레벨/경험치 + 착용 슬롯 배열 (값은 인스턴스 UID)
  └ Wallet      재화
```

- **스택 아이템과 장비가 같은 인벤토리에 있다.** 재료·소모품은 `OwnedItem` 으로 개수만, 장비는 인스턴스로 보관한다.
- `Loadout` 의 슬롯은 `EquipSlotTypes` 정수 인덱스 배열이고 값은 **UID** 다. 인스턴스 자체를 참조하지 않으므로 직렬화가 단순해진다.
- 착용 중인 장비는 인벤토리 그리드에서 제외된다.
- 저장은 dirty 플래그 기반 지연 저장이다.

> **장비 UID 채번이 아직 클라이언트에 있다** (`InventoryDto.nextEquipmentUid`). 서버 권위로 옮기는 것이 남아 있다.

## 5. 옵션 계산 규칙

### 5.1 기본 옵션 (Opt1~4)

```
최종값 = (Val + Step × Level) × EquipPurity.OptionMultiplier
```

- `Val` · `Step` 은 **현재 등급에 해당하는 행 하나**에서만 가져온다.
- 승급하면 `Val` · `Step` 이 다음 등급 행의 값으로 교체되어 수치가 계단식으로 상승한다.
- 품질은 기본 옵션에 영향을 주지 않는다.
- 순도 데이터가 없으면 배율 1.0으로 폴백한다 — 옵션이 통째로 0이 되는 사고를 막는다.

> **`Val` 은 0레벨 기준값이다 — 캐릭터 스탯과 규칙이 반대다**
>
> 장비는 1레벨부터 시작하므로 테이블의 `Val` 이 그대로 표시되는 일은 없다. `Val=10, Step=1` 이면 1레벨 실제 값은 11이다.
>
> 반면 `CharacterStat.BaseValue` 는 **1레벨 기준값**이며 `BaseValue + PerLevel × (Level - 1)` 이다. 두 문서를 오가며 데이터를 넣을 때 가장 실수하기 쉬운 지점이다. **장비는 0레벨 기준, 캐릭터는 1레벨 기준.**

**계산 예시** — 쌍검(`1010101001`), Rare 등급, 45레벨, 순도 A(1.2)

```
Opt1 (OPT_ATK_ADD)  Val=60, Step=1.2
→ (60 + 1.2 × 45) × 1.2 = (60 + 54) × 1.2 = 136.8
```

### 5.2 해금 옵션 (UnlockOpt)

```
최종값 = MinVal + (MaxVal - MinVal) × (Quality / 100)
```

- **현재 등급 이하의 모든 등급 행**의 `UnlockOpt` 가 누적 적용된다.
- 강화 레벨의 영향을 받지 않는다. **품질로만 값이 결정된다.**
- `MinVal` 과 `MaxVal` 이 같으면 품질과 무관한 고정 옵션이 된다.
- `SkillGrant` 나 `Modifier` 타입 옵션을 해금 옵션에 쓸 때는 반드시 `MinVal = MaxVal` 로 둔다. 스킬 획득 여부가 품질에 따라 흔들리면 안 된다.

**계산 예시** — 쌍검, Rare 등급, 품질 60

```
Magic 해금  OPT_ATK_SPEED_ADD   Min=0.02, Max=0.2
→ 0.02 + (0.2 - 0.02) × 0.6 = 0.128

Rare 해금   OPT_CRIT_RATE_ADD   Min=0.1,  Max=0.15
→ 0.1 + 0.05 × 0.6 = 0.13
```

Mythic 등급 장비는 Normal~Mythic **6개** 해금 옵션을 전부 갖는다.

### 5.3 최종 스탯 반영

각 옵션은 `Option.OptionTarget` 이 지정한 `StatDetail` 로 누적된다. 적용 경로는 다음과 같다.

```
EquipmentAspect (IHeroAspect, source = "Equipment")
  → Loadout 의 착용 슬롯 순회
  → EquipmentOptionCalculator.Collect(instance, buffer)
  → OptionCatalog.TryGet(option)
       ├ Stat       → hero.Stats.AddModifier(statDetail, value, "Equipment")
       ├ SkillGrant → 보유 스킬 등록
       └ SkillLevel / Modifier → SkillResolver
```

장비 해제는 `RemoveAllFromSource("Equipment")` 한 번으로 끝난다.

최종 스탯 합성 순서는 다음과 같다.

```
[1] 기본값        CharacterStat (캐릭터 레벨)      → StatDetail_*_Base
[2] 마스터리 보너스 LevelBonusOption               → Option   (무기 무관, 항상)
[3] 스킬 트리      현재 마스터리의 노드 투자        → Option   (그 무기일 때만)
[4] 장비          EquipOption 기본 · 해금 옵션      → Option   ★ 이 문서
[5] 버프          SkillEffect (StatChange)        → StatDetail
```

> **합성식과 클램프는 `기반테이블_설계.md` 8장이 소유한다.** 이 절은 [4]가 무엇을 공급하는지만 서술한다. **[2]~[5]의 적용 순서는 결과에 영향을 주지 않는다** — 같은 레이어에 들어가는 값은 전부 합산이다.

`Modifier` 타입 옵션은 이 식에 들어가지 않고 스킬 리졸브 파이프라인으로 전달된다 (`스킬시스템_설계.md` 11장).

## 6. 강화 및 승급

구현: `Contents/Upgrade/EquipmentUpgrade.cs`

### 6.1 강화

**레벨 상한**

```
MaxLevel = EquipEnhanceTier[현재 Grade].MaxLevel
```

등급별 상한은 20 / 40 / 60 / 80 / 100 / 120이다. 상한에 도달하면 승급해야 추가 강화가 가능하다.

**비용 계산**

```
Tier = EquipEnhanceTier 중 MinLevel ≤ 현재 Level ≤ MaxLevel 인 행
n    = 현재 Level - Tier.MinLevel

소모 아이템 = CostItemCnt × (1 + CostItemMult × n)
소모 재화   = CostCurrencyValue × (1 + CostCurrencyMult × n)
```

> **티어를 찾는 기준이 두 가지라 혼동하기 쉽다.**
>
> | 목적 | 조회 키 |
> |---|---|
> | 레벨 상한 | **현재 등급** → `EquipEnhanceTier[Grade].MaxLevel` |
> | 비용 | **현재 레벨** → `MinLevel ≤ Level ≤ MaxLevel` 인 티어 |
>
> 승급 직후에는 둘이 달라진다. Rare로 승급한 25레벨 장비는 상한이 60(Tier_3)이지만 비용은 Tier_2를 쓴다.

`n` 은 구간 내 상대 레벨이므로 티어가 바뀌면 0으로 리셋된다. 구간의 시작 비용은 `CostItemCnt` 그 자체다.

**계산 예시** — `CostItemCnt=10, CostItemMult=0.1` 인 Tier_2(21~40레벨)

```
21레벨 → n=0  → 10 × (1 + 0.1 × 0)  = 10
30레벨 → n=9  → 10 × (1 + 0.1 × 9)  = 19
40레벨 → n=19 → 10 × (1 + 0.1 × 19) = 29
```

> **티어 경계 검증** — 구간마다 배율이 리셋되므로 데이터를 잘못 넣으면 티어 경계에서 비용이 역전될 수 있다. `이전 티어 최대 비용 ≤ 현재 티어 최소 비용` 을 검증하는 것이 좋다.

### 6.2 승급

**조건**

- 재료와 재화만 있으면 승급할 수 있다. **레벨 조건은 없다.**
- `EquipPromotion` 에서 `(슬롯, 현재 등급)` 으로 행을 찾고, `ToGrade` 가 비어 있으면 승급 불가다.
- 현재 등급이 `Equipment.MaxGrade` 에 도달했으면 승급 불가다.

**결과**

```
Grade   = ToGrade (+1 단계)
Level   = 유지
Purity  = 유지
Quality = 유지
```

레벨이 유지되고 상한만 확장되므로, 저레벨에서 먼저 승급하든 만렙을 찍고 승급하든 **최종 결과는 동일하다.** 성장 경로에 따른 손해가 발생하지 않는다.

### 6.3 비용 처리

`UpgradeCost` 구조체가 `아이템 또는 재화 + 필요량 + 보유량`을 함께 싣는다. UI가 부족분을 바로 표시할 수 있게 하기 위함이다.

**전부 충분할 때만 차감한다.** 검사를 먼저 끝내고 차감하므로 부분 차감이 남지 않는다.

> **강화·승급은 현재 클라이언트 로컬 권위다.** 서버 검증이 없다.

## 7. 아이템 생성 절차

구현: `Contents/Items/EquipmentFactory.cs`

### 7.1 절차

| 단계 | 처리 | 참조 |
|---|---|---|
| 1 | 대상 ItemID 결정 | 보상 시스템 |
| 2 | 등급 추첨 | `EquipGradeWeight` |
| 3 | 순도 추첨 | `EquipPurity.AssignWeight` |
| 4 | 품질 추첨 | `EquipQuality` 구간 → 구간 내 균등 |
| 5 | `Level = 1` 로 인스턴스 생성 | — |

세 가지 생성 경로가 있다.

| API | 용도 |
|---|---|
| `Create(itemId, gradeWeightId)` | 일반 드랍. 전부 추첨 |
| `CreateFixed(itemId, grade)` | 등급만 지정. 개발·테스트 |
| `CreateExact(itemId, grade, purity, quality)` | 전부 지정. **확정 지급 상품** — 미리보기와 실제 지급이 같은 값을 쓴다 |

### 7.2 등급 추첨 상세

```
1) 드랍처가 지정한 GradeWeightID로 EquipGradeWeight 행 조회
2) 유효 등급 범위 산출
     하한 = Item.Grade
     상한 = Equipment.MaxGrade
3) 범위 밖 등급의 가중치를 0으로 제외
4) 남은 가중치 합이 0이면 → 해당 드랍을 스킵한다 (null 반환)
5) 남은 가중치로 재정규화 후 추첨
```

> **가중치 합이 0이면 드랍하지 않는다**
>
> 전설부터 시작하는 장비가 "필드 - 초반" 그룹(전설·신화 가중치 0)에서 뽑히면 유효 등급이 하나도 없다. **최소 등급으로 강제 배정하지 않는다** — 등급 가중치로 걸어둔 구간 제한이 무력화되기 때문이다.

**재정규화 예시** — `Item.Grade = Rare`, `MaxGrade = Mythic` 인 장비를 `20003`(보스 - 후반)에서 뽑는 경우

| 등급 | 원본 가중치 | 유효 여부 | 재정규화 확률 |
|---|---|---|---|
| Normal | 0 | 제외 | — |
| Magic | 50 | 제외 | — |
| Rare | 250 | 유효 | 25.5% |
| Epic | 450 | 유효 | 45.9% |
| Legendary | 230 | 유효 | 23.5% |
| Mythic | 20 | 유효 | 2.0% |

제외된 가중치를 다른 등급으로 몰아주지 않고 남은 가중치끼리 비율을 다시 맞추므로, 그룹이 의도한 상대적 희귀도가 보존된다.

### 7.3 순도·품질 추첨

- **순도** — `AssignWeight` 합에서 가중치 추첨. **드랍처·등급과 무관한 전역 분포**다.
- **품질** — `AssignWeight` 로 구간을 뽑고 `MinValue ~ MaxValue` 사이에서 균등 분포로 정수를 추첨한다.

## 8. 표시 규칙

| 대상 | 표시 형식 | 비고 |
|---|---|---|
| 기본 옵션 | 최종값만 | 구간 표시 없음 |
| 해금 옵션 | 최종값 + (Min ~ Max) 구간 | 품질에 따른 범위를 함께 노출 |
| 순도 | `DisplayName` + `ColorHex` | D~S |
| 품질 | 숫자만 | 별도 등급명·색상 없음 |
| 무기 | 아이템명 옆에 `WeaponType` | 장착 시 바뀌는 마스터리를 함께 노출 |

옵션 문구는 `StatDetail.DisplayFormat` 을 사용한다.

**표기 예시**

```
쌍검 [희귀] Lv.45  순도 A  품질 60

  공격력 136.8
  근접 피해량 54.5%
  [고급] 공격 속도 12.8% (2 ~ 20%)
  [희귀] 치명타 확률 13% (10 ~ 15%)
```

관련 UI: `UI/Screen/Equipment/EquipmentPresenter.cs`(장비창 + 착용 외형 프리뷰), `UI/Popup/ItemInfoPresenter.cs`(아이템 정보 팝업).

## 9. 제약 사항 및 미구현 항목

### 9.1 데이터가 비어 있는 것

| 항목 | 상태 |
|---|---|
| **강화 비용** | `EquipEnhance` 48행이 **전부 0**이다. 구조만 있고 수치가 없어 강화가 무료다 |
| **승급 비용** | `EquipPromotion` 48행이 **전부 0**이다. `ToGrade` 만 채워져 있다 |
| 아이템 종류 | 장비 18종(무기 4 + 방어구 8 + 장신구 4 + 유물 2), 재료 6종, 소모품 6종 |
| `EquipOption` 수치 | 구조 검증용 임시값. 해금 옵션은 추후 장비별로 차별화 예정 |

### 9.2 미구현

| 항목 | 내용 |
|---|---|
| 순도 상승 기능 | 생성 시 결정 후 변경 불가. 상승 수단 미구현 |
| 품질 상승 기능 | 동일 |
| 아이템별 차등 스킬포인트 | 상위 서적(3포인트 등)은 `Consumable.EffectParam_2` 로 표현 가능하나 데이터 없음 |
| 장비 UID 서버 채번 | 현재 클라이언트가 채번한다 |
| 강화·승급 서버 검증 | 현재 클라이언트 로컬 권위 |

### 9.3 데이터 작성 시 주의

1. `ItemMainCategory` · `ItemSubCategory` · `EquipSlotTypes` enum에 항목을 **중간 삽입하면 기존 ID 규칙과 저장 데이터가 깨진다.** 신규 항목은 반드시 끝에 추가한다.
2. 아이템 ID는 **10자리가 상한**이다. 초과 시 Int32 오버플로우가 발생한다.
3. 하나의 `EquipOptionGroupID` 는 **6개 등급 행을 빠짐없이** 가져야 한다.
4. `Val` 은 **0레벨 기준값**이다. 캐릭터 스탯은 1레벨 기준이므로 규칙이 반대다.
5. `EquipPurity` · `EquipQuality` 의 `CalcRate` 는 기획 확인용이다. 런타임은 `AssignWeight` 를 쓴다.
6. 방어구·장신구에는 근접·원거리 전용 피해 옵션을 주축으로 넣지 않는다. 무기를 바꾸면 사장된다.
7. 해금 옵션에 `SkillGrant` · `Modifier` 를 쓸 때는 `MinVal = MaxVal` 로 고정한다.
8. `WeaponType` 을 추가할 때는 `WeaponMastery` 행도 함께 만든다. 대응 마스터리가 없는 `WeaponType` 은 오류다.
9. `Percent` 계열 옵션 값은 소수로 적는다. 15%는 `0.15` 다.
10. 비율(Ratio/Amp) 옵션은 `Atk` · `MaxHp` · `HpRegen` · `Def` · `LifeOnHit` **5개 스탯에만** 붙일 수 있다 (`기반테이블_설계.md` 3.3).
