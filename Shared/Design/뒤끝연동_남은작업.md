### 3단계 — 소셜·계정
- [x] **우편**: 뒤끝 관리자·랭킹 우편으로 교체(`BackndMailProvider`, 수령 시 서버 지급)
- [x] **랭킹**: 뒤끝 유저 리더보드로 교체(`BackndRankingProvider`, `Function_Ranking.cs`) — 최고 전투력, 보상 없음 (새 테이블 구조는 실기 확인 전)
  - **테이블 2개**: `USER_RANKDATA`(비공개) = 랭킹 점수 컬럼(지금 `BattlePower`), 리더보드가 컬럼을 가져다 쓴다 / `USER_PROFILE`(공개) = 정보 스냅샷 `Data`(`PlayerProfileDto` — 히어로 레벨·총합 마스터리 레벨·현재 전투력·최고 전투력·장착 장비·코스튬). 프로필은 랭킹과 무관한 정보 보기다
  - **전투력은 서버가 계산한다** — 공유 `Shared/Ranking/BattlePowerRules`(기본 스탯·장비·마스터리·펫, 저장 데이터와 테이블만 사용). 클라가 보내는 값은 없다
  - 갱신(`RankOps.Refresh`)은 전투력이 바뀌는 펑션이 저장을 끝낸 뒤 스스로 한다: SaveLoadout, EquipmentEnhance/Promote/Transfer, SaveMasteryTree, PetEnhance/Promote, SaveAppearance(코스튬), 그리고 레벨이 오르거나 펫을 얻었을 때의 FieldSettle/FieldSessionRotate/FieldBossKill/DungeonClear/ShopBuy/MailReceive. 기존 계정은 로그인(GetUserData) 때, 그리고 RankList 첫 페이지 조회 때도 맞춘다
  - 점수는 최고 기록일 때만 오른다(파밍 세트로 낮아져도 유지). 스냅샷은 지금 모습이고 달라졌을 때만 쓴다. 갱신 실패는 본래 행동을 실패시키지 않으며, 원인은 RankList 응답의 error 로만 보인다(`[BackndRankingProvider] 내 랭킹 갱신 실패`)
  - **전 유저가 리더보드에 등록된다.** 리더보드 항목은 콘솔에서만 지울 수 있어(SDK·펑션에 삭제 기능 없음, 테이블 행을 지워도 순위 정보는 남는다) 순위권 밖 정리·커트라인은 넣지 않았다
  - 뒤끝 제약: 리더보드 대상 테이블은 비공개여야 한다(공개면 400 bad public Table) / 목록은 한 번에 50명까지 / 초기화가 설정된 리더보드는 초기화 1시간 전부터 갱신 실패
  - 클라: 목록은 100위까지만. 처음 50명을 받고 스크롤이 끝에서 20줄 안으로 오면 다음 50명을 딤 없이 이어 받는다(`RankList` offset 0/50, 슬롯은 프레임당 10개씩 생성). 목록 5분 캐시, 유저 정보는 누를 때마다 조회. 내 순위는 9,999위까지 숫자, 10,000위부터·미등록은 `---`(`PlayerRankSlot.MaxCountedRank`)
  - 화면의 전투력(`BattlePowerCalculator`, 살아 있는 히어로)과 서버 계산은 **구현이 따로**다 — 새 영구 스탯 출처(IHeroAspect)를 추가하면 `BattlePowerRules` 에도 넣어야 두 값이 같게 유지된다(2026-10-04 두 상태에서 일치 확인)
  - 콘솔 설정: ① `USER_RANKDATA`(비공개, `BattlePower` 숫자) ② `USER_PROFILE`(공개, `Data`) ③ 유저 리더보드 제목 `BattlePower`, 테이블 `USER_RANKDATA`, 컬럼 `BattlePower`, 내림차순. 서버는 제목으로 uuid 를 찾는다
  - **랭킹 추가 절차**(균열 최고 웨이브 등): `USER_RANKDATA` 에 숫자 컬럼 추가 → 콘솔에 그 컬럼을 보는 리더보드 생성 → 점수가 바뀌는 서버 펑션에서 `submitScore(리더보드 제목, 컬럼, 점수)` 호출 → 조회 펑션·클라 Provider 를 보드별로 확장
- [x] **닉네임 자동 부여**: 최초 로그인(GetUserData)에서 닉네임이 없으면 서버가 `Player` + 8자리 숫자(예: `Player48291034`)를 뒤끝 계정 닉네임으로 등록(`Function_Nickname.cs`)
  - 값: 계정 gamerId(UUID)를 64비트로 접어 XOR·곱셈으로 섞고 1억으로 나눈 나머지. 키는 서버 상수
  - 펑션 컨텍스트에서는 `Backend.UID`가 비어 있고 GetUserInfoV2 에도 uid 가 없어 gamerId 를 쓴다
  - 중복(409)이면 시도 번호를 섞은 다음 값으로 재시도(최대 10회) — 중복 닉네임은 생기지 않는다
  - 실패해도 로그인은 진행, 다음 로그인에 재시도. 클라는 응답 nickname 을 `MyPlayerProfile`에서 쓴다

## 우편 첨부 차트(MailItem) 갱신 절차
1. `Shared/Backnd/MailItem.bat` 실행 → 같은 폴더에 `MailItem.csv` (테이블 .bytes 기준이라 엑셀을 고쳤으면 ExcelDataTable 변환을 먼저)
   - 행: 재화 전부 + 장비를 뺀 아이템 전부(스택·수집품). 컬럼 `MailItemID, RewardType, TargetID, Name`
2. 뒤끝 콘솔 차트 관리에 MailItem 이름으로 업로드(재업로드)하고 '우편 사용'을 켠다.
3. 우편 발송 시 MailItem 차트에서 행을 고르고 수량을 입력한다. 서버는 RewardType·TargetID·수량만 본다.
- 아이템·재화를 추가·삭제하면 다시 내보내서 올린다. 테이블에 없는 첨부는 서버가 지급하지 않고 건너뛴다.

## 새 펑션 추가 절차 (공통 패턴)
1. 공유 규칙 `Core/Network/Shared/<영역>/<영역>Rules.cs` — 클라·서버가 같은 판정을 쓴다.
2. 패킷 `Shared/Packet/Packet_<영역>.cs` + `FunctionName` 상수
3. 서버 `Server/Functions/BackendFunction/Function_<영역>.cs` + `Function_Main.cs` 분기
   - 처리 순서: `GameData.EnsureLoaded` → req 파싱 → `MyData.Load` → 판정 → 변경 → `TransactionWriteV2`
4. 클라 `NetworkManager.Request<X>`
   - 버튼 1회 행위는 딤을 쓴다.
   - 전투 중 자동 처리·묶음 전송은 딤을 쓰지 않는다.
5. 재화 반영은 차감량(증감)으로만 한다. 미정산 필드 처치분과 섞여도 값을 덮어쓰지 않기 위해서다.
6. 새 USER_ 테이블은 뒤끝 콘솔에서 먼저 만든다(`Data` 컬럼에 JSON, 비공개). GetUserData에서 ensure한다.
7. 검증: 서버 `dotnet build` / Unity 컴파일 → Build.bat 배포 → 실기 확인
