# 출석 시스템 설계

> 2D 탑다운 방치형 핵앤슬래시 (Unity, 싱글플레이) — 주간 / 월간 출석 보상
> 관련 문서: `보상시스템_설계.md`, `히어로패스시스템_설계.md`, `뒤끝서버시스템_설계.md`
> **이 문서는 현재 구현 상태를 기술한다.** 컬럼·행 수는 실제 테이블 기준, 동작 서술은 `Contents/DailyBonus/` 와 클라·서버 공용 규칙 `Core/Network/Shared/DailyBonus/DailyBonusRules.cs` 구현 기준이다.

## 1. 개요

### 1.1 구성 요소

| 대상 | 파일 | 시트 | 현재 행 수 |
|---|---|---|---|
| 출석 | `DailyBonus.xlsx` | `#Enum` (`DailyBonusType`) | 3값 |
| | | `DailyBonus` | 47 (주간 7 + 월간 30 + 신규 10) |

| 런타임 | 파일 |
|---|---|
| 규칙 (클라·서버 공용) | `Core/Network/Shared/DailyBonus/DailyBonusRules.cs` |
| 진행도 도메인 | `Contents/DailyBonus/DailyBonusBook.cs` |
| 조회 위임 · 정합성 검증 | `Contents/DailyBonus/DailyBonusCatalog.cs` |
| 하루 경계 | `Core/Network/Shared/Dungeon/ResetDay.cs` (클라 `DailyReset`) |
| 저장 DTO | `Core/Network/Shared/Dto/DailyBonusDto.cs` |
| UI | `UI/Popup/DailyBonusPopupPresenter.cs`, `DailyBonusPopup.cs` |

### 1.2 핵심 규칙

- 출석은 **종류마다 따로 도는 순환 보상**이다. 주간(7일)과 월간(30일)이 동시에 진행된다.
- 종류마다 **"다음에 받을 일차"** 하나만 기억한다. 받으면 일차가 1 오르고, 마지막 일차를 받으면 1일차로 돌아간다.
- **하루에 한 번, 종류마다 따로 받는다.** 하루 경계는 한국 시간 오전 6시다.
- **연속 출석이 아니다.** 며칠을 쉬어도 일차가 초기화되지 않고 이어진다.
- **수령은 서버 권위다.**

## 3. `DailyBonus` 테이블 (5컬럼)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ID` | `!int` | 일련번호 |
| `DailyBonusType` | `!DailyBonusType` | 종류 |
| `DayCount` | `!int` | 일차 (1부터) |
| `RewardGroupID` | `!int` | → `Reward.GroupID` |
| `IsDisabled` | `!bool` | TRUE 면 이 행을 사이클에서 뺀다 |

**한 종류에서 `IsDisabled` 를 뺀 행을 `DayCount` 오름차순으로 세운 것이 한 사이클이다.** 사이클 길이가 곧 순환 기준이다 — 길이를 컬럼으로 따로 두지 않는다.

| 종류 | 사이클 | 보상 그룹 |
|---|---|---|
| `Week` | 7일 | `7101` ~ `7107` |
| `Month` | 30일 | `7201` ~ `7230` |
| `Newbie` | 10행 | **전부 비어 있다** |

> **`DayCount` 는 1부터 빈틈없이 이어져야 한다.** 중간이 비면 순환 카운터가 그 칸에서 영원히 멈춘다. 조용히 깨지므로 `DailyBonusCatalog.Build()` 가 부팅 때 잡는다.

## 4. 진행과 수령

### 4.1 판정

```
오늘 받을 수 있는가 = lastClaimedDay != 오늘      (ResetDay 값)
받을 보상           = 그 종류의 dayCount 일차 행
수령 후             = lastClaimedDay = 오늘
                      dayCount = (dayCount 가 사이클 끝이면 1, 아니면 +1)
```

`ResetDay` 는 한국 시간 오전 6시에 값이 바뀌는 갱신일 번호다. 절대 날짜가 아니라 **"하루가 넘어갔는가"를 비교하는 데만** 쓴다. 클라와 서버가 같은 식을 쓴다.

두 종류의 수령일은 따로 저장하지만 하루 경계가 같아 실제로는 같이 움직이고, **일차만 사이클 길이가 달라 따로 순환한다.**

### 4.2 수령 흐름

```
팝업에서 Focus 가 켜진 칸을 누른다
  └ 서버 DailyBonusClaim     서버 시간(KST 06시)으로 오늘 수령 여부와 일차를 판정 → 보상 추첨·지급 → 저장
       └ 응답                 지급 결과를 인벤/지갑에 반영 (RewardGranter.FromServer)
                              DailyBonusBook.MarkClaimed 로 로컬 진행도를 맞춘다
```

> **수령은 사용자가 칸을 눌러야 일어난다.** 팝업을 열자마자 자동으로 주면 무엇을 받았는지 보이지 않아 수령 연출이 성립하지 않는다.

- **주간·월간은 탭마다 각각 눌러서 받는다.**
- 받고 나면 그 칸은 체크 표시로 바뀐다. 받은 칸을 다시 누르면 보상 정보 팝업이 뜬다.
- 응답 전 재요청은 대기 중 표시로 막는다. 계정 반영은 팝업이 닫혔어도 한다.
- 팝업은 다음 초기화(오전 6시)까지 남은 시간을 보여준다.

### 4.3 일차는 "누른 날"에만 오른다

> **접속만 하고 누르지 않으면 일차가 오르지 않는다.** 출석일 누적과 보상 수령이 한 값으로 묶여 있기 때문이다.
>
> "접속만 해도 일차는 오르고, 밀린 보상은 나중에 받는" 형태로 바꾸려면 출석일 누적과 보상 수령을 갈라 저장해야 한다 (`DailyBonusBook` 의 TODO).

부수 효과로 **놓친 날의 보상은 사라지지 않고 뒤로 밀린다.** 3일차를 받은 뒤 일주일을 쉬고 와도 다음에 받는 것은 4일차다.

## 5. 저장 데이터

```
progress   List<{
               typeId            ← DailyBonusType (정수)
               dayCount          ← 다음에 받을 일차 (1부터)
               lastClaimedDay    ← 마지막으로 수령한 날 (ResetDay 값)
           }>
```

서버(`USER_DAILYBONUS`)가 보관한다 (`DailyBonusDto`). 진행 기록이 없는 종류는 1일차·미수령으로 취급한다.

## 7. 검증 규칙

`DailyBonusCatalog.Build()` 가 부팅 시 검사한다 (`RewardCatalog` 이후에 불려야 한다 — 보상 그룹의 존재를 본다).

| # | 항목 | 분류 |
|---|---|---|
| 1 | 종류별 `DayCount` 가 1부터 빈틈없이 이어지는가 | 경고 (순환이 그 칸에서 멈춘다) |
| 2 | `RewardGroupID` 가 비었거나 그 그룹에 `Reward` 행이 없는가 | 경고 (종류마다 한 줄로 묶어 보고) |
| 3 | 팝업의 칸 수가 사이클 길이보다 적은가 | 런타임 경고 (`DailyBonusPopup`) |

> 보상 누락을 종류마다 한 줄로 묶는 이유 — 통째로 비어 있는 종류(아직 안 채운 신규 출석)가 콘솔을 수십 줄 덮으면 진짜 구멍 하나를 못 본다.

## 8. 미결 / 다음 작업

- **신규 유저 출석(`Newbie`) 미완** — enum 값과 10행이 있으나 보상 그룹이 전부 비어 있고, 팝업에 탭이 없어 받을 수 없다. "가입 후 N일" 같은 1회성 규칙이라면 순환하지 않는 종류를 다룰 구조도 필요하다.
- **일차가 누른 날에만 오른다** — 4.3절.
- **보상 데이터가 임시다** — 전부 재화다.
- **출석 알림이 없다** — 받을 보상이 있다는 표시(배지)가 메뉴에 없다.
