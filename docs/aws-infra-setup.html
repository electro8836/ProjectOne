AWS 인프라 구축 가이드

ProjectOne AWS 백엔드 연동 — 3단계 · 작성 2026-06-18 · 따라하기용

이 문서는 docs/aws-backend-roadmap.md의 3단계(AWS 인프라 구축)를 콘솔에서 직접 따라 할 수 있도록 풀어 쓴 가이드다. 1·2단계(Repository 비동기화 / 액션 계층 설계)는 이미 완료됐고, 이 단계가 끝나면 4단계(Unity 인증 플로우)와 5단계(서버 구현체 결선)로 넘어간다.

⚠ 인증 방식 — 로드맵과의 차이
로드맵 원문에는 Cognito Identity Pool이라 적혀 있으나, 이 문서는 Cognito User Pool 기준으로 진행한다.
  • User Pool(채택): 구글을 페더레이션 IdP로 연결 → User Pool이 JWT를 발급 → API Gateway의 JWT Authorizer가 검증. Lambda는 토큰의 sub를 userId로 쓴다. 서버리스 API 보호의 표준이며 우리 인터페이스와 1:1로 맞는다.
  • Identity Pool: 구글 토큰을 AWS 임시 자격증명으로 바꿔 클라가 DynamoDB에 직접 접근하는 방식. 우리는 API Gateway를 경유하므로 필요 없다.
이 변경은 3단계 완료 후 로드맵 문서에도 반영할 것.

1. 사전 준비

  • AWS 계정 + 콘솔 로그인
  • 구글 계정 (Google Cloud Console 접근용)
  • 이 문서 예시 리전: 서울(ap-northeast-2) — 모든 리소스를 같은 리전에 만든다.
💡 표기 규약
<...>로 감싼 값은 본인 환경 값으로 치환한다. 예: <ACCOUNT_ID>, <USER_POOL_ID>, <APP_CLIENT_ID>.
진행하면서 아래 값들을 메모장에 적어두면 뒤 단계가 수월하다:
① User Pool ID ② App Client ID ③ User Pool 도메인 ④ API 엔드포인트 URL ⑤ 계정 ID

2. 아키텍처 개요

[Unity 클라]
   │  ① 구글 로그인 → Cognito User Pool 페더레이션
   │  ② User Pool 이 ID Token(JWT) 발급
   ▼
[API Gateway · HTTP API]  ── JWT Authorizer(User Pool 검증) ──┐
   │  GET  /userdata/{key}            → Lambda loadUserData    │
   │  PUT  /userdata/{key}            → Lambda saveUserData    │ 모든 요청에
   │  POST /commands/claimDungeonReward → Lambda claim...      │ JWT 필요
   ▼                                                           ┘
[Lambda]  ── JWT 의 sub 를 userId 로 사용 ──▶ [DynamoDB]
                                               PK userId / SK domainKey

저장 계층(read/write)은 /userdata/{key}, 액션 계층(서버 권위 계산)은 /commands/*로 분리한다. 이는 코드의 IServerDataRepository ↔ IServerCommand 두 계층과 정확히 대응한다.

3. Google OAuth 클라이언트 생성

User Pool이 구글 로그인을 위임받으려면 구글 측 OAuth 클라이언트가 필요하다. (User Pool 도메인을 먼저 만들어야 리디렉트 URI를 채울 수 있으므로, 이 단계와 4단계를 오가게 된다 — 일단 클라이언트만 만들고 리디렉트 URI는 4단계에서 채운다.)

  1. Google Cloud Console → 프로젝트 생성(또는 선택)
  2. API 및 서비스 → OAuth 동의 화면 → 외부(External) → 앱 이름/이메일 입력해 생성
  3. API 및 서비스 → 사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID
  4. 유형: 웹 애플리케이션
  5. 생성 후 나오는 클라이언트 ID와 클라이언트 보안 비밀을 메모 (User Pool 설정에 넣는다)
⚠ "승인된 리디렉션 URI"는 4단계에서 User Pool 도메인이 정해진 뒤 https://<도메인>/oauth2/idpresponse 형태로 추가한다. 지금은 비워두거나 임시로 둔다.

4. Cognito User Pool + 구글 연동

콘솔: Cognito → 사용자 풀 생성

  1. User Pool 생성: 로그인 옵션은 이메일 정도면 충분(구글 페더레이션이 주 경로). 이름 예: ProjectOne-Users
  2. 생성 후 소셜 및 외부 공급자 → 자격 증명 공급자 추가 → Google
    • 클라이언트 ID / 클라이언트 보안 비밀: 3단계에서 받은 값 입력
    • 승인 범위(scopes): profile email openid
    • 속성 매핑: 구글 email → User Pool email, sub → username(또는 기본값)
  3. 앱 클라이언트 생성 (앱 통합 → 앱 클라이언트):
    • 유형: 퍼블릭 클라이언트(게임 클라엔 시크릿 미사용 권장)
    • 이름 예: ProjectOne-GameClient
    • OAuth 흐름: Authorization code grant
    • OAuth 범위: openid email profile
    • 활성화 IdP: Google 체크
  4. 호스팅 UI 도메인 설정 (앱 통합 → 도메인): Cognito 관리형 도메인 생성 → 예 projectone-auth → 전체 도메인 https://projectone-auth.auth.ap-northeast-2.amazoncognito.com
  5. 콜백/로그아웃 URL(앱 클라이언트 → 호스팅 UI): 4단계 Unity에서 쓸 리디렉트를 등록. 개발용 예: http://localhost/callback (실제 값은 4단계 인증 구현 시 확정)
  6. 위 5번 도메인이 정해지면 3단계 Google 콘솔로 돌아가 승인된 리디렉션 URI에 https://<도메인>/oauth2/idpresponse 추가
💡 메모할 값 — USER_POOL_ID (예 ap-northeast-2_XXXXXXXXX), APP_CLIENT_ID, 호스팅 도메인. 4·5단계와 API Gateway Authorizer에서 쓴다.

5. DynamoDB 테이블 생성

콘솔: DynamoDB → 테이블 생성

항목값
테이블 이름ProjectOneUserData
파티션 키(PK)userId (문자열) — JWT의 sub
정렬 키(SK)domainKey (문자열) — character / inventory / skill / currency
용량 모드온디맨드(개발 단계 권장 — 사용량만큼 과금)

한 유저의 도메인별 데이터가 아이템 1건씩 들어간다. 아이템 형태:

{
  "userId":    "google_1029384756",   // PK = JWT sub
  "domainKey": "inventory",           // SK
  "data":      "{\"items\":[...]}",   // 도메인 DTO 를 JSON 문자열로 보관
  "updatedAt": 1718700000000
}
💡 왜 data를 JSON 문자열로? 클라(Unity)가 JsonUtility로 직렬화한 DTO를 그대로 주고받으면 서버/클라 양쪽 변환이 단순해진다. 서버가 값을 계산해야 하는 claimDungeonReward에서만 파싱한다.

6. IAM 실행 역할 / 정책

Lambda가 DynamoDB에 접근할 권한. 콘솔: IAM → 역할 → 역할 만들기 → 신뢰 주체 Lambda

  1. 관리형 정책 AWSLambdaBasicExecutionRole 부착(CloudWatch 로그용)
  2. 아래 인라인 정책 추가 — 우리 테이블에만 최소 권한:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProjectOneUserDataAccess",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:Query",
        "dynamodb:UpdateItem"

      "Resource": "arn:aws:dynamodb:ap-northeast-2:<ACCOUNT_ID>:table/ProjectOneUserData"

역할 이름 예: ProjectOne-Lambda-Role. 세 Lambda가 공유한다.

7. Lambda 함수

런타임 Node.js 20.x / 핸들러 index.handler / 실행 역할 ProjectOne-Lambda-Role / 환경변수 TABLE_NAME = ProjectOneUserData

함수 3개를 만든다. AWS SDK v3는 Node 20 런타임에 기본 포함되어 별도 설치가 필요 없다(콘솔 인라인 편집 가능).

7-1. loadUserData — GET /userdata/{key}

코드의 IServerDataRepository.LoadAsync<T>(key, ct) → (found, data)에 대응. 응답을 { found, data } 형태로 맞춘다.

const { DynamoDBClient } = require("@aws-sdk/client-dynamodb");
const { DynamoDBDocumentClient, GetCommand } = require("@aws-sdk/lib-dynamodb");

const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const TABLE = process.env.TABLE_NAME;

exports.handler = async (event) => {
	const userId = event.requestContext?.authorizer?.jwt?.claims?.sub;
	const key = event.pathParameters?.key;
	if (!userId || !key) {
		return resp(400, { message: "userId/key 누락" });
	}

	const out = await ddb.send(new GetCommand({
		TableName: TABLE,
		Key: { userId, domainKey: key },
	}));

	if (!out.Item) {
		return resp(200, { found: false, data: null });
	}

	// data 는 JSON 문자열 → 객체로 풀어서 반환(클라가 다시 DTO 로 역직렬화)
	return resp(200, { found: true, data: JSON.parse(out.Item.data) });
};

function resp(status, body) {
	return {
		statusCode: status,
		headers: { "content-type": "application/json" },
		body: JSON.stringify(body),
	};
}

7-2. saveUserData — PUT /userdata/{key}

코드의 SaveAsync<T>(key, data)에 대응. 요청 본문은 도메인 DTO 그 자체.

const { DynamoDBClient } = require("@aws-sdk/client-dynamodb");
const { DynamoDBDocumentClient, PutCommand } = require("@aws-sdk/lib-dynamodb");

const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const TABLE = process.env.TABLE_NAME;

exports.handler = async (event) => {
	const userId = event.requestContext?.authorizer?.jwt?.claims?.sub;
	const key = event.pathParameters?.key;
	if (!userId || !key) {
		return resp(400, { message: "userId/key 누락" });
	}

	const dto = event.body || "{}"; // 클라가 보낸 도메인 DTO(JSON 문자열)
	await ddb.send(new PutCommand({
		TableName: TABLE,
		Item: {
			userId,
			domainKey: key,
			data: dto,               // 문자열 그대로 저장(파싱 불필요)
			updatedAt: Date.now(),
		},
	}));

	return resp(200, { ok: true });
};

function resp(status, body) {
	return {
		statusCode: status,
		headers: { "content-type": "application/json" },
		body: JSON.stringify(body),
	};
}

7-3. claimDungeonReward — POST /commands/claimDungeonReward

코드의 IServerCommand 액션. 요청 { mapId, characterId } → 응답 { grants, inventory, character, currency }(=ClaimDungeonRewardResponse). 서버가 보상ID/확률을 계산하는 부분이 핵심이며, 이를 위해 보상 테이블 데이터가 서버에 있어야 한다.

⛔ 미완성 지점 — 보상 테이블 반입
확률 계산을 하려면 Table_MapInfo(맵→ClearRewardIDs)와 Table_Reward(확률/수량)가 서버에 있어야 한다. 이 데이터는 현재 클라의 Excel→.bytes에만 있다.
해결 옵션(3단계에서 확정할 "확률 테이블 위치"):
  • (A) Lambda 동봉: 보상 테이블을 JSON으로 export 해 함수 코드에 포함 — 가장 단순, 밸런싱 시 함수 재배포 필요
  • (B) DynamoDB 설정 테이블: ProjectOneConfig 테이블에 보상 데이터 적재 — 클라 배포 없이 밸런싱 가능(권장 방향)

8. API Gateway (HTTP API) + JWT Authorizer

콘솔: API Gateway → HTTP API 생성 (REST API 아님 — HTTP API가 더 싸고 JWT Authorizer 내장)

  1. API 이름 예: ProjectOne-API
  2. JWT Authorizer 생성 (Authorization 메뉴):
    항목값
    이름CognitoJWT
    Identity source$request.header.Authorization
    Issuer URLhttps://cognito-idp.ap-northeast-2.amazonaws.com/<USER_POOL_ID>
    Audience<APP_CLIENT_ID>
  3. 라우트 + 통합 연결 (각 라우트에 위 Authorizer 부착):
    메서드경로Lambda 통합
    GET/userdata/{key}loadUserData
    PUT/userdata/{key}saveUserData
    POST/commands/claimDungeonRewardclaimDungeonReward
  4. 스테이지는 기본 $default 자동 배포 사용 → Invoke URL 메모 (예 https://abc123.execute-api.ap-northeast-2.amazonaws.com)
⚠ CORS — Unity 빌드(특히 WebGL)나 브라우저 테스트 시 CORS 설정이 필요할 수 있다. HTTP API의 CORS 메뉴에서 허용 Origin/헤더(authorization, content-type)/메서드를 추가한다. 네이티브 빌드(PC/모바일)만 쓸 거면 생략 가능.

9. 동작 테스트

JWT 없이는 모든 라우트가 401이어야 정상(Authorizer 작동 확인):

# 토큰 없이 → 401 Unauthorized 기대
curl -i https://<API>.execute-api.ap-northeast-2.amazonaws.com/userdata/inventory

유효한 ID Token으로 저장 → 로드 왕복(4단계에서 실제 토큰 획득; 그 전엔 Cognito 호스팅 UI나 테스트 유저로 발급):

TOKEN=<Cognito_ID_Token>
BASE=https://<API>.execute-api.ap-northeast-2.amazonaws.com

# 저장(PUT)
curl -X PUT "$BASE/userdata/inventory" \
  -H "Authorization: Bearer $TOKEN" \
  -H "content-type: application/json" \
  -d '{"items":[{"itemId":1001,"count":3,"enhanceLevel":0}]}'

# 로드(GET) → {"found":true,"data":{"items":[...]}}
curl "$BASE/userdata/inventory" -H "Authorization: Bearer $TOKEN"

# 액션(POST) → {"grants":[],"inventory":null,...} (스켈레톤 단계)
curl -X POST "$BASE/commands/claimDungeonReward" \
  -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -d '{"mapId":1,"characterId":101}'
💡 문제 시 각 Lambda의 CloudWatch 로그를 먼저 본다. 401이면 Authorizer(Issuer/Audience), 403이면 IAM 정책, 500이면 Lambda 코드/환경변수(TABLE_NAME)를 의심한다.

  • Lambda loadUserData / saveUserData / claimDungeonReward (TABLE_NAME 환경변수)
  • HTTP API 생성 + JWT Authorizer(Issuer/Audience)
  • 라우트 3개 연결 + Authorizer 부착
  • 토큰 없이 401, 토큰 있을 때 저장/로드 왕복 확인
  • Invoke URL 메모 (4·5단계용)
